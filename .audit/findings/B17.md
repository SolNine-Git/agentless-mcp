## High

### B17-H1 — `view_service.py:167-185`: an inverted range or a negative context renders the whole file, which is exactly the failure the docstring and the tool description promise it prevents

`read_slice` filters intervals on one predicate only:

```python
total = len(text.split("\n"))
satisfiable = [(start, end) for start, end in intervals if start <= total]
...
widened = [(max(1, start - context), min(total, end + context)) for start, end in satisfiable]
rendered = line_wrap_content(text, widened or None, symbols=symbols)
```

Nothing checks `end >= start`, `start >= 1`, or `context >= 0`. When the widened interval comes out inverted, `slices._clamp` (`core/slices.py:119-130`) drops it and falls back to its documented default: `return clipped or [(1, total)]` — the whole file.

Measured on a 40-line file (`ViewService.read_slice` called directly):

| call | lines returned |
| --- | --- |
| `intervals=[(30, 5)], context=0` | 41 (whole file) |
| `intervals=[(10, 10)], context=-50` | 41 (whole file) |
| `intervals=[(-5, -1)], context=0` | 41 (whole file) |
| `resolve_locations(["line: 10"], context=-50)` | intervals `((60, -40))` in the JSON payload, 41 lines in `slice` |

The method's own docstring says the opposite:

> "An interval whose start lies beyond the file's last line cannot be satisfied even in part, so it is reported per item ... instead of being clipped away, **which would leave no intervals and render the whole file as if it were the requested slice**."

So does the agent-facing contract in `prompts/tool_descriptions.json`: *"A range starting beyond the file is reported with the file's true line count, never answered with substitute content."*

The guard keys on a proxy (`start <= total`) rather than on the invariant it protects (the widened interval list is non-empty **and** every entry is a real range). Reachability: the CLI validates (`adapters/cli/main.py:1383`, `if start < 1 or end < start: return None`), the MCP surface does not — `adapters/mcp/server.py:557-559` accepts any `list[list[int]]` and only checks pair length, and `context_lines: int` is unbounded. Failure scenario: an agent transposes a range or passes `context_lines=-1` and gets a whole 4,000-line file back inside a tool response it believes is a 10-line slice — the token blow-out the entire funnel exists to avoid, with no error text to notice.

Recommendation: validate in the service, not in one adapter — it is the owner of the invariant and both front doors call it. Reject `context < 0` outright, and split intervals into satisfiable / unsatisfiable on the full predicate (`start >= 1 and start <= end and start <= total`), reporting the rejects through the existing `slice_range_beyond_file`-shaped per-item message. Then make the fallback explicit: pass `widened` (never `widened or None`) once `intervals` was non-empty, so "the caller asked for ranges and none survived" can never mean "render everything". `resolve_locations` needs the same `context` guard — `core/locs.py:140-146` builds the inverted interval that reaches the response payload.

### B17-H2 — `map_service.py:374-382`: a ranked file with no extracted symbols vanishes from the function-granularity map, focus seeds included

`_group` builds its file list from `totals`, which is derived only from `candidates`:

```python
totals: dict[str, int] = {}
for candidate in candidates:
    totals[candidate.path] = totals.get(candidate.path, 0) + 1
order = sorted(totals, key=lambda path: (-rank.get(path, 0.0), path))
```

`candidates` comes from `_score_symbols`, which emits nothing for a file with an empty `facts.symbols`. A file that ranked into the top ten but declares no symbols — a script, an `__init__`-style module, a file of top-level statements, a file whose grammar produced no tags — is therefore absent from the map entirely, while the file-granularity branch (lines 138-155) lists it.

That contradicts this function's own docstring, verbatim:

> "Every candidate file is listed, including the ones whose symbols all lost the budget ... **A file that vanishes entirely because it placed no symbols is the bounded-view-mistaken-for-complete failure** -- the reader would have no way to know it was ever a candidate."

Measured on a three-file repository where `main.py` contains only `import core` and two call statements:

```
function granularity files: ['core.py', 'app.py']      # main.py absent
file granularity files:     ['core.py', 'app.py', 'main.py']
focus=("main.py",) -> seeds ('main.py',), files ['core.py', 'app.py']
```

The last line is the sharp edge: `--focus main.py` resolves, takes the entire teleport mass, is reported in `seeds` and in `unresolved_seeds=()` — and the file the caller named is not in the answer. Failure scenario: an agent seeds the map on the file it was told the bug is in, sees a map that does not contain it, and concludes the file is irrelevant or that the seed was wrong. The `unresolved_seeds` machinery (the "loud seeds" work) explicitly does not cover this case, because the seed *did* resolve.

Recommendation: build `order` from the chosen file list, not from `totals` — pass `chosen` (or the `by_path` slice) into `_group` so every ranked file gets a header with `omitted=0`, and let `totals.get(path, 0)` supply the count. That also removes the divergence between the two granularity branches. Add a test with a symbol-free file that is both ranked and seeded.

## Medium

### B17-M1 — `map_service.py:117-124`: request fields are unvalidated at the service, and the bound is enforced on the config source rather than on the value

`build` resolves three settings through `projectconfig.resolve` and then trusts whatever comes out:

```python
max_files = projectconfig.resolve(request.max_files, ctx.config.max_files, DEFAULT_MAX_FILES)
granularity = projectconfig.resolve(request.granularity, ctx.config.granularity, GRANULARITY_FUNCTION)
...
if granularity == GRANULARITY_FILE:
```

`core/projectconfig.py:209-211` validates the *file* path strictly — `map_budget` within `[200, 64_000]`, `max_files` within `[1, 200]`, `granularity` against `GRANULARITIES`, each with a warning when it misses. The *request* path is validated only by the CLI's argparse (`choices=GRANULARITIES`, `_positive_int`). `adapters/mcp/server.py:490-505` passes `budget: int | None`, `max_files: int | None` and `granularity: str | None` through untouched.

Consequences, all silent: `granularity="File"` or `"functions"` is not an error, it is a function-granularity map (measured); `budget=0` or a negative budget produces a map with headers and no symbols; `max_files=50_000` scores every symbol in the repository and renders it once for the auto-budget estimate plus `log2(n)` times for the packing search.

This is the "guards key on the invariant, not a proxy" rule failing: the bound is attached to where the value came from, not to the value. A repo owner's committed config is checked more carefully than a live tool call.

Recommendation: move the three bounds into `MapService.build` (or into a `MapRequest` parse step) so both adapters inherit them, reusing `projectconfig`'s existing `MIN_BUDGET`/`MAX_BUDGET`/`MIN_MAX_FILES`/`MAX_MAX_FILES`/`GRANULARITIES` constants. An out-of-range request should refuse with a named bound, the way `fslimits` does, rather than degrade.

### B17-M2 — `view_service.py:167` and `:200`: the reported line count is one too high for every newline-terminated file

```python
total = len(text.split("\n"))
```

A file ending in `\n` — effectively every source file — yields a trailing empty element. Measured on a three-line file `a = 1\nb = 2\nc = 3\n`:

```
whole file:   '1|a = 1\n2|b = 2\n3|c = 3\n4|\n'
(4,4):        '...\n4|\n'
(5,5):        'unsatisfiable: line range 5-5 is beyond m.py (4 lines)'
resolve_locations(["line: 4"]) -> spans ((4, 4),) intervals ((1, 4),)
```

So the map's own tool description ("reported with the file's true line count") is off by one, `read_slice` treats a line that does not exist as satisfiable and answers with a blank numbered line, and `resolve_locations` resolves `line: N+1` rather than reporting it. `tests/unit/test_services.py:228-235` pins the wrong number in a golden-style assertion (`"is beyond ledger.py (10 lines)"` for a nine-line file), so the defect is currently protected by a test.

The same `len(text.split("\n"))` convention appears in `core/refs.py:244` (`line_count`) and `core/slices.py:93-94`, so a fix has to be made in one place and propagated — see cross-block observations.

Recommendation: compute the count once, in a shared helper, discounting a single trailing empty element; feed it to both `total` uses here and to `LocTarget.total_lines`. Update the pinned message in the test deliberately, with the off-by-one named in the commit.

### B17-M3 — `view_service.py:134-144, 163-165, 196-198`: three methods of one service, three different error contracts

* `skeleton` reports per file in `FileView.error` — but a `SecurityRefusal` from `_load` -> `contained_path` propagates and aborts the whole batch, so one bad path in a ten-path call loses the nine good views, while an unreadable path in the same position is reported and skipped.
* `read_slice` reports the load failure in `FileView.error`, and reports an unsatisfiable range in `FileView.text` — an in-band string the MCP handler cannot distinguish from content (`adapters/mcp/server.py:277`: `view.text or view.error`).
* `resolve_locations` raises: `raise RepoResolutionError(error)` where `error` is `"notes.md: no grammar for this file type"` or `"big.py: skipped: 2000000 bytes exceeds the per-file cap"`. Neither is a repository-resolution failure; `RepoResolutionError` is documented in `util/errors.py:33-34` as "a repository root could not be resolved or interrogated". A caller catching that type to distinguish "your --root is wrong" from "that file is not parseable" gets the wrong answer.

The underlying shape is `_load` returning `tuple[str, str, str, str]` with an out-of-band error string in the fourth slot: a stringly-typed, positional error channel that each caller re-interprets its own way. All four of these paths are among the uncovered lines (140-142, 165, 198, 224), which is why the inconsistency has never been felt.

Recommendation: give `_load` one return type (a small frozen dataclass, or a `FileView`-with-error) and pick one contract per failure class — refusals raise, per-file failures return a view carrying the reason. `resolve_locations` should return a `LocationView` whose resolution is empty with a reason, matching how it already reports an unrecognized loc.

### B17-M4 — `map_service.py:173-184`: `skipped` is collected, carried and then never rendered in the text answer

`MapResult.skipped` is populated from `scan.skipped` on both branches and serialized in `as_dict()` (line 97). No text renderer touches it: `render_text` prepends only the unresolved-seed note, `render.render_map` (`application/render.py:758-773`) renders ranked files only, and neither adapter reads the field (`grep -n skipped` over `adapters/` returns nothing). The MCP `repo_map` tool returns text only — `adapters/mcp/server.py:212-228` — so for every agent using the server, files that were too large, unreadable, or had no warmed grammar are simply not in the answer.

`core/refs.py:19-21` states the opposite intent for exactly this data: *"Files that cannot be read, are too large, or whose grammar is not warmed are reported in `skipped` with the reason -- never dropped into an answer that then looks complete."* That guarantee is met by the JSON path and broken by the text path, which is the one the primary consumer sees.

Failure scenario: a repository with an unwarmed Go grammar returns a Python-only map with no indication that half the repository was not considered; the agent reports the symbol does not exist.

Recommendation: render a one-line footer (or reuse the `# note:` header style already used for unresolved seeds) naming the skipped count and the first few reasons. It is the same "bounded view mistaken for complete" defense `_group`'s docstring argues for.

### B17-M5 — `map_service.py:56-68` vs `adapters/mcp/server.py:219-220` and `adapters/cli/main.py:1409-1424`: one precedence rule, two adapter-side implementations

`MapRequest`'s docstring makes the case for resolving precedence in the service — *"Resolving that here rather than in each adapter is what keeps the CLI and the MCP server from answering the same question two ways"* — and then exempts `budget`, which is consequently resolved twice:

```python
# server.py
if request.budget is None and ctx.config.map_budget is not None:
    request = replace(request, budget=ctx.config.map_budget)

# cli/main.py
if raw is None:
    return (None if ctx.config.map_budget is None else ctx.config.map_budget), ""
if raw == AUTO_BUDGET:
    return None, ""
```

They agree today. They are also the only place the rule lives, so a change to it has to be made twice with nothing to catch the miss. The exemption is caused by `None` carrying two meanings (`unsaid` and `auto`), which a sentinel would remove.

A second consequence: the MCP surface cannot express "auto" at all. A repository whose `.agentless-mcp.json` sets `map_budget` gives every MCP caller that budget with no way to ask for auto-sizing, while `--budget auto` works on the CLI. Undocumented asymmetry between two front doors onto the same service.

Recommendation: introduce an explicit `AUTO` sentinel (or `budget: int | Literal["auto"] | None`) so `MapRequest` can carry all three states and `MapService.build` owns the precedence for all three settings.

## Low

### B17-L1 — dead defensive branches against conditions the call site prevents
`rank`'s keys are `graph.nodes`, which is `tuple(sorted(facts.path for facts in scan.files))` (`core/graph.py:130`), which is exactly `by_path`'s key set. So `map_service.py:347-348` (`if facts is None: continue`), the two `if path in by_path` guards at `:143` and `:151`, and `if definition.path in known` at `:313-314` can never take their false branch. Line 348 being one of only three uncovered statements in the file is the evidence. Delete them; a genuine invariant violation should surface, not be skipped.

### B17-L2 — `GRANULARITIES` has two homes
`core/projectconfig.py:55` spells `("function", "file")` as literals; `map_service.py:45` builds the same tuple from its two constants. The config validator and the service that consumes the value can drift apart — a third granularity added to the service would be rejected by the config loader with a "must be one of" warning. Because core cannot import application, the single home has to be core, with `map_service` re-exporting.

### B17-L3 — `_pack`'s binary search assumes a monotonicity the renderer does not guarantee
`map_service.py:192-205` binary-searches the number of included symbols, and the module docstring (lines 24-26) claims the result is "the largest prefix of the score ordering that fits". Render size is not strictly monotone in that count: including a file's last symbol adds an entry line but *removes* the `... N more symbols in this file` line (`render.py:770-771`). For a short signature and a long path the removal can outweigh the addition, in which case the search can settle below the true maximum. It never exceeds the budget (`low` only advances to verified-fitting positions), so the impact is a slightly under-full map, not an over-budget one. Either state the weaker guarantee in the docstring or make the search a linear scan from the binary-search result.

### B17-L4 — the documented "~6x compression" auto-budget is inert on ordinary repositories
`_auto_budget` (lines 186-190) divides the full candidate render by 6 and clamps to `[2000, 8000]`. The divisor therefore only governs when the full render is between 12,000 and 48,000 tokens; below that the floor wins. On all three characterization fixtures the whole map is 388-711 tokens, so the estimate is ~120 and the budget is always 2,000 — and `test_the_auto_budget_stays_inside_the_documented_band` passes on the clamp alone, never on the divisor. The module docstring presents the divisor as the operative decision. Worth either a measured note in the docstring or a test that exercises the band.

### B17-L5 — `_load` mixes a resolved root with the raw one
`view_service.py:216-217`: `contained_path` resolves the root internally (`root.resolve()`), then `absolute.relative_to(ctx.root)` uses the unresolved field. `resolve_repo` always stores a resolved root, but `RepoContext` is a public frozen dataclass constructed directly elsewhere (both characterization suites do it), and a relative or symlinked `root` makes `relative_to` raise a bare `ValueError` instead of one of this package's typed errors. Resolve once and use the same value for both.

### B17-L6 — error views name the raw path, success views name the resolved one
`view_service.py:136` and `:165` build `FileView(path=raw, ...)` on the error branch while every success branch uses `resolved`. Two records from the same call describe their subject two ways; the `path` field of a JSON error entry is then whatever the caller typed, including `../` segments. Use `resolved` on both branches (it is already computed and already refused if it escapes).

### B17-L7 — `focus_paths` is core knowledge living in the application layer
`map_service.py:264-316` operates purely on a `core.refs.RefIndex` and a set of scan paths, and `graph_service.py:549` imports it across the application layer to answer the same question for the diagram. The import-linter contract permits it (intra-layer), and the docstring's rationale for making it public is sound. But "what a focus argument means" is a property of the scan, not of the map, and the natural home is `core.refs` beside `definitions_for`, which resolves the sibling question ("what does a lookup target mean").

## Cross-block observations

* **Line counting is one convention implemented three times.** `view_service.py:167`/`:200`, `core/refs.py:244` (`line_count`) and `core/slices.py:93-94` all use `len(text.split("\n"))` and all inherit the phantom trailing line (B17-M2). Whichever block owns `core/slices.py` should get the shared helper; every consumer of a line count is affected, and at least one agent-facing message states the number as "true".
* **The MCP adapter validates nothing that the CLI validates.** Both B17-H1 and B17-M1 have the same shape: `adapters/cli/main.py` performs argument validation (`_parse_ranges`, `_positive_int`, argparse `choices`) that `adapters/mcp/server.py` does not, and the application services trust their inputs because "the adapter checks". Worth a sweep of every MCP tool signature against its CLI counterpart during synthesis — `read_slice`, `repo_map`, `resolve_locations` and `list_dir` (`depth`, `max_entries` are equally unbounded) are the ones visible from this block.
* **`skipped` is collected everywhere and rendered almost nowhere.** `core/refs.RepoScan.skipped` reaches `MapResult` and dies there on the text path (B17-M4). Other services consuming `scan_repo` should be checked for the same drop — the guarantee is stated once, in `refs.py`, and has to be honored by every renderer.
* **`core/slices._clamp`'s "empty means whole file" default is a loaded gun.** `core/slices.py:130` (`return clipped or [(1, total)]`) turns "every interval you gave me was invalid" into "here is everything". It is correct for the genuine no-argument case and dangerous for every caller that filters intervals upstream. Any other block calling `line_wrap_content` with a computed interval list has B17-H1 latent in it.
