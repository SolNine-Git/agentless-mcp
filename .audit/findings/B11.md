## High

### B11-H1 — `detect_communities` accepts a `resolution` it cannot compute with, and answers anyway
`src/agentless_mcp/core/communities.py:161-193` (no validation), scored at `:296`.

`detect_communities` validates nothing about `resolution` or `max_passes`, while its sibling in the same block validates every one of its knobs (`mermaid._validate`, `mermaid.py:248-261`). `resolution` reaches it from user input with only a cast in between:

```python
setting = communities.DEFAULT_RESOLUTION if resolution is None else float(resolution)
partition = communities.detect_communities(ranked.graph, resolution=setting)
```
(`application/graph_service.py:197-198`, fed by CLI `--resolution` with `type=float` and by the MCP `analyze_structure(resolution: float | None)` parameter.)

`float("nan")` passes that cast. Inside `_score` every gain becomes NaN, every `score > best_score + EPSILON` comparison is therefore False, no node ever moves, and the partition degenerates to one community per file with a NaN modularity — the single field a caller would use to detect that the answer is meaningless.

Reproduced against this repository:

```
$ uv run agentless-mcp communities --resolution nan --json | grep -n modularity
14:  "modularity": NaN,
$ uv run agentless-mcp communities --resolution nan | head -4
110 communities over 110 files (modularity nan at resolution nan)
```

Failure scenario: an agent calls `analyze_structure(operation="communities", resolution=<nan or inf from an upstream computation>)` and receives 110 plausible-looking singleton communities. Nothing errors, nothing warns, and the JSON body carries a bare `NaN` token — accepted by Python's `json` and by `jq`, rejected by `JSON.parse`, Go's `encoding/json`, and any RFC 8259 strict parser, so an MCP client outside Python fails to decode the response rather than seeing the bad number. `inf` yields `-Infinity`, same shape. `max_passes=0` is the same class: it silently returns the all-singleton starting state with `passes=0` and a negative modularity.

This is the "Errors surface" invariant failing at the module that owns the arithmetic: a non-finite resolution is a caller bug, not repository content, and the module's own docstring promises `modularity` as the caller's evidence that the detector found something.

Recommendation: give `detect_communities` the `_validate` treatment `mermaid` already has — raise `ValueError` when `resolution` is not finite or is negative, and when `max_passes < 1` — and pin it with tests for NaN, inf, negative resolution, and `max_passes=0`. Validating at the CLI/MCP boundary as well is a separate, additive fix (see cross-block observations); the domain guard is what keeps every future caller honest.

## Medium

### B11-M1 — hitting the pass cap is indistinguishable from converging on it
`src/agentless_mcp/core/communities.py:187-193`.

```python
    passes = 0
    while passes < max_passes:
        passes += 1
        if not _one_pass(nodes, weighted, total, membership, resolution):
            break

    return _partition(membership, weighted, resolution=resolution, passes=passes)
```

`passes` is incremented before the pass runs, so a run that converges on pass 50 and a run that was still moving nodes when the bound cut it off both report `passes == 50`. The comment at `:68-71` calls the bound a guard against a pathological graph spinning, but when it fires the caller is handed a half-converged partition labelled exactly like a finished one, and `modularity` is a real number so nothing looks wrong. `application/graph_service.py:198-216` does not surface `passes` at all, so today the signal dies twice.

Failure scenario: a large monorepo whose local-moving phase needs more than 50 passes gets a stable-looking but arbitrary rollup, and the only way to notice is to rerun with a higher bound and diff.

Recommendation: either carry a `converged: bool` on `CommunityPartition` (set from whether the final `_one_pass` returned zero) or raise when the bound is exhausted. Test: a fixture run with `max_passes=1` must be distinguishable from the same fixture run to convergence.

### B11-M2 — `safe_label` is not injective, so two different modules can render as the same label
`src/agentless_mcp/core/mermaid.py:228-245`.

Every character outside `ALLOWED_LABEL_CHARS` (ASCII letters, digits, `" ._-/"`) becomes `_`, runs collapse to one `_`, and anything past 60 characters is truncated to a shared prefix plus `...`. Both reductions are many-to-one, and nothing downstream disambiguates:

```
safe_label("src/日本.py") -> 'src/_.py'
safe_label("src/中国.py") -> 'src/_.py'

flowchart LR
    n0["src/_.py"]
    n1["src/_.py"]
```

Same for two paths sharing a 57-character prefix. Note the asymmetry inside this module: `_group_label` (`:351-365`) goes out of its way to give repeated *subgraph* titles an ascending ordinal because "two boxes with the same title tell a reader nothing" — the identical problem on node labels is unhandled, and node labels are the ones that carry the file identity a reader needs.

Failure scenario: any repository with non-ASCII filenames (CJK, Cyrillic, accented Latin — `café.py` becomes `caf_.py`) renders a diagram in which distinct modules are visually identical, and the arrows between them cannot be read back to files. Truncation does the same to deep paths, and truncation keeps the *directory* head and drops the filename — the informative half.

Recommendation: keep the allowlist (the injection defence is sound and should not be relaxed) and disambiguate on collision the same way `_group_label` does — an ascending ordinal per repeated label, computed over the sorted selection so it stays deterministic. Consider truncating from the left (`...core/mermaid.py`) so the filename survives. Test: two paths differing only outside the allowlist must render two distinguishable labels.

### B11-M3 — the legend advertises a dashed encoding the default render never contains
`src/agentless_mcp/core/mermaid.py:197-199` with `:403-416`.

The legend is emitted whenever `imports is not None and edge_lines`, but `edge_lines` is non-empty even when every line in it is the "not drawn" comment, and reference edges are all-or-nothing against `max_edges` (default 40). On this repository's own diagram — the only production caller, `graph_service.py:247`, never sets `max_edges` — the result is:

```
$ uv run agentless-mcp diagram | head -2
flowchart LR
    %% solid: imports, dashed: references
$ uv run agentless-mcp diagram | grep -c '\-\.\->'
0
$ uv run agentless-mcp diagram | tail -2
    %% 498 reference edges not drawn (edge bound 40)
```

A legend naming two encodings on a diagram that uses one is the same failure the module docstring says it exists to prevent ("a diagram lying about which references exist"). It is worse in the extreme case reproduced in review, where a graph over the bound with zero import edges renders a legend, three bare nodes and a comment — a legend on a diagram with no edges at all.

Failure scenario: a reader sees "dashed: references", sees no dashed arrows, and concludes the repository has no reference-only edges — the opposite of the 498 the comment counts three screens further down.

Recommendation: emit the legend only when a `-->` and a `-.->` line were both actually produced, and keep the "not drawn" comment unconditional. One-line fix in `render_flowchart`, pinned by a test asserting the legend is absent when the edge bound drops every reference edge.

### B11-M4 — `selected_nodes` exposes half the elision arithmetic, so callers print a different number than the diagram does
`src/agentless_mcp/core/mermaid.py:210-225` with `:203-205`.

`render_flowchart` computes its elision line as `len(candidates) - len(selected)`, where `candidates` is the focus neighbourhood when a focus is set. `selected_nodes` returns only the *selected* half; there is no accessor for the candidate count, so the consumer that wants to report elision has to guess a denominator, and it guesses the wrong one:

```python
elided=max(0, len(ranked.graph.nodes) - len(drawn)),
```
(`application/graph_service.py:259`.)

Reproduced — one response, two answers to the same question:

```
$ uv run agentless-mcp diagram --focus src/agentless_mcp/core/mermaid.py --max-nodes 5 --json
  text: '... n_elided["... 89 more modules"]'
  elided: 105
```

The docstring at `:218-221` argues `selected_nodes` exists so callers do not have to parse the rendered text — but parsing the text is currently the only way to get the number the diagram shows.

Failure scenario: an agent reports "105 modules elided" while the diagram it just relayed says 89; neither number is wrong on its own terms and there is nothing in the response to reconcile them.

Recommendation: return the candidate count alongside the selection (a small frozen result value, or a second function `candidate_count(graph, options)`), and have `render_flowchart` and the consumer read the same number. Test: with a focus set, the count a caller reports equals the integer in the rendered elision line.

### B11-M5 — the partition's JSON surface has no production caller and is duplicated with different semantics
`src/agentless_mcp/core/communities.py:104-112`, `:129-135`, `:137-144`.

`Community.as_dict`, `CommunityPartition.as_dict` and `CommunityPartition.index_of` are called from nowhere in `src/` — grep over the tree finds only `tests/unit/test_communities.py:57,110,117` and the structurally identical, independently maintained `application/render.py:466-484`, which re-derives the same JSON from its own `CommunityReport`/`CommunityRow` with *different* semantics (members truncated to a limit, an added `omitted` count). Two homes for one serialization, one of them shipped and one of them test-only, is the DRY rule failing in the direction that drifts silently: a field added to `Community.as_dict` will never appear in any user-visible output, and the two will disagree the moment either changes.

Failure scenario: a maintainer adds `converged` (see B11-M1) or a member count to `Community.as_dict`, sees the domain test pass, and ships nothing — the CLI and MCP JSON come from `render.py`.

Recommendation: delete `as_dict` from both dataclasses and let `render` own presentation (the layer that already does), or have `render.CommunityReport` build on the domain method instead of re-implementing it. `index_of` is genuinely useful and worth keeping regardless of which way that goes.

## Low

### B11-L1 — the determinism argument in the docstring omits float summation order
`src/agentless_mcp/core/communities.py:32-48`, mechanism at `:236-244` and `:268-271`.

The module states determinism is "a property of three explicit rules", each an ordering decision "that would otherwise be taken by dictionary iteration". There is a fourth: `adjacency[source][target]` accumulation, `degree = sum(adjacency[node].values())` and the per-community `weights` accumulation in `_one_pass` all sum floats in `graph.edges` / adjacency *insertion* order, which is not sorted. Float addition is not associative, so a graph whose edge map was built in a different order can produce last-ULP-different degrees, and `EPSILON = 1e-12` is an absolute threshold against those sums.

Honest scope: I could not construct a divergence — the reordering probes I ran (including a `1e16 / 1.0 / 1.0` triple) came out bit-identical, and `test_edge_insertion_order_does_not_change_the_answer` passes on its fixture. The finding is that the stated guarantee is stronger than the code's, not that a break is reachable today. Recommendation: sum in sorted-key order in `_symmetrise` and `_one_pass` (cheap, both dicts are already small), or amend the docstring to name insertion-order-independence as tested-not-proved.

### B11-L2 — docstring rule 2 does not hold for the value the function returns
`src/agentless_mcp/core/communities.py:38-40` versus `:333`.

The module says "community 0 is always the community of the lexicographically first path, whatever it grows into". That is true of the internal `membership` ids and false of `CommunityPartition.communities`, which `_partition` re-sorts by `(-size, members)` before returning. `detect_communities`'s own docstring (`:169-172`) describes the size ordering correctly, so the two contradict each other. A reader who takes rule 2 as an API guarantee — the next agent generating against this file will — indexes into the wrong community. Recommendation: scope rule 2 to the internal ids explicitly ("the ids the algorithm carries, not the order the partition is returned in").

### B11-L3 — `_group_label` both returns a value and mutates its accumulator, and can exceed the label bound
`src/agentless_mcp/core/mermaid.py:351-365`.

```python
    label = safe_label(community.label)
    drawn[label] = drawn.get(label, 0) + 1
```

A function that returns data and mutates caller state in the same call is the "either returns data or mutates state" rule; here it is a private helper with a small blast radius, hence Low. Measured side effect: a 60-character truncated label plus `" 2"` renders a 62-character title, past the `LABEL_MAX_CHARS` bound the module documents as absolute. Recommendation: compute the ordinals in `_node_lines` from the already-known community sequence and pass a finished title down; re-apply the length bound after the ordinal is appended.

### B11-L4 — three of five `DiagramOptions` knobs and one `detect_communities` knob have exactly one real setting
`src/agentless_mcp/core/mermaid.py:147-161`, `src/agentless_mcp/core/communities.py:161-166`.

`max_edges`, `focus_distance` and `direction` are never set outside `mermaid.py` itself — the only production construction is `DiagramOptions(max_nodes=max_nodes, focus=seed.node or None)` (`graph_service.py:247`) — and `max_passes` is never passed a non-default value anywhere in `src/` or `tests/`. That is not automatically wrong for a value object, but it means the edge bound that silently drops 498 edges on this repository (B11-M3) is not reachable by any user, and `focus_distance`'s validation branch is one of the two uncovered lines. Recommendation: either plumb `max_edges` through the diagram command (the natural pairing with `--max-nodes`) or drop it to a module constant; same choice for `max_passes`.

### B11-L5 — `render_flowchart` computes the candidate set and validates the options twice
`src/agentless_mcp/core/mermaid.py:189-195`.

```python
    candidates = _candidates(graph, settings)
    selected = set(selected_nodes(graph, rank, settings))
```

`selected_nodes` re-runs `_validate` and `_candidates` internally, so a focused render builds the full undirected adjacency map (`_neighbourhood`, an O(E) pass over every edge) twice per call. Correct, just wasteful, and it is the shape that makes B11-M4 easy to miss. Recommendation: have `render_flowchart` call `_bounded(candidates, rank, settings)` directly and leave `selected_nodes` as the public wrapper over both.

### B11-L6 — a label-safety test cannot fail on the injection it names
`tests/unit/test_mermaid.py:400-406`.

```python
        assert '"' not in rendered.replace('["', "").replace('"]', "")
```

The stripping is unanchored, so an escaped title such as `subgraph s0["a"] x"]` reduces to `subgraph s0a x` and passes. The test is named `test_a_community_label_is_sanitised_too` — it is the only assertion standing behind community-label escaping, and it would survive the bug it exists to catch. Every other test in that class asserts exact output; this one should too. Recommendation: assert the full rendered string, as `test_an_injected_filename_renders_as_an_inert_label` (`:361-366`) already does.

### B11-L7 — `_identifier` and `_identifier_index` are coupled by an undocumented format contract
`src/agentless_mcp/core/mermaid.py:264-274` and `:419-426`.

`_identifier` exists to survive a prefix change ("the check in `_identifier` is what keeps that true if the prefixes ever change", `:91-93`) by appending `_` to a reserved word. `_identifier_index` then parses ids back with `int(identifier.lstrip(string.ascii_letters).rstrip("_"))` — which raises `ValueError` on any id whose numeric part is empty, exactly the case the reserved-word guard is designed for (`"end"` -> `"end_"` -> `int("")`). Unreachable with today's `n`/`s` prefixes, so Low, but the guard and its inverse defend against different futures. Recommendation: sort edges by the integer index carried alongside the identifier rather than re-parsing it out of the string; the caller already has it at `:194`.

## Cross-block observations

- **Unvalidated numerics cross the MCP/CLI boundary untouched.** `resolution` travels from `analyze_structure(resolution: float | None)` (`adapters/mcp/server.py:616`) and `--resolution type=float` (`adapters/cli/main.py:357-360`) through `float(resolution)` (`application/graph_service.py:197,241`) into `detect_communities` with no finiteness or range check anywhere on the path (B11-H1). Worth checking whether the same pattern holds for the other numeric tool parameters (`limit`, `max_nodes`, `members`) — `max_nodes` at least lands on `mermaid._validate`, which raises `ValueError`; whoever reviews the MCP adapter should confirm that a `ValueError` from a core module becomes a useful tool error rather than a traceback.
- **JSON output can contain non-finite tokens.** `adapters/cli/main.py` emits `json.dumps(report.as_dict(), indent=2)` at six call sites with default `allow_nan=True`. Any float that reaches a report from a computation can therefore emit bare `NaN`/`Infinity`, which strict (non-Python) JSON parsers reject. A single `allow_nan=False` at those call sites would turn the class of bug into a loud one; that is an adapter-block decision.
- **The elision count is computed in two places with different denominators** (B11-M4): `core/mermaid.py:203` against the focus candidate set, `application/graph_service.py:259` against the whole graph. The service block should not be inventing this number; whichever block owns the fix, the two must read the same value.
- **`render.CommunityReport` duplicates `communities.CommunityPartition`'s serialization** (B11-M5). Reviewers of the render/application block should decide which one is the owner; the domain copy is currently exercised only by tests.
- **B09 dependency note:** `RefGraph.edges` is a `Mapping` whose iteration order is load-bearing for B11's float sums (B11-L1) and irrelevant to its logical result. If B09 ever swaps the edge map for a structure with unstable ordering, B11's documented determinism claim needs revisiting.
