## High

### B13-H1 — `patches.py:553-567` — a block that is `...` on both sides is APPLIED, and it injects a literal `...` line into the source file

```python
    if search == ELISION:
        if not replace or replace[0].isspace():
            return (... "elided search block needs a replacement whose first line starts at column 1")
        anchor = _find_anchor(padded, scopes)
        ...
        return anchor, replace + "\n\n" + anchor, ""
```

The only guard on the replacement side of an elided block is "not empty and does not start with whitespace". `...` satisfies both. `ELISION_PREFIX` stripping at :550 does not help either, because `replace.startswith("...\n")` is false for a bare `...`, and for `replace == "...\n"` exactly the `len(replace) > len(ELISION_PREFIX)` clause deliberately skips the strip.

Verified end to end through the real parser, not by hand-building an `Edit`:

```
### a.py
<<<<<<< SEARCH
...
=======
...
>>>>>>> REPLACE
```
→ `parse_blocks` errors: `()`; `apply_edits` outcome: `applied`, `ApplyResult.ok == True`,
`new_contents == {'a.py': '...\n\nimport os\n\ndef f():\n    return 1\n'}`

Failure scenario: a model that truncates or gets confused mid-generation emits `.../=======/...` — an extremely cheap shape to produce, since `...` is the format's own elision token. The patch is reported as fully applied, `patch apply` writes it, and in Python `syntax_delta` blesses it because `...` is a valid `Ellipsis` expression statement (`{'old_errors': 0, 'new_errors': 0, 'ok': True, 'detail': ''}`). Every gate this block owns says "clean". The file now has a stray statement at module top.

Recommendation: an elided search side must require that the replacement is not itself an elision. Reject when `replace.strip() == ELISION` or when `replace.lstrip().startswith(ELISION)` after prefix stripping, with a `NO_ANCHOR`-family reason naming the block. The same guard should reject `replace == ELISION_PREFIX`, which today inserts `...\n` verbatim.

### B13-H2 — `normalize.py:203-204` — dropping every comment node makes semantically load-bearing comments hash as "the same patch"

```python
        if item.type in COMMENT_NODE_TYPES:
            continue
```

`COMMENT_NODE_TYPES` is `frozenset({"comment", "line_comment", "block_comment"})` (`core/extractor.py:84`). Several tier-1 languages put behaviour in exactly those node types. Measured:

| change | `file_key` equal to no-change? |
| --- | --- |
| `//go:build linux` → `//go:build windows` (go) | **True** |
| `#!/usr/bin/env python3` → `python2` (python) | **True** |
| `x = f()  # type: int` → `# type: str` (python) | **True** |
| deleting `# noqa: F401` (python) | **True** |
| deleting `// @ts-expect-error` (typescript) | **True** |

Failure scenario: `equivalence_key` is the vote's clustering primitive (`core/vote.py:236,272` via `validate_service.py:503`). A candidate that flips a Go build constraint, or changes a shebang, or strips a `# type:` annotation, is clustered as identical to the candidate that changes nothing — so its votes are credited to a class it does not belong to, and the ranking the module exists to fix is corrupted in the direction of the no-op. The module docstring at `normalize.py:11-13` states the design goal as "a change to what the code does moves the key"; for these five inputs it does not.

Recommendation: comment *text* cannot be dropped unconditionally. Either keep comment leaves whose text matches the directive prefixes that are semantic per language (`//go:`, `// +build`, `#!`, `# type:`, `# noqa`, `# pragma`, `@ts-`, `eslint-`), or — cheaper and more honest — keep every comment leaf with its whitespace collapsed and drop only pure-prose reflowing, then say so in the docstring. Whichever is chosen, pin it with a per-language row in `TestEquivalence`.

### B13-H3 — `normalize.py:115-125` — every structurally-empty change collapses onto one universal key, and nothing distinguishes it from a real equivalence class

```python
    diff = "\n".join(difflib.unified_diff(before.splitlines(), after.splitlines(), lineterm=""))
    return hashlib.sha256(diff.encode("utf-8")).hexdigest()
```

When the streams match, `unified_diff` yields nothing, so `file_key` returns `sha256(b"")` = `e3b0c442...` for *any* file and *any* content. Measured:

```
file_key("x = 1  # one\n", "x = 1  # ONE\n", "python")            == e3b0c442...
file_key("def totally(different): pass\n", "...  # hi\n", "python") == e3b0c442...  # equal
equivalence_key({"a.py": ("x = 1  # one\n", "x = 1  # ONE\n")}) ==
equivalence_key({"a.py": ("y = 2\n",        "y = 2  # note\n")})   # True
equivalence_key({}, ...)                                           == e3b0c442...
```

The docstring at :118-121 states this is intended ("a comment-only or whitespace-only edit becomes indistinguishable from no edit at all") but stops there — it does not give the caller a way to *detect* it. The one guard downstream, `validate_service.py:503` (`key = normalized.key if normalized.result.new_contents else None`), keys on the wrong invariant: it asks "did any bytes change", and a comment-only edit changes bytes, so the empty key is admitted as a normal class.

Failure scenario: in a sampling run, every candidate that only touched comments or whitespace in `a.py` — regardless of what it wrote there — lands in one cluster. Since the repository's tests almost certainly still pass for all of them, that cluster is both the largest and fully green, and the vote hands back a patch that changes nothing.

Recommendation: export the empty-diff digest as a named constant (`NO_STRUCTURAL_CHANGE_KEY`) or, better, have `file_key`/`equivalence_key` return `None` for a change with no structural delta, so the type forces the caller to decide. Then change the `validate_service` guard to key on that instead of on `new_contents`.

## Medium

### B13-M1 — `patches.py:307-323` — CRLF patch text parses clean and then fails as "search text not found"

`_split_body` normalises the divider (`line.rstrip() == DIVIDER`, :318) but takes the payload lines raw, so every search and replace line keeps its `\r`. Measured on the exact CRLF form of the corpus's `BARE` fixture:

```
errors: ()
search  = '    return total\r'
replace = '    return round(total, 2)\r'
apply against an LF file → not_found  "search text not found"
```

Failure scenario: an agent on Windows, or one whose model output was round-tripped through a CRLF-normalising editor or a Windows shell redirect, gets a parse that reports zero errors and an apply that reports "search text not found" for a search text that is character-for-character present. The agent's only reasonable next move is to re-derive the search text, which will fail identically, forever.

Recommendation: strip a single trailing `\r` from each payload line in `_split_body` (the divider check already does the equivalent), or refuse the whole text at :226 when it contains `\r\n` with a reason that names line endings. Silent asymmetry between the marker check and the payload is the worst of the three options.

### B13-M2 — `patches.py:288-292` — any non-blank, non-fence line becomes a filename; the parse step never produces a validated path

```python
    for line in reversed(header.splitlines()):
        candidate = line.strip()
        if not candidate or candidate.startswith(FENCE):
            continue
        return candidate.lstrip("#").strip() or None
```

Measured:

```
"I will now fix the rounding in src/app.py:\n<<<<<<< SEARCH\n..."
  → edits[0].path == 'I will now fix the rounding in src/app.py:'   errors: ()
"### ../../../etc/passwd\n<<<<<<< SEARCH\n..."
  → edits[0].path == '../../../etc/passwd'                          errors: ()
```

This is the Boundary-integrity rule: foreign data crosses in through one parse step that converts it to typed domain values *or raises*. `Edit.path` is `str` and is whatever prose happened to sit above the marker. Containment is enforced later, at `patch_service._canonical` → `contained_path` (`patch_service.py:384-387`), so the traversal case is not exploitable — but that means the *only* validation lives one layer up, and the diagnostic the agent gets for a missing header is `no such file in this repository` naming a sentence, not "this block has no file header".

Recommendation: reject a header candidate that is not path-shaped before returning it — no interior whitespace runs plus a `/` or a known extension is a cheap and sufficient rule here — and report `block names no file` instead. Escalates from Low because the parse step is exactly the place this repo's own docstring (`patches.py:113-117`) claims malformed input is caught.

### B13-M3 — `patches.py:122-125, 192-195` — `ok` is vacuously true for a patch with no blocks at all

`ParseResult.ok` is `not self.errors`; a text with no markers yields `edits=(), errors=()` → `ok is True`. `ApplyResult.ok` is `all(outcome.applied for outcome in self.outcomes)` → `all(())` → `True` on zero outcomes.

Measured through the CLI, on a text that is a model refusal:

```
$ agentless-mcp patch check --repo <r> --file nope.txt        # "Sorry, I could not locate the bug."
# checked 0 of 0 edits across 0 files; 0 parse no worse than before
no files were edited
EXIT=0
```

Failure scenario: an orchestrating agent that gates on the exit code, or on `ok` in the JSON envelope, treats "the model produced no patch at all" as "the patch is clean". `validate_service.py:472` does guard this (`if not parsed.edits: return _apply_failed(...)`), which proves the case is real and that the guard belongs *in* the type rather than being re-derived per consumer.

Recommendation: add an explicit `ParseResult.empty` / `ApplyResult.empty` property, or make `ok` false for a zero-edit result and let a caller that genuinely wants "no edits is fine" say so. A boolean named `ok` that is true for the empty input is a default-allow.

### B13-M4 — `patches.py:226,259-267` — a stray marker string anywhere in the text fabricates a block error, and `validate` then rejects the whole candidate

`text.split(REPLACE_MARKER)` is global and unanchored. Measured:

```
"### a.py\n<<<<<<< SEARCH\nx\n=======\nX\n>>>>>>> REPLACE\nNow rerun the >>>>>>> REPLACE step.\n"
  → edits: [('a.py', 'x')]
  → errors: (BlockError(index=1, path='Now rerun the', reason='block has no <<<<<<< SEARCH marker'),)
```

and a replace side that legitimately contains a `=======` line (a reStructuredText underline, a resolved merge conflict) is refused with `block has 2 ======= dividers; expected one`.

Failure scenario: `validate_service.py:470-471` fails the entire candidate when `parsed.errors` is non-empty. So a correct, applicable patch is discarded because the model's prose after it echoed the format's own marker — a thing repair prompts actively encourage the model to talk about. The fabricated `path='Now rerun the'` in the error message makes the diagnosis worse, not better.

Recommendation: require the marker to be alone on its line (`^>>>>>>> REPLACE\s*$` / `^=======\s*$` over line-split text) rather than splitting on the bare substring. That also removes the "cannot patch a file containing an `=======` line" limitation for free.

### B13-M5 — `normalize.py:161-168` — `syntax_delta` compares error *counts*, so a patch can fix one parse error and introduce another and be judged clean

```python
    ok = new_errors <= old_errors
```

Measured: old = `def broken(:\n    pass\n\ndef fine():\n    return 1\n` (1 error), new = `def fixed():\n    pass\n\ndef fine(:\n    return 1\n` (1 error, in the other function):

```
{'old_errors': 1, 'new_errors': 1, 'ok': True,
 'detail': 'file already had 1 parse errors before the edit'}
```

Failure scenario: on a repository with any pre-existing parse error under the loaded grammar — which the module docstring (:33-38) says is the whole reason the check is a delta — a patch that repairs the old breakage while breaking a different function reports `ok`, and the detail string actively tells the reader the remaining error is pre-existing when it is not.

Recommendation: compare the *set* of error positions (byte offset plus node type), not the count, or at minimum compare counts *and* assert that no new error node starts outside the byte ranges the edit touched. The counting-only shape is defensible; the detail string asserting provenance it did not check is not.

### B13-M6 — `normalize.py:152-159, 137-139` — no grammar means `ok=True` and a fallback that normalises away semantic indentation

```python
    if parser is None:
        return SyntaxVerdict(..., ok=True, detail="no grammar for this file: syntax was not checked")
```
```python
    if parser is None:
        return " ".join(text.split())
```

Measured: `syntax_delta("valid", "!!!! not valid !!!!", "cobol")` → `ok=True`. And the equivalence fallback collapses all whitespace including newlines, so `"a:\n  b: 1\n"` and `"a:\nb: 1\n"` share a key — an indentation change that is semantic in YAML, and would be in any whitespace-significant language without a grammar in the pack.

Failure scenario: a repository whose patch targets are `.yaml`, `.tf`, `.cfg` or any language the pack does not carry gets a default-allow on both gates this module owns, with the truth confined to a `detail` string that `CheckReport.ok` (`patch_service.py:98`) never reads.

Recommendation: `ok` for the no-grammar case should be a third state, not `True` — add `checked: bool` to `SyntaxVerdict` and make consumers decide, rather than encoding "unknown" as "fine". For the stream fallback, join on `"\n"` per line with intra-line whitespace collapsed, preserving leading indentation, so indentation-only changes still move the key.

### B13-M7 — `patches.py:342, 356, 371-374, 417, 431-445, 489-534` plus `EditStatus.OUTSIDE_INTERVALS` at :145 — the entire `intervals` machinery has no production caller

`grep -rn "intervals" src/` shows every occurrence in `patch_service.py` is `intervals=intervals` threaded from a parameter that defaults to `None`; no CLI flag, no MCP tool argument, and no application-layer call site ever supplies one. `slices.py`/`view_service.py` intervals are a different concept and never reach `apply_edits`.

That is roughly 60 lines — `_initial_scopes`, `_line_spans`, `_within`, `_shift`, `scoped_paths`, the `OUTSIDE_INTERVALS` branch, an enum member that is part of the JSON contract — plus a whole test class (`TestIntervals`, 70 lines) held alive by tests alone. It also carries an undocumented `end == -1` sentinel at :520 that nothing produces, and silently clamps `start < 1` at :519 rather than refusing it.

Justify-its-existence test: deleting it makes the codebase smaller and removes a public enum member the write side must keep supporting. The argument for keeping it is "Agentless had `context_segment`" — that is provenance, not a caller.

Recommendation: either wire it to `resolve-locs` output (there is an obvious seam: `resolve_locations` already produces intervals per path) in the same change that keeps it, or delete it and the enum member. A dead parameter that a public status enum depends on is the expensive kind.

### B13-M8 — `normalize.py:12-13` — the docstring claims reformatting normalises away; three of the four things a formatter does move the key

> "Reformatting, re-commenting and re-indenting all normalise away"

Measured, python:

| change | key moves? |
| --- | --- |
| `x = 'a'` → `x = "a"` (black quote normalisation) | **yes** |
| `y = aaa + bbb` → parenthesised across lines | **yes** |
| `f(a, b)` → magic trailing comma across lines | **yes** |
| re-indentation, re-commenting | no (as claimed) |

Failure scenario: a comment that asserts an invariant the code does not hold is read literally by the next agent (Pass 1). Recommendation: correct the docstring to name what actually normalises (comments, whitespace, indentation) and what does not (quote style, line wrapping, trailing commas). Do not chase token-level format normalisation to make the claim true — that is a much larger commitment than this module should take on.

### B13-M9 — `normalize.py:142` — `INDENT_BLOCK_NODE_TYPES.get(language or "", ())` fails open for every indentation-sensitive language not in the table

```python
    blocks = frozenset(INDENT_BLOCK_NODE_TYPES.get(language or "", ()))
```

The table is `{"python": ("block",)}`. Any other whitespace-significant language in the pack (or added later) silently gets no block markers, and the dedent case the module was explicitly built to catch — documented at :26-31 and pinned only for python — returns "equivalent" for a real behaviour change. The `.get(..., ())` default means a typo in a language key, or a rename of the `"block"` node type in a grammar bump, degrades to silence rather than failing.

Failure scenario: the pack is pinned at `tree-sitter-language-pack==1.14.3` (`pyproject.toml:35`). A future bump that renames python's `block` node type turns `equivalence_key` back into the byte-identical-stream state the measurement note at `extractor.py:96-97` says was the bug, and no test outside `TestBlockStructure`'s python row would notice — that row would, so this is a maintenance hazard rather than a live defect, but the fail-open `.get` is what makes it silent.

Recommendation: assert at import or first use that each language named in `INDENT_BLOCK_NODE_TYPES` has its node types present in the loaded grammar, and raise rather than defaulting to `()` for a language that *is* in the table. Add a row for any other indentation-sensitive language the pack carries.

## Low

### B13-L1 — `patches.py:481-482` — unreachable defensive check
`_find_all`'s `if not needle: return` cannot fire: every caller passes `_pad(...)`, which is `"\n" + text + "\n"`, minimum length 2. It is also the only uncovered *logic* line in the file. Delete it, or move the guard to the one place an empty search can actually originate (see B13-L4).

### B13-L2 — `patches.py:527-534` — `_line_spans` counts a phantom trailing line
`"a\nb\n".split("\n")` is `["a", "b", ""]`, so a 2-line file reports 3 lines and an interval of `(3, 3)` is accepted as a real scope. Harmless today only because B13-M7 says nothing supplies intervals.

### B13-L3 — `normalize.py:207` — `errors="replace"` collapses distinct invalid byte sequences
`item.text.decode("utf-8", errors="replace")` maps every invalid byte to `U+FFFD`, so two different binary payloads in a source file hash identically. Vanishingly rare and cheap to leave; noting it because the module's whole job is "different content, different key".

### B13-L4 — `patches.py` (no guard) — an explicitly empty search matches blank lines
`Edit(search="")` produces `needle == "\n\n"`, which matches every blank line: measured `ambiguous (2 matches)` on `"a\n\nb\n"`, and it would **apply** on a file with exactly one blank line, inserting the replacement there. `patch_service.load_edits`'s docstring (:178-181) says a document missing `search` "must not read downstream as an empty search that matches the start of a file" — an explicitly-present `""` walks straight past that intent. Refuse `search == ""` in `apply_edits`.

### B13-L5 — `patches.py:314-316` — a trailing blank line on the replace side is silently dropped
`if lines and lines[-1] == "": lines = lines[:-1]` cannot distinguish "the newline before the closing marker" from "the author wanted a trailing blank line". Unfixable within the format; worth one sentence in the docstring, which currently explains the *other* half of the same decision (content sharing the closing-marker line) and not this one.

### B13-L6 — this block's tests never touch the JSON contract
`Edit.as_dict` (:82), `BlockError.as_dict` (:105), `ParseResult.as_dict` (:127), `EditOutcome.as_dict` (:168), `ApplyResult.as_dict` (:202), `ParseResult.ok` (:122), `ApplyResult.failures` (:198) and `EditStatus.__str__` (:149) are all uncovered by `test_patches.py`. `as_dict` is the wire format the CLI `--json` path and the MCP envelope emit; `test_patch_service.py:272` round-trips `ParseResult.as_dict()` through `load_edits`, which is real coverage but sits in another block and does not pin `EditOutcome`/`ApplyResult` at all. A key rename in `EditOutcome.as_dict` breaks every consumer and no test in this block fails.

## Cross-block observations

1. **`adapters/cli/main.py:1218-1221` (`_patch_call`) drops the invariant `ParseResult` exists to protect.** The module docstring at `patches.py:113-117` states it plainly: *"A parse that returns edits and drops the malformed blocks silently is the failure mode this type exists to prevent: a truncated patch would otherwise apply its first half and report success."* The CLI does exactly that — it prints each `BlockError` as a stderr note and returns `parsed.edits` regardless. Measured:
   ```
   $ agentless-mcp patch apply --repo <r> --file trunc.txt
   agentless-mcp: block 1 (app.py): block is not terminated by >>>>>>> REPLACE (truncated output?)
   # applied 1 of 1 edits to 1 files in a scratch worktree, against HEAD (1629648a)
   <diff of the first half>
   EXIT=0
   ```
   `validate_service.py:470-471` gets this right (`if parsed.errors: return _apply_failed(...)`); the CLI and `lint_service.py:129-141` (which downgrades unparsed blocks to a `NOT_CHECKED` finding) do not. One owner, three policies. Route this to whichever block owns `adapters/cli`.

2. **`patch_service._apply_at` (`patch_service.py:342-343`) writes `result.new_contents` unconditionally, before consulting `result.ok`.** `ApplyResult.new_contents`'s docstring (`patches.py:182-187`) invites this — "so a caller can write exactly those back" — and says nothing about partial application. Measured with two edits where the first applies and the second does not: the file is written, the diff is emitted, exit code is 1. In the scratch-worktree path that is harmless; with `--in-place` it leaves the caller's checkout half-patched on a failed run. Either the docstring should state that `new_contents` may be a partial application and must be gated on `ok`, or `apply_edits` should return `{}` when any edit failed.

3. **`validate_service.py:503`'s "did this patch change anything" guard keys on a proxy, not the invariant.** `key = normalized.key if normalized.result.new_contents else None` asks whether bytes changed; the invariant it wants is whether the *structure* changed. B13-H3 is the in-block half of this; the fix has to land in both places.

4. **The `COMMENT_NODE_TYPES` / `INDENT_BLOCK_NODE_TYPES` tables live in `core/extractor.py:84-100` and are consumed by `core/normalize.py`, `core/skeleton.py` and `core/patchlint.py:1050`.** B13-H2 and B13-M9 both argue those tables are load-bearing for a correctness verdict, not just for rendering. Whichever block owns `extractor.py` should be told that a change to those frozensets changes the equivalence key for every language, and that the only regression net today is `TestBlockStructure`'s three rows.

5. **Adversarial tests worth adding (Phase 4), all of which fail or mislead today:**
   - `test_an_elision_on_both_sides_is_refused` — `.../=======/...` must not report APPLIED (B13-H1).
   - `test_a_crlf_patch_parses_to_lf_search_text` — CRLF input must either match an LF file or be refused at parse (B13-M1).
   - `test_a_go_build_constraint_change_moves_the_key` — `//go:build linux` vs `windows` (B13-H2).
   - `test_a_comment_only_change_has_no_equivalence_class` — the empty-diff key must be distinguishable from a real class (B13-H3).
   - `test_a_marker_string_in_prose_does_not_fabricate_a_block` — valid patch + explanatory prose mentioning `>>>>>>> REPLACE` must parse with zero errors (B13-M4).
