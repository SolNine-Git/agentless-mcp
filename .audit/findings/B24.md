# Block B24 — Composition root

Dependencies: B01, B07, B17, B18, B19, B20, B21, B23 (+dynamic B22)
Upstream consumers: none — B24 is the composition root, the top of the dependency graph

Measured with `uv run --with pytest-cov pytest tests/unit/test_package.py --cov=agentless_mcp.bootstrap --cov-report=term-missing -q` and the same command over `tests/`. Both extras (`mcp`, `tokens`) are installed in this venv, so `fastmcp` and `tiktoken` are importable here.

What the missing 29% leaves unpinned, concretely:

- **`mcp_main` in its entirety (132-153)** — 22 of 56 statements. The second console script (`agentless-mcp-server`) is never executed by any of the 1141 passing tests, even though `fastmcp` is installed and the module would import cleanly. Neither the missing-extra message, the `ServerServices` construction, nor the `serve` call is covered.
- **`cli_main`'s failure path (112-114)** — the `AtlasError` -> stderr -> exit 2 handler. No test asserts the CLI prints an actionable message instead of a traceback when a counter cannot be built.
- **`TiktokenCounter`'s refusal branch (70-76)** — covered only on machines *without* the `tokens` extra (`tests/unit/test_token_counter.py:65` skips the whole class when it is installed). On this machine and on any dev/CI box that installs extras, the branch is dead.

## High

### B24-H1 — `mcp_main` misreports every server-module `ImportError` as "the mcp extra is not installed"

`src/agentless_mcp/bootstrap.py:132-140`

```python
    try:
        module = importlib.import_module(SERVER_MODULE)
    except ImportError as exc:
        sys.stderr.write(
            "agentless-mcp: the MCP server needs the 'mcp' extra, which is not installed "
            f"({exc}). Install it with: uv sync --extra mcp, or pip install "
            "'agentless-mcp[mcp]'.\n"
        )
        return 2
```

The guard keys on a proxy (*any* `ImportError` raised while loading a 684-line module that itself imports the whole application layer) rather than on the invariant it claims to protect (*`fastmcp`/`mcp`/`pydantic` are absent*). `adapters/mcp/server.py` imports fifteen first-party modules; every `ImportError` from any of them — a renamed export, a partially-installed `tree_sitter`, a circular import introduced later — is swallowed into a message that sends the operator to fix the wrong thing.

Verified empirically (probe that raises a first-party `ImportError` from `importlib.import_module` for `SERVER_MODULE`):

```
agentless-mcp: the MCP server needs the 'mcp' extra, which is not installed (cannot import name 'ViewService' from 'agentless_mcp.application.view_service'). Install it with: uv sync --extra mcp, or pip install 'agentless-mcp[mcp]'.
exit: 2
```

The chained exception text is interpolated, so the truth is present but framed as a parenthetical inside a false diagnosis; there is no traceback. Global invariant violated twice: *Guards key on the invariant, not a proxy* and *Errors surface* — a genuine wiring failure at startup is reported as an installation problem.

**Failure scenario.** A refactor renames a symbol in the application layer. `agentless-mcp-server` starts telling every user to install an extra they already have. The unit suite stays green (B24-H2), the CLI keeps working, and the misdiagnosis costs the operator the debugging session.

**Recommendation.** Key the guard on the actual optional dependency: probe with `importlib.util.find_spec("fastmcp")` (and `mcp`, `pydantic`) before importing, emit the install message only when a spec is genuinely missing, and let any other `ImportError` propagate with its traceback. Alternatively inspect `exc.name` and re-raise when it is not one of the extra's distributions.

### B24-H2 — the dynamic-import wiring in `mcp_main` is invisible to mypy *and* to the test suite

`src/agentless_mcp/bootstrap.py:144-153`

```python
    services = module.ServerServices(
        maps=MapService(extractor, counter),
        ...
    )
    serve = cast("Callable[[Sequence[str] | None, object], int]", module.serve)
    return serve(argv, services)
```

`importlib.import_module` returns `ModuleType`, whose attribute access is `Any`, so `module.ServerServices(...)` and `module.serve` are unchecked under `--strict`. Verified with a probe file type-checked by this repo's own mypy config:

```python
m = importlib.import_module("agentless_mcp.adapters.mcp.server")
s = m.ServerServices(bogus_field_that_does_not_exist=1)
r = m.no_such_function(1, 2, 3)
```
```
Success: no issues found in 1 source file
```

The `cast` compounds it: the second parameter is typed `object`, so even the hand-written contract declines to say it is a `ServerServices`. And lines 132-153 are executed by zero tests — the whole function is in the missing 29%.

**Failure scenario.** Someone adds a required field to `ServerServices` (e.g. `patches`, mirroring `CliServices`, when write tools are exposed over MCP), or changes `serve`'s signature. mypy passes, import-linter passes, 1141 tests pass, and `agentless-mcp-server` dies at startup with `TypeError: ServerServices.__init__() missing 1 required keyword-only argument`. This is exactly the class of bug a composition root exists to concentrate and exactly the one nothing here catches.

**Recommendation.** Add one test that actually invokes `mcp_main` with `serve` patched to a no-op recorder (`monkeypatch.setattr(server_module, "serve", recorder)`), asserting it returns the recorder's code and that the recorded services object has the fields the server expects. That single test pins the constructor arity, the keyword names, and the `serve` call shape. Separately, import `ServerServices`/`serve` under `if TYPE_CHECKING:` (import-linter is configured with `exclude_type_checking_imports = true`, so this costs nothing at the contract level) and annotate the locals so mypy checks the construction statically.

### B24-H3 — the optional-extra contract is enforced by a substring search that misses the likely breakage

`tests/unit/test_package.py:36-39`

```python
    source = Path(bootstrap.__file__).read_text(encoding="utf-8")
    assert "import fastmcp" not in source
    assert "from fastmcp" not in source
    assert bootstrap.SERVER_MODULE == "agentless_mcp.adapters.mcp.server"
```

The invariant is *"importing `agentless_mcp.bootstrap` must not import `fastmcp`"*. The test asserts a proxy: that two literal strings do not appear in one file. `from agentless_mcp.adapters.mcp.server import ServerServices` — the single most likely way a future edit breaks this, since it is the obvious fix for B24-H2 if done carelessly — contains neither string and would sail through.

Nothing else covers it. The import-linter layers contract lists `adapters, application, core, prompts, util` with `containers = ["agentless_mcp"]`; `bootstrap` is deliberately outside the layer list (pyproject.toml:250-253), so no layer rule constrains its imports. The independence contract names `agentless_mcp.adapters.cli` and `agentless_mcp.adapters.mcp` — not `bootstrap`. There is no `.github/workflows` directory, so there is no CLI-only-install smoke test either.

**Failure scenario.** A contributor imports the server module at bootstrap scope. Every gate stays green. `pip install agentless-mcp` (no extras) plus `agentless-mcp map` then fails with `ModuleNotFoundError: No module named 'fastmcp'` for every CLI-only user of the published package — the exact failure the module docstring (lines 12-16) says is designed out.

**Recommendation.** Assert the behavior, not the text: run `python -c "import agentless_mcp.bootstrap, sys; sys.exit('fastmcp' in sys.modules or 'agentless_mcp.adapters.mcp' in sys.modules)"` in a `subprocess` from the test (a fresh interpreter is required — the in-process `sys.modules` is polluted by other tests). Confirmed to hold today:

```
$ python -c "import sys, agentless_mcp.bootstrap; print('fastmcp loaded:', 'fastmcp' in sys.modules)"
fastmcp loaded: False
```

Keep the `SERVER_MODULE` string assertion; drop the two substring assertions once the subprocess check exists.

## Medium

### B24-M1 — `TiktokenCounter.__init__` makes an untimed network call at process startup, outside the error guard

`src/agentless_mcp/bootstrap.py:67-77`

```python
        except ImportError as exc:
            ...
            raise AtlasError(message) from exc
        self._encoding = tiktoken.get_encoding(encoding_name)
```

Only the *import* is guarded. `get_encoding("cl100k_base")` on a cold cache downloads the BPE file; the installed tiktoken does it with no timeout (`.venv/.../tiktoken/load.py:17`):

```python
        resp = requests.get(blobpath)
        resp.raise_for_status()
```

So `agentless-mcp --token-counter tiktoken map` on a first run behind a blackholing network hangs indefinitely before printing anything, and on a refused connection raises `requests.exceptions.ConnectionError` — not an `AtlasError`, so `cli_main`'s `except AtlasError` at line 112 does not catch it and the user gets a raw traceback from the composition root. Violates *External calls fail, hang, or duplicate: every network or out-of-process call gets a timeout*, and the docstring's claim that the missing-extra case "produces an actionable message instead of a traceback" (lines 15-16) does not extend to the adjacent, more likely failure.

**Recommendation.** Wrap the `get_encoding` call in the same `try` and convert any exception into an `AtlasError` naming the encoding and pointing at `TIKTOKEN_CACHE_DIR` for offline pre-seeding. A timeout cannot be injected into tiktoken's `requests.get`, which is itself an argument for surfacing the failure clearly rather than pretending it is instantaneous.

### B24-M2 — the MCP entry point drags in the entire 1424-line CLI adapter

`src/agentless_mcp/bootstrap.py:32`

```python
from agentless_mcp.adapters.cli.main import CliServices, counter_parser, run
```

Module scope, so `agentless-mcp-server` — which uses none of these three names — imports `adapters/cli/main.py` (1424 lines, the full argparse subcommand tree) plus `PatchService`, `ValidateService` and `LintService`, none of which appear in `ServerServices`. Importing `agentless_mcp.bootstrap` pulls 47 first-party modules, `agentless_mcp.adapters.cli.main` among them.

The repo's stated decision (pyproject.toml, independence contract) is that "either [adapter] importing the other would make the CLI drag in fastmcp ... or the server inherit argparse exit-code semantics." The composition root holds one half of that symmetry with real machinery (the dynamic import) and breaks the other half by accident. Import-linter cannot see it because `bootstrap` is outside the layer list.

**Failure scenario.** A module-level error or slow import in the CLI adapter (a bad default, a heavy import) takes down the stdio server, which never uses that code. Diagnosis starts in the wrong adapter.

**Recommendation.** Split the composition root into two — `bootstrap.cli_main` importing only the CLI adapter, `bootstrap.mcp_main` importing only the server module — with the shared four-service construction in a small private helper that imports neither adapter. That also removes the need for the dynamic import to double as optional-dependency gating for the CLI's benefit.

### B24-M3 — an unknown token-counter name silently becomes the default

`src/agentless_mcp/bootstrap.py:90-92`

```python
    if choice == COUNTER_TIKTOKEN:
        return TiktokenCounter()
    return Chars4Counter()
```

`select_counter("tiktokn")` returns the chars/4 estimator without a word. The module docstring is emphatic that the counter choice moves every token budget in the package ("a counter that changed underneath them would move budgets nobody asked to move", lines 22-24) — which is an argument for failing on an unrecognized name, not for coalescing it to a default. The behavior is pinned by a test that acknowledges the gap in its own comment (`tests/unit/test_token_counter.py:40-43`: *"argparse rejects an unknown value before this is reached; the fallback exists so a library caller cannot end up with None"*) — the stated goal (never `None`) is achievable by raising.

argparse's `choices=TOKEN_COUNTERS` does guard the CLI path, so this is a library-caller-only exposure, hence Medium rather than High. But `select_counter` is public API on the composition root and B24-M2's split would give it more callers, not fewer.

**Recommendation.** `if choice in (None, COUNTER_CHARS4): return Chars4Counter()` then `if choice == COUNTER_TIKTOKEN: ...` then `raise AtlasError(f"unknown token counter {choice!r}; choose from {TOKEN_COUNTERS}")`. Update the test to assert the refusal.

### B24-M4 — the missing-extra refusal is tested only on machines that lack the extra

`tests/unit/test_token_counter.py:65-69`

```python
@pytest.mark.skipif(TIKTOKEN_INSTALLED, reason="the tokens extra is installed")
class TestWithoutTheExtra:
    def test_asking_for_tiktoken_refuses_with_the_install_command(self):
        with pytest.raises(AtlasError, match="tokens' extra"):
            bootstrap.select_counter(COUNTER_TIKTOKEN)
```

`TIKTOKEN_INSTALLED` is read from the ambient environment (`importlib.util.find_spec`), so which assertions run depends on how the venv was synced. In this repo's venv tiktoken *is* installed, so bootstrap.py:70-76 — the actionable-message branch, the whole point of the design — is never executed by any test run here. The corresponding branch for the `mcp` extra (B24-H1) has no test in either direction. Violates *hermetic tests: no dependence on ambient env vars* in spirit — a suite whose coverage of an error path flips based on what happens to be installed.

**Recommendation.** Make it environment-independent: `monkeypatch.setattr(bootstrap.importlib, "import_module", raiser)` where `raiser` raises `ImportError("No module named 'tiktoken'")`, and assert the `AtlasError` text. The same pattern gives B24-H1 a test. Keep the skipif classes only for the assertions that genuinely need the real library (`count() > 0`).

## Low

### B24-L1 — `cli_main`/`mcp_main` re-implement `fail()` and hardcode the exit code

`src/agentless_mcp/bootstrap.py:113-114` and `135-140`

```python
        sys.stderr.write(f"agentless-mcp: {error}\n")
        return 2
```

`adapters/cli/formatting.py:51-54` is the same three lines with the same prefix (`fail(message, code)`), and `EXIT_USAGE = 2` is a named constant there whose meaning is documented in that module's docstring ("usage or security ... the request itself was not admissible"). The composition root duplicates the format string and the literal. Two homes for one convention drift silently — and a missing optional extra is arguably an environment failure rather than a usage error, so the choice of 2 deserves to be stated rather than typed.

**Recommendation.** For `cli_main`, `return fail(str(error), EXIT_USAGE)`. For `mcp_main`, leave the write inline (importing the CLI adapter's formatting into the server path would deepen B24-M2) but use a module-level constant with a comment on why the code is 2.

### B24-L2 — `encoding_name` is a parameter no caller ever passes

`src/agentless_mcp/bootstrap.py:54, 67`

```python
TIKTOKEN_ENCODING = "cl100k_base"
...
    def __init__(self, encoding_name: str = TIKTOKEN_ENCODING) -> None:
```

The only construction in the repo is `TiktokenCounter()` (line 91); no test passes an encoding either. Configuration with one real setting, and the accompanying six-line comment (lines 50-53) argues *against* making the encoding vary. The constant earns its place as documentation of the fixed choice; the parameter does not.

**Recommendation.** Drop the parameter and read `TIKTOKEN_ENCODING` directly, or keep it and give `select_counter` a way to pass it. Not both.

### B24-L3 — the pre-parse rejects a bad `--token-counter` value with a stripped-down usage line, from a function typed `-> int`

`src/agentless_mcp/bootstrap.py:103, 107`

`counter_choice` runs `counter_parser().parse_known_args(argv)` on a parser built with `add_help=False` and no subcommands. A typo'd value exits there:

```
$ agentless-mcp --token-counter bogus map
usage: agentless-mcp [--token-counter {chars4,tiktoken}]
agentless-mcp: error: argument --token-counter: invalid choice: 'bogus' (choose from chars4, tiktoken)
```

The user sees a usage line advertising one flag and no subcommands, rather than the full parser's. It also means `cli_main`, annotated `-> int`, can terminate the process via `SystemExit` instead of returning — fine under the console script and `__main__.py:6`, surprising for a library caller or an in-process test.

**Recommendation.** Low-cost fix: give `counter_parser()` `prog="agentless-mcp"` and `usage=argparse.SUPPRESS` for the pre-parse instance, or scan argv for the flag without argparse and leave all diagnostics to the full parser. Either way the full parser re-validates the value, so nothing is lost.

### B24-L4 — `mcp_main` hardcodes the chars/4 counter with no flag and no comment

`src/agentless_mcp/bootstrap.py:143`

```python
    counter = Chars4Counter()
```

`cli_main` selects a counter; `mcp_main` does not, and `adapters/mcp/server.py:663-676` declares only `--root`, so the `tokens` extra is unreachable from the server. That may well be the intended decision (the MCP tools' budgets are pinned the same way the CLI's are), but the module docstring describes the opt-in as "the extra has to be installed *and* `--token-counter tiktoken` passed" without noting that one of the two front doors has no such switch. The next reader cannot tell an intentional restriction from an oversight.

**Recommendation.** One comment line at 143 stating that the server budget is deliberately fixed to the pinned estimator, or wire the same `counter_choice` pre-parse into `mcp_main` and add the flag to the server parser. Silence is the only bad option.

## Cross-block observations

- **The layer contract has a hole exactly where the composition root sits.** `bootstrap` and `__main__` are outside the import-linter layer list by explicit decision (pyproject.toml:250-253), and the independence contract names only `adapters.cli` / `adapters.mcp`. Nothing constrains what `bootstrap` imports, so both B24-H3 (a static `fastmcp` import through the server module) and B24-M2 (the server entry point importing the whole CLI adapter) are invisible to the dependency gate. Phase-6 candidate: add a `forbidden` contract — `agentless_mcp.bootstrap` must not import `agentless_mcp.adapters.mcp` — which is enforceable today and would replace the substring test.
- **Dynamic imports are a repo-wide static-analysis blind spot, not a bootstrap-local one.** deptry already carries a permanent `DEP002` exemption for `tiktoken` because it cannot see the dynamic import (pyproject.toml:290-296), and mypy is proven blind to the `module.ServerServices(...)` construction. Any other block reached only through `importlib` deserves the same "is there a test, since there is no type check?" question.
- **No CI.** There is no `.github/workflows` directory; the gates are pre-commit hooks run locally (`ruff`, `mypy`, `lint-imports`, `deptry` on commit; repo-wide ruff and pytest on push). Every "this is enforced" claim in this audit resolves to "enforced if the contributor has the hooks installed." Worth a single cross-block note in the final report rather than a per-block finding.
- **Environment-conditional test classes appear here and may appear elsewhere.** `tests/unit/test_token_counter.py` gates on `find_spec("tiktoken")`; 4 tests skip in the full run. Any other `skipif` keyed on an installed optional package hides an error path from coverage on the machines most likely to run the suite.
