## Critical

### B07-C1 — Recursive tree walks blow the stack on ordinary generated code and abort the whole repository index
`src/agentless_mcp/core/extractor.py:782-854`, `:957-980`, `:1337-1362`, `:1379-1398`; caller `src/agentless_mcp/core/cache.py:657-663`

The module opens by claiming the traversal is stack-safe:

```python
def walk_nodes(root: Node) -> list[Node]:
    """Return every node in the tree, parents before children.

    Iterative rather than recursive: a deeply nested expression in a generated
    file must not turn a repository map into a RecursionError.
    """
```
(`extractor.py:481-486`)

`walk_nodes` and `collect_refs` honour that. Four other walkers in the same file do not: `_visit_generic_children` / `_visit_generic_node` are mutually recursive over the entire tree (`:790-791`, `:854`), and `_collect_import_nodes` (`:979-980`), `_walk_require` (`:1361-1362`) and `_walk_bash_source` (`:1397-1398`) each recurse per child unconditionally.

Measured thresholds (binary search, default `sys.setrecursionlimit` of 1000):

| input | first failing size |
| --- | --- |
| JS `a.m0().m1()…` chained calls | **248 calls** |
| JS `"p0" + "p1" + …` concat chain | **496 terms** |

Both shapes are routine in minified bundles, generated clients, and hand-written SQL/CSS builders — this is not an adversarial-only bound. All three public entry points fail: `extract_from_source`, `extract_imports_from_source` (js/ts/tsx/go/java/php/kotlin/swift) and the lua/ruby `require` walk. Only `extract_refs_from_source` survives, because it is the one that uses `walk_nodes`.

The failure is not contained. The index scan catches exactly one error class:

```python
        try:
            symbols = extractor.extract_from_source(read.text, language, repo_file.path)
            imports = extractor.extract_imports_from_source(read.text, language, repo_file.path)
            refs = extractor.extract_refs_from_source(read.text, language, repo_file.path)
        except LanguageUnavailable as exc:
```
(`cache.py:657-661`)

`RecursionError` propagates out of `_plan_index`, so **one qualifying file anywhere in the tree makes `agentless index` — and therefore every read tool — fail for the entire repository**, with a Python traceback rather than an `IndexFailure` row. `core.patchlint.py:178-188` already enumerates `RecursionError` in its `DEGRADED_ERRORS` tuple, so the repo knows this class is reachable on the parse path; the scan loop was never given the same treatment.

Failure scenario: a user runs `agentless index` on any JS/TS repo containing one webpack bundle or one generated API client. The tool crashes and stays crashed until they find and exclude the file by hand.

Recommendation: convert the four recursive walkers to the explicit-stack form `walk_nodes` already uses — `_visit_generic_node`'s "descend unless matched" rule is expressible with a `(node, parent)` stack. Independently, widen the `except` in `cache._plan_index` to a named tuple including `RecursionError` so one pathological file degrades to an `IndexFailure` instead of killing the scan, and add a regression test asserting a 600-term chain indexes without raising.

### B07-H1 — Go type declarations extract nothing; the dead config is frozen into a golden and pinned by a test
`src/agentless_mcp/core/extractor.py:225-238`, `:932-942`

```python
    "go": LanguageConfig(
        function_node_types=("function_declaration", "method_declaration"),
        class_node_types=("type_declaration",),
```

`_generic_name` resolves the field `name` on the matched node, then falls back to `cfg.name_node_types` (`identifier`, `type_identifier`, `property_identifier`, `word`). A Go `type_declaration` has neither: its children are the `type` keyword and one or more `type_spec` nodes, and the name lives one level down inside the `type_spec`. `_generic_name` returns `""`, the `if name:` guard at `:829` drops the symbol, and no recursion happens either — `class_node_types` is dead configuration.

Measured:

```
type Config struct { A int }
type Handler interface { Do() }
func (c *Config) Validate() error { return nil }
  -> [(method, 'Validate', parent='Config')]      # the two types are absent
```

The checked-in golden confirms this is the shipped behavior, not a probe artifact. `tests/characterization/fixtures/repo_go/` declares `Tier`, `PriceBook`, `Item`, `Inventory` and `ReportError`; `tests/characterization/goldens/map/repo_go.map.json` contains **zero** type stable ids — only `go:pricing.go::PriceBook.CostOf`, `go:inventory.go::Inventory.Add` and friends.

Worse, a unit test now enforces the defect:

```python
    def test_a_plain_function_keeps_no_owner(self, extractor):
        symbols = extractor.extract_from_source(GO_RECEIVERS, "go", "config/config.go")
        plain = [symbol for symbol in symbols if not symbol.parent_class]
        assert [symbol.name for symbol in plain] == ["Validate"]
```
(`tests/unit/test_stable_ids.py:117-120`, over a fixture that declares `ServerInfo` and `AWSConf` structs)

Fixing the extractor makes this test red. It is a bug-pinning test.

Failure scenario: `find_symbol("Inventory")` or `get_symbols_overview` on any Go repository reports no types at all. For a tool sold as structural navigation, half the Go type system is invisible and the golden says that is correct.

Recommendation: in `_generic_name`, when the matched node yields no name, descend one level into a configured wrapper node type (add e.g. `name_wrapper_node_types=("type_spec",)` to `LanguageConfig`) — or give Go a dedicated handler that iterates `type_spec` children so a grouped `type ( A …; B … )` block yields both. Then update the golden and rewrite `test_a_plain_function_keeps_no_owner` to assert the owner of `Validate`, not the total symbol set.

### B07-H2 — Python PEP-695 `type X = …` aliases extract nothing: the handler reads a field the grammar does not name
`src/agentless_mcp/core/extractor.py:1621-1644`

```python
    def _extract_type_alias(self, node: Node, source: bytes, module_path: str) -> ASTSymbol | None:
        """Extract a type alias (Python 3.12+ 'type X = ...')."""
        name_node = node.child_by_field_name("name")
        if name_node is None:
            return None
```

The grammar shipped by tree-sitter-language-pack 1.14.3 names that field `left`, not `name`:

```
node: type_alias_statement fields: [(None,'type'), ('left','type'), (None,'='), ('right','type')]
by_field name -> None
by_field left -> (type (identifier))
```

So `type Alias = int` produces `[]`. Both the dispatch arm (`:1421-1424`) and the handler body (`:1623-1630`) are uncovered by the entire 1141-test suite, which is why the wrong field name survived — this is the classic hallucinated-API shape, and the neighbouring Rust handler (`_extract_rust_type_alias`, `:1826`) uses `"name"` correctly for `type_item`, which makes the Python copy look plausible on review.

Failure scenario: a modern Python codebase using PEP 695 aliases has them silently missing from every map, overview and symbol lookup. Nothing reports a gap.

Recommendation: read `left` (keeping `name` as a fallback if the pack revision is expected to vary), and add a test asserting `type Alias = int` yields one `SymbolKind.TYPE_ALIAS` symbol named `Alias`.

### B07-H3 — `is_async` is decided by a substring scan of the first 10 bytes and false-positives on any name containing "async"
`src/agentless_mcp/core/extractor.py:1475-1485`

```python
        is_async = False
        if node.parent and node.parent.type == "decorated_definition":
            is_async = any(c.type == "async" for c in node.parent.children)
        if not is_async:
            end = min(node.start_byte + 10, node.end_byte)
            prefix_text = source[node.start_byte : end].decode("utf-8", errors="replace")
            if "async" in prefix_text:
                is_async = True
```

Measured:

```
def async_run():        -> is_async=True,  signature "async def async_run()"
def asyncio_helper():   -> is_async=True,  signature "async def asyncio_helper()"
def normal():           -> is_async=False
```

Both branches are also wrong about where the marker lives. The grammar puts `async` as a direct child of `function_definition` in *both* the plain and the decorated case:

```
function_definition ['async', 'def', 'identifier', 'parameters', ':', 'block']
decorated_definition ['decorator', 'function_definition']
  inner fn children: ['async', 'def', 'identifier', 'parameters', ':', 'block']
```

So the decorated-parent lookup at `:1476-1477` can never fire (line 1477 is uncovered by the full suite, confirming it), and the byte-prefix heuristic exists only to compensate for looking in the wrong place. The correct one-liner is already written twelve hundred lines away in the same file — `_extract_rust_function` uses `is_async = any(c.type == "async" for c in node.children)` (`:1708`). Two homes for one rule, and the Python home has the wrong answer.

Failure scenario: `ASTSymbol.is_async` and the rendered signature are wrong for any function whose name starts within 10 bytes with a token containing `async` — `async_run`, `asyncio_setup`, `async_client`. Consumers that filter or render on `is_async` (map output, skeletons) report a synchronous function as `async def`, which reads as fact to the next agent.

Recommendation: replace lines 1475-1483 with `is_async = any(c.type == "async" for c in node.children)`, matching the Rust handler. Add a test with `def async_run()` asserting `is_async is False`.

### B07-H5 — Parse failure is indistinguishable from an empty file; malformed symbols ship with no signal
`src/agentless_mcp/core/extractor.py:687-693`, `:731-737`

```python
        tree = parser.parse(bytes(source, "utf-8"))
        source_bytes = bytes(source, "utf-8")

        # get_parser succeeded, so the language is registered.
        symbols: list[ASTSymbol] = []
        self._registry[language].extract_symbols(tree.root_node, source_bytes, module_path, symbols)
        return disambiguate(symbols)
```

`tree.root_node.has_error` is never consulted anywhere on the extraction path — `grep -rn "has_error" src/` hits only `core/normalize.py:231`, which uses it for patch validation. Measured on a truncated Go file:

```
package main

func Broken( { {
  -> [ASTSymbol(name='Broken', kind=FUNCTION, signature='fn Broken(', ...)]
  root_node.has_error = True
```

A symbol with the signature `fn Broken(` is emitted as though it were a fact. The `IndexFailure` channel that `cache._plan_index` maintains for unreadable files and unavailable grammars gets nothing, so the map presents a half-parsed file exactly like a clean one. This is the global **Errors surface** invariant failing: the error is neither handled meaningfully nor propagated, it is discarded.

Contrast with `test_syntax_error_tolerance` (`tests/unit/test_extractor.py:183-188`), which asserts only `isinstance(symbols, list)` — a tautology that passes whatever the extractor does with a broken file.

Failure scenario: a file mid-edit, a template with `{{ }}` placeholders, or a language variant the grammar does not accept produces plausible-looking garbage symbols and a silently incomplete map. An agent localizing a bug is told the file contains one function called `Broken`.

Recommendation: return the parse health alongside the symbols (or expose `tree.root_node.has_error` via a small result type) and have `cache._plan_index` record an `IndexFailure`/degradation row for files that parsed with errors, so "partially parsed" is visible in `index` output rather than inferred.

### B07-H6 — C/C++ extraction sees only root-level declarations: every method and everything inside a namespace is invisible
`src/agentless_mcp/core/extractor.py:1210-1260`

```python
        for node in root.children:
            if node.type == "function_definition":
                ...
            elif node.type in ("struct_specifier", "class_specifier", "enum_specifier"):
```

The loop never descends. Measured:

```cpp
namespace ns {
class Foo { public: void bar() {} };
int free_fn() { return 1; }
}
int top() { return 0; }
  -> [(function, 'top')]
```

`ns`, `Foo`, `Foo::bar` and `ns::free_fn` are all dropped. For C++ specifically this removes essentially the whole symbol surface of any file that uses a namespace, which is nearly all of them. Recommendation: give `_extract_c_symbols` the same descend-through-non-declarations walk the generic handler uses (iteratively — see B07-C1), tracking `namespace_definition` / `class_specifier` as the parent so methods carry an owner. Add the `repo_c` fixture from B07-H4 covering a namespaced class.

### B07-M3 — `_locally_bound` is quadratic in file size
`src/agentless_mcp/core/extractor.py:431-435`, called per-ref at `:475`

```python
def _locally_bound(scopes: Sequence[_BindingScope], name: str, line: int) -> bool:
    return any(
        scope.start_line <= line <= scope.end_line and name in scope.names for scope in scopes
    )
```

Every identifier occurrence scans every binding scope in the file. Measured on synthetic Python:

| functions | refs | `collect_refs` |
| --- | --- | --- |
| 200 | 1200 | 7.5 ms |
| 400 | 2400 | 23.3 ms |
| 800 | 4800 | 74.3 ms |

Doubling the input roughly triples the time — ~O(n²). Extrapolated, a 5000-function generated Python module costs seconds in the reference pass alone, per index, and the reference pass runs on every file of every scan.

Recommendation: build a line-indexed structure once per file (sort scopes by `start_line` and binary-search, or maintain a stack during a single ordered walk since scopes nest), turning the per-ref cost into O(log n) or O(1).

### B07-M6 — God-module seam: node-type vocabulary and the Python-only binding analysis live inside an ostensibly language-generic extractor
`src/agentless_mcp/core/extractor.py:84-117` (tables), `:357-435` (Python scope analysis)

### B07-M8 — `collect_refs` bypasses the registry, defeating the module's single-dispatch claim
`src/agentless_mcp/core/extractor.py:438-461`

The module header promises one dispatch point:

```
Language support is registry-driven: every language is wired in one place --
the registry built by `_build_registry` -- which pairs the grammar name with
the symbol- and import-extraction handlers for that language.  A single
dispatch consults it, so adding a language is a one-entry change
```

and `_build_registry`'s docstring repeats it: "This is the single place a language is dispatched -- the two public extraction methods and the parser lookup all read from it, so a language cannot be handled by one chain and missed by another."

`collect_refs` reads neither. It resolves node types from a *second* table union (`LANGUAGE_CONFIGS` ∪ `_EXTRA_IDENTIFIER_NODE_TYPES`, `:438-443`) and gets its parser with `grammars.get_parser(language)` (`:458`) rather than `self._grammar_of(language)`. Today `grammar == language` for all fifteen registry entries and the table union exactly covers the registry (verified: both set differences are empty), so nothing is broken — but `_grammar_of` exists precisely because those names are allowed to diverge, and `identifier_node_types` falls back to `DEFAULT_IDENTIFIER_NODE_TYPES` for an unknown language rather than raising, so a language added to the registry with a different grammar name would extract symbols correctly and collect references from the wrong grammar, or none. `core/skeleton.py:100` and `core/normalize.py:184` call `grammars.get_parser(language)` the same way.

Recommendation: have `collect_refs` take the grammar name from the registry (or move `identifier_node_types` into `_LanguageSpec` as a third field so the three tables cannot drift), and add a test asserting `set(_registry) == set(LANGUAGE_CONFIGS) | set(_EXTRA_IDENTIFIER_NODE_TYPES)` so a new language cannot be half-wired.

### B07-L1 — `_truncate` and its two constants duplicate `normalise_signature`, and one of them can never manifest
`src/agentless_mcp/core/extractor.py:46-47`, `:120-124`; against `core/symbols.py:45`, `:147-156`

`ASTSymbol.__post_init__` already runs every signature through `normalise_signature`, which caps at `SIGNATURE_MAX_CHARS = 80` with the identical `flattened[: N - 3] + "..."` idiom. `_MAX_VALUE_CHARS = 80` therefore only pre-trims a value that is about to be capped at 80 anyway, and `_MAX_TYPE_ALIAS_CHARS = 120` is unreachable in effect — a 120-char alias signature is cut to 80 downstream regardless. ## Cross-block observations

- **B06 (grammar loading) carries a claim B07's coverage refutes.** `core/grammars.py:38-40` asserts every tier-1 language has "characterization coverage"; `c`, `cpp` and `rust` have no fixture and no executed handler line in the entire suite (B07-H4). The tier split is load-bearing — it is what lets a broken tier-2 grammar degrade without failing tier-1 warmup — so the claim should be gated by a test that asserts a fixture exists per tier-1 language, or the tier membership corrected.

- **`cache._plan_index` narrows its `except` too far, and B07 is not the only supplier.** `core/cache.py:657-661` catches only `LanguageUnavailable`, while `core/patchlint.py:178-188` has already enumerated the realistic parse-path failure set (`AtlasError, ValueError, TypeError, KeyError, IndexError, AttributeError, UnicodeDecodeError, RecursionError, OSError`) with an explicit rationale for naming them rather than catching `Exception`. Whoever owns the cache block should adopt that same tuple; without it any per-file defect in B07 is a whole-repository outage (B07-C1).

- **Node-type vocabulary is shared state with three owners.** `core/normalize.py` and `core/skeleton.py` import `COMMENT_NODE_TYPES`, `INDENT_BLOCK_NODE_TYPES`, `BODY_BLOCK_NODE_TYPES` and `LANGUAGE_CONFIGS` from `core/extractor.py`. Any block-level recommendation to split the extractor must move those tables to a neutral module first (B07-M6), or the split will break two other blocks. This is the single highest-value mechanical refactor in the repo's dependency graph: it is the reason `extractor` has Ca=14.

- **Goldens are pinning at least one defect, and possibly more.** `tests/characterization/goldens/map/repo_go.map.json` records the absence of every Go type (B07-H1), and `tests/unit/test_stable_ids.py:117-120` asserts it. Any block reviewing the characterization suite should treat "the golden matches" as evidence of stability, not of correctness — the goldens were generated from the implementation, so they encode its blind spots. Recommend a one-time audit of each golden against a hand-written expectation of what the fixture declares.

- **Recursion-depth discipline is inconsistent across the core layer.** `core/resolve.py:733` documents an explicit iterative choice for the same reason `extractor.walk_nodes` does, and `core/patchlint.py` guards for `RecursionError` — but four walkers in `extractor.py` recurse anyway. Worth a repo-wide sweep for tree/graph walks that recurse per child, since the pattern is clearly known and unevenly applied.
