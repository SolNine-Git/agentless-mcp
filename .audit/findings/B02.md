### B02-M1 — `cache_stale_remediation` gives CLI-only remediation on the MCP surface
`src/agentless_mcp/prompts/messages.json:14`

```json
"cache_stale_remediation": "rerun agentless-mcp index or pass --no-cache",
```

`--no-cache` is an `argparse` flag that exists only on the CLI adapter (`src/agentless_mcp/adapters/cli/main.py:201`). Over MCP the equivalent is a tool argument, `no_cache: bool = False` (`src/agentless_mcp/adapters/mcp/server.py:495, 545, 559, ...`). This string is not CLI-only in practice: `core/cache.py:110` aliases it as `REMEDIATION` and `cache.py:142` renders it into `CacheStatus.receipt`, which `application/envelope.py:78` interpolates into `ENVELOPE.receipt_line` on **every** MCP answer whenever the index is stale.

Failure scenario: an agent whose cache has gone stale reads "pass --no-cache" in the receipt of every response, attempts `--no-cache` as a tool argument, and gets a schema rejection; the correct action (`no_cache=true`) is never named. The other half of the advice, "rerun agentless-mcp index", is a shell command an MCP client generally cannot issue either — note that `cache_build_hint` (line 15) has the same shape but at least gives the exact command with `--repo {repo_root}`.

Recommendation: the remediation is surface-specific, so either split it into two keys (`cache_stale_remediation_cli` / `cache_stale_remediation_mcp`) selected by the adapter, or reword to name both spellings ("rerun `agentless-mcp index`, or set no_cache (CLI: `--no-cache`)"). Arguable up to High because it is on the primary surface at high frequency; filed Medium per the lower-severity-when-arguable rule, since the cost is a wasted turn rather than a wrong answer.

### B02-M2 — The package docstring states a guarantee no gate enforces, and the codebase already violates it
`src/agentless_mcp/prompts/__init__.py:1`

```python
"""Every string this package shows an agent, held as data.
```

That is the stated invariant of the whole block, and it is false. Agent-facing strings live outside the catalog in at least five places:

- `src/agentless_mcp/application/symbol_service.py:214` — `unresolved.append((raw, f"not expanded: the per-call limit is {limit} symbols"))`
- `src/agentless_mcp/application/symbol_service.py:386` — `blocks.extend(f"unresolved: {entry} -- {reason}" ...)`
- `src/agentless_mcp/application/render.py:709` — `return "no import cycles\n"`
- `src/agentless_mcp/application/render.py:588` — `return "no communities: nothing in this repository parsed into files\n"`
- `src/agentless_mcp/core/cache.py:107-108,142` — `RECEIPT_NONE = "none"`, `RECEIPT_BYPASSED = "bypassed (--no-cache)"`, and `f"g:{self.generation} stale (repo g:{self.repo_generation}) - {REMEDIATION}"`

The first of these is the sharpest: `symbol_service.py:214` writes a refusal by hand while the sibling refusal three lines later (`:217`) reads from `MESSAGES.expand_no_room`. Two policies in one function.

Failure scenario: the docstring's promise is exactly the thing a maintainer relies on when told "revise the wording without editing Python". They edit the JSON, ship, and half the strings an agent sees are unchanged. Per the global rule, a stated guarantee has to name the gate that enforces it; there is none here (no lint rule, no test enumerating string literals in `application/`/`core/`).

Recommendation: either narrow the docstring to what is true ("the tool descriptions, envelope wording and refusal texts") or move the outliers into `messages.json` and add a gate. The docstring is the cheaper fix and should not wait on the second.

### B02-M3 — `analyze_structure`'s description enumerates each operation's arguments and gets two of them wrong
`src/agentless_mcp/prompts/tool_descriptions.json:10`

> "operation='cycles' takes nothing and returns every module-level import cycle …"
> "operation='communities' takes an optional resolution (lower groups more coarsely) …"

Both accept `limit`, and `limit` is what bounds the answer:

- `src/agentless_mcp/adapters/mcp/server.py:394` — `limit = _or_default(request.limit, DEFAULT_CYCLE_LIMIT)` (default 20, `graph_service.py:58`)
- `src/agentless_mcp/application/graph_service.py:182` — `cycles=tuple(... for cycle in cycles[:limit])`
- `src/agentless_mcp/adapters/mcp/server.py:405` — `limit=_or_default(request.limit, DEFAULT_COMMUNITY_LIMIT)`

So "takes nothing" is wrong twice over: the parameter exists, and "returns every … cycle" is only true below 20. The renderer does mark the elision (`render.py:716`, `"  ... {omitted} more cycles not listed"`), so the agent is told cycles were dropped — but the description has just told it there is no parameter to raise, so the only recovery it can infer is that the answer is complete or unobtainable. This is the description class the last commit ("evidence-based tool description rewrites") was aimed at, and this operation was missed.

Failure scenario: a repo with 40 import cycles; the agent sees 20 plus "20 more cycles not listed", concludes the tool cannot show more, and reports a partial cycle inventory as the full one.

Recommendation: name `limit` in the sentence for both operations, and have `render_cycles`/`render_communities` say how to get the rest (the same pattern `expand_body_truncated` already uses: "Expand this id on its own for the whole body").

### B02-M4 — Layering ruling: the import is defensible, the shape of the core consumer is not
`src/agentless_mcp/core/cache.py:68,110,996-1006` (cross-block with B08)

The Phase-1 question was whether a user-facing message catalog imported by the storage layer is a leak. Verdict: **not a leak on dependency grounds.** `prompts` imports only the standard library (verified above), so it introduces no cycle and inverts nothing; it is the most stable module in the package, which is exactly what "depend toward stability" asks for; and the `pyproject.toml:262-266` layers contract (`adapters -> application -> core -> prompts -> util`) is an explicit, gated decision documented at `pyproject.toml:256-261`. A cross-cutting text leaf below core is a coherent design.

The defect is a different one, and it is in the consumer:

```python
def _rejection(meta: _Meta | None, repo_root: Path) -> str:
    """Return why this database must not be used, or an empty string."""
    if meta is None:
        return MESSAGES.cache_discarded_no_index
    ...
    return ""
```

The return value is agent-facing prose **and** the control-flow sentinel for "is this database usable" (empty string = usable). Two concepts in one value: a domain decision and its presentation. The prose then travels as `ctx.note` into `ENVELOPE.receipt_note.format(note=ctx.note)` (`envelope.py:81`), so core is authoring a line of the response envelope.

Failure scenario: someone rewords `cache_discarded_no_index` to the empty-ish or whitespace-only case and the cache silently becomes "usable" — the loader's non-empty-string check is what currently prevents this, which means a *presentation* validation rule is load-bearing for *persistence* correctness. That coupling is invisible from either file.

Recommendation: `_rejection` returns a typed reason (an enum or `None`), the caller decides usability from the type, and the application layer maps reason → `MESSAGES`. Core then needs no prompt import at all — as a consequence of fixing the conflation, not as the goal.

### B02-L1 — A non-UTF-8 prompt file escapes `PromptDataError`
`src/agentless_mcp/prompts/loader.py:34-40`

```python
    try:
        return resources.files(PACKAGE).joinpath(filename).read_text(encoding="utf-8")
    except OSError as exc:
```

`read_text(encoding="utf-8")` raises `UnicodeDecodeError` on a bad byte, and `UnicodeDecodeError` is a `ValueError`, not an `OSError` (verified: `UnicodeDecodeError.__mro__` → `UnicodeError`, `ValueError`, `Exception`). It passes straight through the handler. This contradicts the module docstring at `loader.py:5-8`, which puts "a file that is not JSON" and its siblings in one class that "all five raise `PromptDataError`" — a corrupt-encoding file is the same class of defect and gets neither the typed error nor the message naming the file. Fails loudly at import either way, so the blast radius is a worse diagnostic, not a wrong answer.

Recommendation: `except (OSError, UnicodeDecodeError) as exc`.

### B02-L2 — Duplicate JSON keys are silently collapsed
`src/agentless_mcp/prompts/loader.py:46`

`json.loads` keeps the last of duplicate keys (verified: `json.loads('{"a": "one", "a": "two"}')` → `{'a': 'two'}`). The manifest check at `:56-65` compares key *sets*, so a duplicated key passes every validation while one of the two texts is discarded. This is the one defect class in the docstring's list that the parse step does not actually catch.

Failure scenario: a merge or a copy-paste edit leaves `messages.json` with `"expand_no_room"` twice; the earlier, intended wording is dropped and nothing anywhere reports it.

Recommendation: `json.loads(text, object_pairs_hook=...)` that raises `PromptDataError` naming the repeated key.

### B02-L4 — `build_record` is a wrapper whose test usage exercises nothing of it
`src/agentless_mcp/prompts/loader.py:77-89`

```python
def build_record(filename, text, record, manifest):
    return record(**parse_strings(filename, text, manifest))
```

One production caller (`load_record`, the next function). The four tests that call it directly (`test_prompts.py:147-177`) all expect `PromptDataError`, which is raised inside `parse_strings` before `record(**...)` is ever reached — so the seam it exists to provide is never used for what it provides. Note also the asymmetry with `load_mapping` (`:92-94`), which inlines the same `resource_text` + `parse_strings` composition rather than going through a named half.

Recommendation: either inline `build_record` into `load_record` and point those four tests at `parse_strings` (as two other tests in the same class already do, `:179-185`), or keep it and make `load_mapping` symmetric. Not both shapes.

### B02-L5 — `manifest` on `load_record` is configurability with one possible setting

### B02-L6 — `expand_symbols` description promises bodies for every id; two caps return ids as refusals instead

### B02-L7 — `expand_no_room`'s `{requested}` is not what the caller requested

### B02-L8 — Four tests in `TestLoadedData` cannot fail
`tests/unit/test_prompts.py:94-113`

```python
    def test_every_tool_name_has_a_description(self):
        assert set(TOOL_DESCRIPTIONS) == set(TOOL_NAMES)
        for name in TOOL_NAMES:
            assert TOOL_DESCRIPTIONS[name].strip(), name
```

`TOOL_DESCRIPTIONS` is built by `load_mapping("tool_descriptions.json", TOOL_NAMES)` (`__init__.py:118`), which already raises unless the key sets match and every value is a non-blank string. If the property were violated, the module import raises and this test errors at collection — it can never report the failure it appears to guard. `test_every_parameter_name_has_a_description` is the same shape. `test_the_description_mapping_cannot_be_edited` and `test_the_records_are_frozen` assert stdlib guarantees (`MappingProxyType`, `@dataclass(frozen=True)`), not this code's behavior.

This does not weaken the block's coverage class — the real assertions are in `TestTemplates`, `TestEagerValidation` and `TestWireDescriptions` — but four of 44 tests are decorative and inflate the apparent count.

Recommendation: delete the two stdlib-guarantee tests; keep the two manifest tests only if rewritten to import the module under a corrupted resource (which is the behavior they claim to cover).

### B02-L10 — `PARAMETER_DESCRIPTIONS` documents one of the four genuinely shared parameters

### B02-L11 — `# note:` prefixes server voice and echoed client input identically
`src/agentless_mcp/prompts/messages.json:8`, `src/agentless_mcp/prompts/envelope.json:4`

`receipt_note` is `"# note: {note}"` and lives above the untrusted-content banner; `map_unresolved_seeds` is `"# note: these focus seeds … {seeds}."` and interpolates client-supplied `focus` strings verbatim (`map_service.py:183-184`), including any newlines they contain.

The placement is correct — `envelope.py:127` puts the banner before the body, so the seed note lands inside the region the banner covers — which is why this is Low rather than a trust-boundary finding. But the two share a prefix, so a seed carrying `\n# repo: …` renders lines that are typographically indistinguishable from the receipt for any reader not tracking the banner boundary. Seeds are commonly copied from an issue description, i.e. content the agent did not author.

Recommendation: strip or escape newlines in the joined seed list at `map_service.py:183`, and give body-level notes a prefix distinct from the receipt's.

- **Pattern worth naming at synthesis time:** every finding above except B02-L3/L4/L5 is a *claim* — a docstring, a tool description, or a remediation string — that the code does not hold. The block's machinery for keeping data and code in sync (manifest validation, template field pinning, the live wire listing) is genuinely good and catches structural drift; nothing catches semantic drift between prose and behavior. That gap is the block's real theme.
