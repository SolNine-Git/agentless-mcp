## High

### B10-H1 — `same_file` tier ignores module scope, so a method shadows a declared import and the correct target is discarded
`src/agentless_mcp/core/resolve.py:200-203`

```python
ordered = _ordered(candidates)
same_file = tuple(entry for entry in ordered if entry.path == path)
if same_file:
    return Resolution(name=name, tier=Tier.SAME_FILE, candidates=same_file)
```

The filter is "defined in this file", not "in this file's module scope". A
method is not in the module namespace of any language this package parses, but
`Definition` carries `symbol.parent_class` and the filter never reads it.
Because precedence is "first tier with any candidate wins and the others are
not consulted" (module docstring, lines 31-36), the `imported` candidate is not
merely outranked — it is never produced.

Reproduced:

```python
# user.py
from core import helper


class Cache:
    def helper(self):
        return 0


def use(v):
    return helper(v)
```

```
py:user.py::use  ->  py:user.py::Cache.helper   same_file
```

The edge to `py:core.py::helper` does not exist at any tier. The tool reports
its *strongest* evidence class for an answer that is wrong, and suppresses the
one candidate backed by a declared dependency.

The existing shadowing test (`tests/unit/test_resolve.py:239`) uses a
module-level `def helper`, where the behavior is correct, so the failure mode is
invisible to the suite.

Recommendation: restrict the `same_file` filter to candidates with
`entry.symbol.parent_class == ""`; a class member should fall through to
`imported` / `unique` / `ambiguous` like any other candidate. If class members
must stay reachable in the same file, they belong in a separate, weaker tier —
not folded into the tier documented as "a local definition shadows an import".

### B10-H2 — the `unique` tier asserts an invariant the code does not hold; 54% of its edges in this repo are unreachable bindings
`src/agentless_mcp/core/resolve.py:23-26`, `211-213`

```
``unique``
    Exactly one definition of that name exists in the repository. Nothing
    connects the two files, but there is nothing else it could be either.
```

There is: anything the repository does not define. A stdlib name, a third-party
symbol, a keyword argument, a dict key spelled as an identifier, or an attribute
on an object of an unrelated type all reach `resolve()` as bare names, and if
the repository happens to contain exactly one definition of that spelling the
result is presented as settled evidence. The reference stream includes attribute
identifiers by design — `core.only_once(value)` producing an `only_once` ref is
what `tests/unit/test_resolve.py:219` depends on — so every `obj.attr` and every
`f(kw=...)` is a resolution candidate.

Measured over this repository, the top `unique` edges by count:

```
233  path            -> py:src/agentless_mcp/application/graph_service.py::GraphService.path
136  text            -> py:src/agentless_mcp/core/vote.py::VoteReport.text
111  line            -> py:tests/unit/test_graph.py::line
 50  tier            -> py:src/agentless_mcp/core/grammars.py::LanguageCapability.tier
```

A rigorous lower bound on the error rate: 1,133 of 2,117 `unique` reference
edges (54%) target a symbol of kind `METHOD`, which a cross-file *bare* name
cannot bind to at all — every one of those edges is an attribute occurrence
matched by spelling. `same_file` 873/3,146 and `imported` 1,114/4,039 have the
same shape.

Failure scenario: an agent asks `explain_symbol` for blast radius, is handed a
`unique`-tier fan-in of 233 sites for `GraphService.path`, and edits or reasons
about a method that none of those sites call. Nothing in the rendered output
distinguishes this from a real binding.

Recommendation: either state the limit in the tier's own vocabulary (`unique` is
"only one definition in *this repository* spells this name" — it is not evidence
that the name refers to a repository symbol at all), or stop emitting
`unique`/`same_file` for candidates that a bare name cannot reach (methods, and
anything the file's own imports contradict). The docstring is what downstream
renderers and the next agent generate against; a claim it does not hold is worse
than a weaker claim.

### B10-H3 — multi-candidate `same_file` / `imported` resolutions are ambiguity, but are not marked ambiguous and are admitted into `shortest_path` by default
`src/agentless_mcp/core/resolve.py:203`, `209`, `440-442`

The module states the contract twice:

> ``ambiguous`` … Every candidate is kept and reported -- picking one silently
> is the failure mode this tier exists to prevent. (lines 26-29)

> ``ambiguous`` edges are excluded unless asked for -- a path built on a guessed
> binding is worse than no path, because it reads like a finding. (lines 434-437)

But `Tier.AMBIGUOUS` is reachable only when the candidate set is *both*
cross-file *and* unimported. A file that defines the same name twice, or imports
it from two modules, produces several candidates at a strong tier, one edge each
— and `shortest_path` filters on `edge.tier is not Tier.AMBIGUOUS`, so every one
of those guessed bindings is walkable by default.

Reproduced:

```python
# app.py
class A:
    def run(self): return 1
class B:
    def run(self): return 2
def driver(thing):
    return thing.run()
```

```
py:app.py::driver -run-> py:app.py::A.run   same_file
py:app.py::driver -run-> py:app.py::B.run   same_file
shortest_path(driver, B.run) -> found=True, 1 hop
```

Measured on this repository: 355 of 14,906 resolutions land on more than one
candidate at a non-ambiguous tier (225 `same_file`, 130 `imported`). A real
instance: `run_cli` resolves `same_file` to three different definitions in
`tests/unit/test_cli.py`, 26 sites each.

This is the global "guards key on the invariant, not a proxy" rule failing:
`shortest_path` wants "was this binding guessed", and keys on the tier label,
which is a proxy that breaks exactly when several candidates survive.

Recommendation: make the ambiguity check structural rather than tier-based —
`len(resolution.candidates) > 1` is the invariant, at any tier. Either exclude
multi-candidate edges from the default path search alongside `AMBIGUOUS`, or
carry a `candidate_count` on `SymbolEdge` and filter on it.

## Medium

### B10-M1 — the repository's own noise-name knob does not reach this module
`src/agentless_mcp/core/resolve.py:194-213` vs `src/agentless_mcp/core/graph.py:101-123`

`core.graph` treats "short and ubiquitous names collide across every file" as a
first-class problem, with two mechanisms — log damping on spread and the
user-configurable `stoplist` — and documents why: "Single- and two-character
identifiers (`i`, `x`, `ok`) collide across every file in a repository". The
`stoplist` is a project-config knob (`core/projectconfig.py:61`) threaded into
`graph.build_graph` (`graph_service.py:281`) and into shared-callers
(`symbol_service.py:530`).

`resolve.Resolver` applies neither. The same collision problem, answered two
different ways by two modules in the same layer, and a user who configures a
stoplist to suppress `ctx` in the map still sees `ctx` edges at `unique` tier in
`explain` and `path`. This is the DRY rule failing on a business rule ("which
name matches are noise") that now has two homes and one silent gap.

Recommendation: thread `stoplist` into `Resolver` and demote stoplisted or
sub-3-character names to `AMBIGUOUS` regardless of candidate count, or document
explicitly in the module docstring that tiering is deliberately undamped and
why.

### B10-M2 — 811 LOC covering three separable concerns
`src/agentless_mcp/core/resolve.py`

The module holds (a) the tier vocabulary and name resolution
(`Tier`/`Resolution`/`Resolver`/`build_file_scopes`/`_submodule_import`, ~150
LOC), (b) edge assembly (`build_graph`/`import_graph`/`_reference_edges`/
`_inherit_edges`/`_import_edges`/endpoint builders, ~200 LOC), and (c) two
generic graph algorithms over the assembled edges (`shortest_path` + `_unwind`;
`import_cycles` + `_components` + `_cycle_chain`, ~180 LOC). Group (c) depends on
group (a) only through `Tier.AMBIGUOUS` in one filter expression — a Tarjan SCC
implementation and a BFS have nothing to do with name resolution, and
`_components` is textbook code that would be easier to test and reuse standing
alone.

Not a defect, and the module is genuinely coherent in the sense Pass 2 asks
about (it has a clear point of view, stated and honored). But it is well past
the 200-600 LOC review target, and the split lines are clean.

Recommendation: if this module is touched again, lift (c) into
`core/graphalgo.py` (or similar) taking `Sequence[SymbolEdge]`. Do not split (a)
from (b) — they share the tier precedence rule and separating them would put the
precedence in two places.

### B10-M3 — self-edge suppression is untested; reverting it leaves the suite green
`src/agentless_mcp/core/resolve.py:637-639` (line 638 uncovered by the entire unit suite)

```python
if source.node == target.node:
    return None
```

The docstring makes a behavioral promise — "A recursive call and a module that
imports itself are both real, and both say nothing about how two things relate"
— and no test exercises it. `test_identical_edges_are_reported_once` uses
`def b(): return a() + a() + a()`, which is not recursive. Deleting the guard
passes the whole unit suite; a recursive function would then get a self-loop that
`_undirected` happily hands to the BFS.

Recommendation: add a fixture with a recursive function and a self-importing
module, and assert no edge from a node to itself.

### B10-M4 — `base_name` test cannot distinguish a correct mapping from a wrong one
`tests/unit/test_resolve.py:312-314`

```python
@pytest.mark.parametrize("text", ["Generic[T]", " enum.Enum ", "Base"])
def test_base_expressions_reduce_to_a_lookup_name(self, text):
    assert resolve.base_name(text) in {"Generic", "Enum", "Base"}
```

Three inputs, one assertion that the output is in the set of all three expected
outputs. A `base_name` that returned `"Base"` for every input is green. This is
the only test of the subscript-stripping and dotted-tail behavior that
`patchlint.py:1346` also depends on.

Recommendation: parametrize `(text, expected)` pairs and assert equality.

## Low

### B10-L1 — dead public members on two value objects
`src/agentless_mcp/core/resolve.py:130-133` (`Endpoint.location`, uncovered),
`244-247` (`Hop.origin`, uncovered)

Neither has a caller in `src/` or `tests/` — `graph_service.py:409-413` reads
`node`/`label`/`path`/`line` off an `Endpoint` individually, and the path
renderer uses `hop.arrival` and `hop.edge` only. Both are the two uncovered lines
that survive the full unit suite. Delete them; `git` holds them if a renderer
wants them back.

### B10-L2 — an aliased symbol import loses the `imported` tier
`src/agentless_mcp/core/resolve.py:312-319`

`statement.names` carries the original name, not the alias — confirmed by
`tests/unit/test_resolve.py:362`, which asserts `scopes["aliased.py"].named["mod"]`
for `from pkg import mod as m`. So for `from core import helper as h`, the scope
binds `helper`, and a call spelled `h(v)` resolves against the name `h`, which
the repository does not define — no edge at all. Recall loss rather than a wrong
answer (the alias name almost never collides), so Low, but the file's declared
dependency is invisible for that use. If the extractor exposes the alias, bind
both spellings to the target.

### B10-L3 — `ImportScope.statements` is a positional 3-tuple consumed across a module boundary
`src/agentless_mcp/core/resolve.py:180`, `307`, `317`; consumed at `609` and at
`src/agentless_mcp/application/graph_service.py:303`

```python
statements: tuple[tuple[str, int, str], ...]
```

`(module, line, target)` is unpacked positionally in two modules, with the empty
string standing in for "unresolved". Everything else in this module is a named
frozen dataclass. Making it one costs three lines and removes the possibility of
a silent field-order swap; the sentinel `""` is also a coalesced default in the
sense the boundary rule warns about, though it stays inside the package.

### B10-L4 — `import_cycles` silently drops a strongly connected component whose chain comes back empty
`src/agentless_mcp/core/resolve.py:509-511`, `807-809` (uncovered)

```python
chain = _cycle_chain(component, ordered)
if chain:
    cycles.append(Cycle(files=chain))
```

For a component of two or more files the DFS in `_cycle_chain` cannot fail — I
worked the argument through and could not construct a counterexample — so the
guard is defensive against an impossible state. But if the invariant ever breaks
(a component built from an adjacency the chain walk does not see), a real import
cycle disappears from the report with no signal. Either drop the guard, or raise
/ log when a component produces no chain. Errors surface; a cycle report that
quietly omits a cycle is the failure this tool exists to prevent.

### B10-L5 — the search bound counts dequeued nodes, not expansions, and `visited` under-reports the work done
`src/agentless_mcp/core/resolve.py:58-61`, `456-466`

`visited` is incremented once per node taken off the frontier, and the check
happens before that node's adjacency loop, which is itself unbounded. A single
node with a very large fan-out is fully expanded no matter what `max_visited`
says, and the `visited` reported back to the caller (surfaced in the rendered
path trace) is smaller than the number of nodes actually touched, since `seen`
grows during expansion. The default of 20,000 makes this academic at current
repository sizes (this repo: 11,522 edges, a real path search visits 6 nodes),
which is why it is Low.

### B10-L6 — `source == target` returns `found=True` for a node that is not in the graph
`src/agentless_mcp/core/resolve.py:445-448`

The identity shortcut precedes any membership check, so `shortest_path(graph,
"py:nowhere.py::gone", "py:nowhere.py::gone")` reports a successful zero-hop
path. `GraphService.path` resolves both endpoints before calling
(`graph_service.py:161-166`), so no shipped caller hits it; it is a contract
sharp edge for the next caller, and it sits directly against the module's own
claim that "'no path' and 'stopped looking' are never the same answer" — "node
does not exist" is a third answer that the return type cannot express.

### B10-L7 — the BFS revisit branch and every multi-hop path are unexercised
`src/agentless_mcp/core/resolve.py:465-466` (line 466 uncovered by the full unit suite)

```python
if reached in seen:
    continue
```

No test in the suite ever reaches an already-seen node, which means every path
test is either one hop or disconnected, and `_unwind`'s loop never iterates more
than a couple of times. The dedup that makes the search terminate on a cyclic
graph, and the parent-link unwinding over a real chain, are both untested.

## Cross-block observations

- **B10-H1 and B10-H3 propagate into the patch linter.** `core/patchlint.py:1077`
  defines `_ARITY_TIERS = frozenset({resolve.Tier.SAME_FILE, resolve.Tier.IMPORTED})`
  and trusts those tiers to pick the signature an arity check is run against. The
  `_CALL` regex at `patchlint.py:1060` has a `(?<![\w.])` lookbehind, so dotted
  attribute calls are excluded — which contains B10-H2 — but a *bare* call to a
  name the file also defines as a class member (B10-H1) or defines twice (B10-H3)
  would be checked against the wrong signature. Whether that produces a false
  "wrong number of arguments" finding on a user's patch should be verified in the
  patchlint block; I did not trace the end-to-end lint path from here.
- **`stoplist` wiring is incomplete at the layer boundary.** `ctx.config.stoplist`
  reaches `graph.build_graph` (`graph_service.py:281`) and shared-callers
  (`symbol_service.py:530`) but not `resolve.build_resolver`
  (`graph_service.py:269`, `symbol_service.py:245`, `lint_service.py:83`). Worth
  checking in the config block whether the knob is documented as map-only.
- **`ResolvedGraph.outgoing()` / `incoming()` rebuild a full dict over every edge
  on each call**, and `graph_service.explain` (`graph_service.py:144-145`) calls
  both for a single node — two full passes over 11,522 edges per `explain_symbol`
  request, to read one bucket from each. Flagging for the graph_service block;
  the fix could equally be a cached mapping on `ResolvedGraph`.
- **`bases` is Python-only.** `extractor._get_bases` reads the
  `superclasses` field, a Python-grammar field name, and every other language's
  handler constructs symbols with `bases=()`. So `Relation.INHERITS` edges exist
  for Python alone, which the resolve docstring does not say and the tool's
  language-coverage claims may. Belongs to the extractor block.
