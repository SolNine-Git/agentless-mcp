## High

### B03-H1 — `duplicate_index` counts collisions across all kinds, but every consumer that reads it has already filtered by kind, so a valid function becomes unaddressable

`src/agentless_mcp/core/symbols.py:98-102` and `:216-247`; consumer `src/agentless_mcp/core/locs.py:264`.

The field's documented meaning is kind-agnostic:

```python
    # How many earlier symbols in the same file already carry this qualified
    # name. Zero for all but a collision, and assigned by
    # :func:`disambiguate` ...
    duplicate_index: int = 0
```

and `disambiguate` keys on `(symbol.parent_class, symbol.name)` with no reference to `symbol.kind`. The only consumer that interprets the number does so *after* narrowing to one kind:

```python
# locs.py:255-264
    functions = [
        symbol
        for symbol in target.symbols
        if symbol.kind == SymbolKind.FUNCTION and symbol.name == wanted
    ]
    ...
    chosen = next((symbol for symbol in matches if symbol.duplicate_index == ordinal), None)
```

Observed, on `a.py` containing `class Foo: pass` followed by `def Foo(): return 1`:

```
ids:  ['py:a.py::Foo', 'py:a.py::Foo#2']
resolve_locs(["function: Foo"]) ->
  unrecognized=(UnrecognizedLoc(loc='function: Foo',
    reason="a.py defines 1 symbols named 'Foo', so there is no number 1"),)
```

Failure scenario: a model reads a repo map, sees one function `Foo`, and emits the canonical location `function: Foo`. The file's only function named `Foo` is silently unreachable through `resolve_locations` and therefore through every patch-application path that resolves locations, and the refusal message is self-contradictory — it reports one match while claiming number 1 does not exist. The same shape hits any file where a class/dataclass/enum/protocol/type-alias/constant shares a name with a function or method (`class Foo` + `def Foo` factory in one Python module is the common instance).

Recommendation: make the ordinal mean what the id means. Either key `disambiguate` and the consumer on the same population, or — cheaper and local to `locs` — drop `duplicate_index` comparison in `_pick` and match on `id_qualname(symbol) == apply_ordinal(name, ordinal)`, which is kind-agnostic by construction and reuses this module's own vocabulary instead of re-deriving it.

### B03-H2 — ids for non-function kinds do not round-trip through the location grammar, and `slice --symbol` answers "no such symbol" for a currently-valid id

`src/agentless_mcp/core/symbols.py:9-14` (the round-trip claim), consumer `src/agentless_mcp/adapters/cli/main.py:692-694`, `src/agentless_mcp/core/locs.py:167-186`.

The module docstring promises the id round-trips:

> "round-trips: every id printed by a map or a skeleton parses back into the file and qualified name that ``expand_symbols`` needs."

and `docs/agent-guide.md:98` widens that to the whole id surface: *"Both forms are accepted anywhere an id is: `expand`, `refs`, `slice --symbol`, `explain`."* The CLI converts every id into a single location shape:

```python
        parsed = parse_stable_id(args.symbol)
        located = services.views.resolve_locations(
            ctx, parsed.path, [f"function: {parsed.qualname}"], context=args.context
        )
```

`_resolve_function` never considers `CLASS_KINDS` or `TYPE_ALIAS`/`CONSTANT`, so any class-shaped id lands in `_resolve_unqualified_method` and misses. Observed on this repo at HEAD with an id `expand` accepts:

```
$ agentless-mcp expand  "py:src/agentless_mcp/core/symbols.py::StableId"   -> renders the dataclass body
$ agentless-mcp explain "py:src/agentless_mcp/core/symbols.py::StableId"   -> renders the card
$ agentless-mcp refs    "py:src/agentless_mcp/core/symbols.py::StableId"   -> 2 references
$ agentless-mcp slice   --symbol "py:src/agentless_mcp/core/symbols.py::StableId"
no such symbol
```

Failure scenario: the documented two-call recipe hands a caller an id from `repo_map`; `slice --symbol` returns a *wrong answer rather than an error* ("no such symbol") for every class, dataclass, enum, protocol, type alias and module constant — roughly half the vocabulary this module defines. A class id carrying an ordinal fails twice over (`class: Bar#2` -> `"no class named 'Bar#2'"`, because `split_ordinal` is applied only on the function branch).

Recommendation: the id vocabulary lives here, so the id-to-location translation should too — add one function in `symbols.py` mapping a symbol/kind to the location string that addresses it (`class:` for `CLASS_KINDS`, `variable:` for `CONSTANT`, `function:` otherwise), and have `main.py:692` and any future consumer call it instead of hardcoding `f"function: {parsed.qualname}"`. Apply `split_ordinal` in `_resolve_class`/`_resolve_variable` as well, at the same door `_resolve_function` uses.

## Medium

### B03-M1 — "relative" is encoded three ways in `ImportStatement` with no invariant, and consumers each pick a different one

`src/agentless_mcp/core/imports.py:11-20`.

```python
@dataclass(frozen=True, slots=True)
class ImportStatement:
    module: str
    names: tuple[str, ...]
    is_relative: bool
    relative_level: int
```

`is_relative` and `relative_level` are not independent facts, and nothing states their relationship. Only the Python handler populates the level (`extractor.py:1954-1955`, `is_relative=relative_level > 0`); every other handler ships the contradictory pair `is_relative=True, relative_level=0` (`extractor.py:1309-1310` C/C++, `:1354-1355` and `:1391-1392` JS/TS, `:1877-1878` Rust). Downstream, `core/graph.py:255` branches on `statement.relative_level`, `core/patchlint.py:861` branches on `statement.is_relative or not module or module[0] in "./"`, and `graph.py:243` actually keys on the module text `module.startswith(".")` — three consumers, three different notions of the same property.

Failure scenario: a language added later copies the JS handler's `relative_level=0` and its relative imports resolve against the repo root instead of the importing file's directory, silently producing an import graph with missing edges — the failure mode of a graph tool that looks like "this repo just has few edges".

Recommendation: one representation. Either make `relative_level` the only stored fact and expose `is_relative` as a property (`relative_level > 0`), or keep both and enforce agreement in `__post_init__`, and fix the non-Python handlers to compute a real level. Illegal states should not be representable in the shared vocabulary.

### B03-M2 — `resolved_path` is a dead field, carried through a `NOT NULL` cache column

`src/agentless_mcp/core/imports.py:20`.

Every construction site in the repo passes `resolved_path=""` (`extractor.py:975, 1312, 1357, 1394, 1880, 1921, 1935`), and no code anywhere reads the attribute for a decision — the only mentions are the cache's own serialise/deserialise pair (`cache.py:807`, `:820`) and the schema (`cache.py:958: resolved_path TEXT NOT NULL`). Applying the justify-its-existence test: deleting it removes a column, two row-mapping lines, and a field that invites a reader to believe imports are resolved when resolution actually happens in `core/graph.py` against a different representation.

Recommendation: delete the field and the column (this is a prototype-internal surface, so a hard removal beats a shim), or populate it at the one place resolution happens.

### B03-M3 — `symbol_stable_id`'s "repository-relative" precondition is documented but unenforced, and a shipped API violates it

`src/agentless_mcp/core/symbols.py:255-261`, violator `src/agentless_mcp/core/extractor.py:650-666`.

```python
def symbol_stable_id(symbol: ASTSymbol) -> str:
    """...
    ``module_path`` is the repository-relative path the scan passed in, so the
    id is portable across checkouts of the same repository.
    """
```

Nothing in `ASTSymbol` checks this, and `TreeSitterExtractor.extract_symbols(file_path: Path)` sets `module_path = str(file_path)`, so symbols from that entry point produce ids like `py:/home/alice/repo/src/app.py::f` — non-portable, and they leak an absolute filesystem path into tool output. The method (and its twin `extract_imports(Path)`) has no callers in `src/` or `tests/`, so this is latent rather than live, which is why it is Medium and not High.

Recommendation: delete the two unused `Path`-taking wrappers (they add public surface and a trap and hide nothing), or have them relativise against a root before calling `extract_from_source`.

### B03-M4 — the id's stability claim overstates what an ordinal can promise, and the drift is silent

`src/agentless_mcp/core/symbols.py:11-13` vs `:226-231`.

The module docstring says an id "survives a re-index (nothing in it is a row id or a line number)". The ordinal is derived from source position: inserting a third `handle` above two existing ones renumbers the existing `handle#2` to `handle#3`, so a previously reported id now names a *different* symbol. `disambiguate`'s own docstring half-acknowledges this ("inserting a method above another one moves the ordinals the same way a reader would expect"), but the two statements cannot both be true, and no consumer detects the drift: `expand_symbols` matches on `id_qualname` (`symbol_service.py:361`) and will happily return the wrong body. `core/refs.py:185-198` degrades a stale id to a name lookup, so the two consumers already behave differently on the same stale id.

Failure scenario: an agent stores ids from a map in its scratchpad, edits the file, then expands — it silently reads the wrong function. Nothing errors.

Recommendation: correct the docstring to scope the stability claim ("stable under re-index; ordinals shift when the set of same-named symbols in the file changes"), and consider having `expand` note the ordinal in the card so a reader can see which of N it got.

### B03-M5 — `SymbolKind.DECORATOR` is dead vocabulary in the most-depended-on module

`src/agentless_mcp/core/symbols.py:70`.

`grep -rn "DECORATOR"` over `src/` and `tests/` returns exactly the definition. The extractor produces eight of the nine kinds (`FUNCTION`, `CLASS`, `METHOD`, `CONSTANT`, `TYPE_ALIAS`, `PROTOCOL`, `ENUM`, `DATACLASS`); nothing produces or consumes `decorator`. It is part of a wire enum read by 13 modules, so every consumer's exhaustiveness reasoning has to account for a value that cannot occur.

Recommendation: delete the member.

## Low

### B03-L1 — `disambiguate` keys on the tuple, the id keys on the joined string

`src/agentless_mcp/core/symbols.py:233-241` vs `:178-182`.

The backstop counts collisions with `key = (symbol.parent_class, symbol.name)`, while the id component is `f"{parent_class}.{name}"`. `("A.B", "c")` and `("A", "B.c")` are distinct keys that spell one qualified name `A.B.c`, so the uniqueness guarantee would not fire. I probed the handlers that could plausibly produce a dotted component — C++ (`n::f`, `S::f` — uses `::`, not `.`), Java nested classes (flattened to `parent_class=""`), JS prototype/member assignments (not extracted) — and found none today, so this is latent, not live.

Recommendation: key on `qualname(symbol)`, the exact string the id is built from. One-line change that closes the class of bug permanently instead of relying on a survey of today's handlers.

### B03-L2 — `parse_stable_id` promises to raise on malformed ids, but a malformed ordinal resolves silently to the wrong symbol

`src/agentless_mcp/core/symbols.py:264-270` and `:203-213`.

> "Malformed ids raise rather than resolving to a plausible-looking wrong symbol: an id is machine-generated, so a broken one is a bug upstream, not user input to be guessed at."

`apply_ordinal` never emits `#0` or `#1`, yet `split_ordinal` accepts both and clamps: `max(0, int(match.group(1)) - 1)` maps `handle#0` and `handle#1` onto index 0, so `py:a.py::handle#1` — an id this package could not have produced — resolves to the first `handle` without complaint. The docstring's "inverse of `apply_ordinal`" is true only over `apply_ordinal`'s image.

Recommendation: either treat an out-of-range ordinal as malformed (consistent with the stated posture), or drop the inverse claim and document the clamp as deliberate leniency.

### B03-L3 — `stable_id` does not guarantee the id it builds parses back

`src/agentless_mcp/core/symbols.py:250-252`.

`stable_id("python", "a::b.py", "x")` yields `py:a::b.py::x`, which `parse_stable_id` reads back as `path="a"`, `qualname="b.py::x"` — no error, wrong parts. A qualified name containing `::` is fine (C++ names like `n::f` were verified to round-trip, because `partition` splits on the first occurrence and the path has none), so only a `::` in a repo-relative path breaks it. Unreachable with normal filenames.

Recommendation: assert in `stable_id` that `_QUALNAME_SEPARATOR not in path` and that neither part is empty — the round-trip property is the module's stated contract and currently nothing enforces it at construction time.

### B03-T1 — test gaps: the behaviours that broke downstream are exactly the unpinned ones

`tests/unit/test_symbols.py`, `tests/unit/test_stable_ids.py`, `tests/unit/test_import_extraction.py`.

The `symbols.py` tests are good ones — behavioural names, real assertions, no mocks, `test_ordinals_follow_the_source_and_not_the_traversal` pins the property its docstring claims, and the malformed-id parametrisation covers the raise path. What they do not pin:

- **Kind-agnosticism of `duplicate_index`** — every ordinal test uses two symbols of the same kind (`COLLIDING` is two functions). The cross-kind case in B03-H1 is untested in either direction; reverting `disambiguate` to a kind-aware key would leave the suite green.
- **Idempotency of `disambiguate`** — `cache.py:347` re-runs it over rows that were serialised from already-disambiguated symbols. It happens to be idempotent (the key ignores `duplicate_index`); nothing states or tests that, and B03-L1's suggested fix to key on `qualname(symbol)` would quietly break it.
- **`apply_ordinal` directly** — only reached through `id_qualname`; the `apply_ordinal`/`split_ordinal` round trip is never asserted as a pair.
- **`ImportStatement` has no test of its own.** `test_import_extraction.py` asserts extractor output (`imports[0].relative_level == 1` for Python only); no test observes that non-Python handlers ship `is_relative=True, relative_level=0`, so B03-M1's inconsistency is invisible to the suite.
- **`language_prefix` fallback** is tested via `stable_id("zig", ...)`, but `test_every_supported_language_has_a_prefix` is the gate that matters and it only checks `supported <= set(LANGUAGE_PREFIXES)` — a prefix collision between two entries would pass.

Adversarial tests worth adding (one line each): a file with `class Foo` + `def Foo` asserting `function: Foo` resolves; `disambiguate(disambiguate(xs)) == disambiguate(xs)`; `apply_ordinal(*split_ordinal(x)) == x` over generated names; a `slice --symbol` round trip over every id a map prints for a fixture repo (this is the test that would have caught B03-H2 and it belongs in `tests/characterization/test_two_call_contract.py`, which today only round-trips `expand`); `ImportStatement` parity across two languages for the same relative import.

## Cross-block observations

- **`main.py:692` raises out of a CLI handler.** `agentless-mcp slice --symbol not-an-id` prints a Python traceback ending in `ValueError: not a stable id: ...` instead of a usage error; every other id consumer catches it (`symbol_service.py:338-341` returns the message as a miss). Same file as B03-H2 — the CLI is the one consumer that neither catches the documented exception nor translates the id correctly.
- **`locs.py` cannot address three of the nine kinds.** `_resolve_class` covers `CLASS_KINDS`, `_resolve_variable` covers `CONSTANT`, `_resolve_function` covers `FUNCTION`/`METHOD`; `TYPE_ALIAS` (produced for Rust and one other handler) has no location form at all, and `_resolve_class`/`_resolve_variable` ignore the ordinal that `_resolve_function` splits off. The location grammar and the id vocabulary have drifted apart; they should be reviewed as one contract.
- **`cache.py` writes a `qualname` column nobody reads.** `cache.py:716` and `:784` persist `id_qualname(symbol)` into `tags.qualname` (`NOT NULL`, `cache.py:936`), but `_symbol_rows`'s SELECT (`cache.py:349-353`) does not include it and no other query does — while the ordinal it encodes is deliberately *recomputed* on read. Two homes for the same derived knowledge, one of them unread and therefore untested for drift. The recompute-on-read design is the right one; the stored column should go.
- **`extractor.py:650-666` — `extract_symbols(Path)` / `extract_imports(Path)` have no callers** anywhere in `src/` or `tests/`, and are the only code paths that can produce absolute-path stable ids (B03-M3). Candidates for deletion in the extractor block.
- **`tests/conftest.py:29-46` warms grammars over the network on a cold machine** (documented: "If the machine's language-pack cache is cold, this fixture performs one real warmup"). Session-scoped and honest about it, but it means a first run on a fresh CI box is not hermetic; worth a decision at suite level rather than per block.
- **C++ in-class method bodies are not extracted.** Probing `struct S { void f() {} };\nvoid S::f() {}` yielded only the class and the out-of-line `S::f`; the inline definition produced no symbol. Extractor-block issue, surfaced here while checking id uniqueness for C++ overloads.
