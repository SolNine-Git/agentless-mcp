### B09-H1 — `_candidate_bases` keys on a signal the extractor never emits; every Python `from . import x` and `from ..x import y` silently loses its import edge

`src/agentless_mcp/core/graph.py:250-265`

```python
    if module.startswith("."):
        # JavaScript-style "./sibling" and "../up/one", and Python-style
        # ".module" / "..package.module", which the extractor reports with an
        # explicit relative_level.
        if statement.relative_level:
```

The comment asserts a contract with `core/extractor.py` that the extractor does not honor. `_resolve_from_module` (`core/extractor.py:1961-1984`) reads the `import_prefix` node to produce `relative_level` and separately reads the `dotted_name` child to produce `module` — so the dots are **stripped** from the module string. Measured:

```
from . import sib          -> module=''          relative_level=1
from .mod import a         -> module='mod'       relative_level=1
from ..pkg.deep import b   -> module='pkg.deep'  relative_level=2
```

None of those start with `"."`, so the `if module.startswith(".")` gate is never true for Python and lines 255-260 — the only code in the module that actually understands `relative_level` — are dead. Coverage confirms it: `256-260` is uncovered by the **full** 1035-test suite, not just by `test_graph.py`.

Measured on a real package fixture (`pkg/sub/user.py` importing four ways):

```
module=''         lvl=1 -> resolve_import_target = None
module='deep'     lvl=1 -> resolve_import_target = 'pkg/sub/deep.py'   # accidental: directory/dotted happens to be right at level 1
module='helper'   lvl=2 -> resolve_import_target = None
module='sib'      lvl=2 -> resolve_import_target = None
```

Edge weights that resulted: `user.py -> pkg/helper.py: 0.953` and `-> pkg/sib.py: 0.953` (name-reference edges only) versus `-> pkg/sub/deep.py: 4.430` (name edges plus the 3.0 import edge).

Failure scenario: any Python package laid out as a package tree with parent-relative imports — the dominant convention outside src-flat scripts — gets its declared dependency edges silently downgraded to accidental-name-collision edges. The module docstring sells `IMPORT_EDGE_WEIGHT = 3.0` as the thing that makes a declared dependency "worth several accidental name matches"; for those files it contributes nothing. `repo_map --focus` ranks the wrong files, and `core/resolve.py:306` builds an `ImportScope` missing those modules, so cross-file symbol resolution for the same imports degrades to `ambiguous`. Nothing fails loudly; the answer just gets worse.

Recommendation: gate on `statement.relative_level` first, not on `module.startswith(".")`, and keep the `startswith(".")` test only as the JS fallback for `relative_level == 0`. The existing body of lines 255-260 is already correct for the extractor's actual output — it just needs to be reachable. Pin it with a fixture repository containing `from . import x`, `from .mod import x` and `from ..pkg.mod import x`, asserting the resolved target for each.

### B09-H2 — JavaScript/TypeScript `../sibling` imports never resolve: the joined path is never normalized

`src/agentless_mcp/core/graph.py:261-262`

```python
        cleaned = PurePosixPath(module)
        return [str((directory / cleaned).as_posix()).replace("/./", "/")]
```

`PurePosixPath` collapses a leading `./` but never resolves `..` (that would require the filesystem, which `PurePosixPath` deliberately does not touch). Measured:

```
_candidate_bases("../pricing", stmt, PurePosixPath("src/a")) -> ['src/a/../pricing']
resolve_import_target("src/a/b.ts", stmt("../pricing"), ["src/pricing.ts"]) -> None
resolve_import_target("src/a/b.ts", stmt("./pricing"),  ["src/a/pricing.ts"]) -> 'src/a/pricing.ts'
```

`src/a/../pricing` matches no key in `known`, and the `_suffix_match` fallback then tests `endswith("../pricing")` which no repository path ever satisfies. The `./` form works, so the existing test (`test_graph.py:140-151`) passes while the parent form is broken.

Failure scenario: same as B09-H1, for the entire JS/TS/TSX family. `../` is the single most common relative import form in a `src/components` / `src/lib` layout, so a TypeScript repository's map loses most of its declared edges while a flat one keeps them — the ranking quality silently depends on directory depth.

Recommendation: normalize the joined path with `posixpath.normpath` before returning it, and add a test for `"../pricing"` alongside the existing `"./pricing"` one. Note that this and B09-H1 are the two halves of the same site: the one branch that would handle relative imports correctly is unreachable, and the branch that does run cannot handle `..`.

### B09-H3 — `_suffix_match` matches mid-path-component, resolving an import to the wrong file and weighting the wrong edge 3x

`src/agentless_mcp/core/graph.py:279-283`

```python
    matches = sorted(
        (path for path in known if PurePosixPath(path).with_suffix("").as_posix().endswith(tail)),
        key=lambda path: (len(path), path),
    )
    return matches[0] if matches else None
```

`endswith` is a string test, not a path test, so it matches inside a path component. Measured:

```
_suffix_match("core/refs",  {"src/mycore/refs.py"})  -> 'src/mycore/refs.py'
_suffix_match("utils/io",   {"src/myutils/io.py"})   -> 'src/myutils/io.py'
resolve_import_target("app.py", stmt("core.refs"),
                      ["a/mycore/refs.py", "deep/nested/core/refs.py"]) -> 'a/mycore/refs.py'
```

The last case is the damaging one: the correct file `deep/nested/core/refs.py` is present, but the tie-break `key=(len(path), path)` prefers the **shorter** path, so the false match wins outright. The docstring claims the resolver "never guesses between candidates: it takes the shortest match so the answer does not depend on walk order" — shortest-wins is presented as a determinism property, but here it actively selects the wrong candidate over the right one.

Failure scenario: a repository with both `core/` and `mycore/` (or `utils/`/`myutils/`, `api/`/`internalapi/` — common enough after a fork or a vendored copy) gets a fabricated 3x-weighted import edge to the wrong file, and the real one gets nothing. Blast-radius and map answers point at a file that does not participate. This is the failure mode the refs docstring explicitly promises does not happen ("it never silently under-reports").

Recommendation: require the match to begin at a path boundary — `stem == tail or stem.endswith("/" + tail)`. The determinism tie-break can stay.

### B09-M1 — `refs` (domain scan) imports the SQLite persistence module at runtime, not just for typing

`src/agentless_mcp/core/refs.py:28`, used at `refs.py:111`

```python
from agentless_mcp.core.cache import FileSource, effective_source
...
    facts_source = effective_source(source, extractor)
```

Ruling on the phase-1 hint: **half-correct**. `refs` does take a `FileSource` *Protocol* (`core/cache.py:159`), not the concrete `SqliteSource`, so the type coupling is properly inverted — a caller can pass any structural match and `test_cache.py` does. But the abstraction is **defined in the infrastructure module**, and `refs` additionally calls `effective_source`, a concrete factory in the same module, on every scan. So the module edge is a real runtime edge: `import agentless_mcp.core.refs` transitively imports `sqlite3`, `hashlib`, `util.filelock` and `util.platforms`, and every downstream module (`graph`, `resolve`, `patchlint`, `communities`, `symbol_service`, `map_service`, `lint_service`, `graph_service`) inherits it. Dependency inversion is applied to the type and not to the module.

No gate catches this and none can as configured: both modules live in the `core` layer, so the import-linter layers contract (`pyproject.toml`) is silent by construction, and `exclude_type_checking_imports = true` would have excused the Protocol import anyway — but not the `effective_source` call, which is a runtime import regardless.

Failure scenario: no runtime bug today. The cost is that `refs` (Ca=7, Ce=7, I=0.50) cannot be tested, reused, or reasoned about without the persistence stack, and any future change that makes `cache` import something heavier pushes that cost onto the whole graph.

Recommendation: move the `FileSource` Protocol and the `effective_source`/`OnDemandSource` default into a small neutral module below both (`core/facts_source.py`, or `util/`), and have `cache` import *it*. That is a mechanical move — `FileSource` is structural, so no implementation changes. Then the layers contract can be tightened to express "cache is above refs" instead of both being anonymous members of `core`.

### B09-M3 — `resolve_import_target` rebuilds `set(known_paths)` on every call, including from `build_graph`, which already holds the set

`src/agentless_mcp/core/graph.py:233` and `graph.py:131`

```python
    known = set(known_paths)          # line 233, inside resolve_import_target
...
    known = set(nodes)                # line 131, inside build_graph, never passed down
```

`build_graph` computes `known` at line 131 for the name-edge loop, then calls `resolve_import_target` once per import statement (line 150) passing the `nodes` tuple, which reconstructs an identical set each time. Measured on this repository: 639 import statements over 110 nodes — 70k redundant set insertions for a small repo, growing as O(import statements x files). `core/resolve.py:306` and `core/resolve.py:348` have the same shape, and `_submodule_import` calls it once *per imported name*.

Failure scenario: not a correctness bug, but the repo-map primitive is the one call agents make on every task, and this is the term that grows fastest with repository size. On a 10k-file / 50k-import repository it is ~5x10^8 set operations of pure waste.

Recommendation: accept an optional pre-built `frozenset[str]` (or make the parameter `AbstractSet[str] | Sequence[str]` and skip the rebuild when it is already a set) and pass `known` down from `build_graph` and `build_file_scopes`.

### B09-M4 — `build_graph(scan, index)` takes two arguments that must be derived from each other, with nothing enforcing it

`src/agentless_mcp/core/graph.py:126-128`

```python
def build_graph(
    scan: RepoScan, index: RefIndex, *, stoplist: frozenset[str] = frozenset()
) -> RefGraph:
```

`index` must be `build_ref_index(scan)` for the result to mean anything — `_reference_weight` reads `index.files_referencing` for names it found in `scan`, and `index.defining_paths(name)` supplies the edge targets. Every one of the five call sites does exactly `scan = ...; index = build_ref_index(scan); build_graph(scan, index)` (`map_service.py:125-130`, `graph_service.py:279-281`, three test sites). Passing a mismatched pair produces a silently wrong graph rather than an error: `_reference_weight`'s `index.files_referencing.get(name, 1)` (line 288) coalesces the miss to a damping of `1 + log(2)` and carries on.

The same unenforced pairing repeats in `resolve.py:415 resolve_repo(scan, index)` and `resolve.py:351 build_resolver(scan, index)`.

Recommendation: since no caller ever separates them, either have `build_graph` take the scan and build the index itself, or attach the index to `RepoScan` as a cached property so the pair cannot come apart. Failing that, drop the `.get(name, 1)` default at line 288 so a mismatched index raises instead of producing a plausible number.

### B09-M5 — `RefGraph` accepts edge maps its own consumer cannot process, failing two different ways depending on which end is unknown

`src/agentless_mcp/core/graph.py:95-98` and `graph.py:193-195`

```python
        collected: dict[str, list[tuple[str, float]]] = {node: [] for node in self.nodes}
        for (source, target), weight in self.edges.items():
            collected.setdefault(source, []).append((target, weight))
```

The `setdefault` tolerates an edge whose *source* is absent from `nodes` — and `personalized_pagerank` then iterates `nodes` only, so that edge is silently discarded. An edge whose *target* is absent crashes. Measured:

```
RefGraph(nodes=("a.py",), edges={("ghost.py","a.py"): 1.0}) -> {'a.py': 1.0}          # silently dropped
RefGraph(nodes=("a.py",), edges={("a.py","ghost.py"): 1.0}) -> KeyError 'ghost.py'
RefGraph(nodes=("a.py","a.py"), edges={})                   -> ranks sum to 0.5       # duplicate nodes
```

`build_graph` maintains the invariant, but `RefGraph` is a public frozen dataclass constructed directly by `mermaid.py`, `communities.py` and four test modules, so the invariant is convention only. The `setdefault` is the tell: it is a defensive branch that makes one invariant violation invisible while the symmetric one raises a bare `KeyError` from inside a numeric loop.

Recommendation: replace `setdefault` with plain indexing so both violations fail identically and immediately, or validate in `__post_init__` that every edge endpoint is in `nodes` and that `nodes` has no duplicates. Do not keep the current asymmetry.

## Cross-block observations

**Ruling on the `refs -> cache` edge (phase-1 hint).** The hint is half right and the half that is right is the module edge, not the type edge. `refs` takes the `FileSource` **Protocol**, never the concrete `SqliteSource` — structural typing, and `test_cache.py:566` exercises a substitute. So dependency inversion *is* applied at the type level. What is not inverted is the module: `FileSource` is declared inside `core/cache.py`, the 1000-line SQLite module, and `refs.py:111` additionally calls `effective_source`, a concrete factory from that same module, on every scan. The transitive `sqlite3` dependency the hint predicts is therefore real and is a runtime import, not a `TYPE_CHECKING` one — `graph`, `resolve`, `patchlint`, `communities`, `mermaid` and all four application services inherit it. Fix is mechanical: move the Protocol and the on-demand default into a neutral module below both. See B09-M1.

**The import-linter contract cannot see this class of problem.** The layers contract names five layers with `core` as one opaque member, so any intra-`core` direction — `refs -> cache`, `graph -> refs`, `patchlint -> graph` — is unconstrained by construction. Combined with `exclude_type_checking_imports = true`, the repo's stated dependency guarantee does not extend inside its largest layer. Worth a Phase-6 recommendation to add intra-`core` layering, which the modules already respect in every case I checked except this one.

**`resolve_import_target` is shared infrastructure and both H-findings propagate through it.** Three consumers outside this block call it: `core/resolve.py:306` (ImportScope construction — the missing edges degrade symbol resolution to `ambiguous`), `core/resolve.py:348` (`_submodule_import`, once per imported name), and `core/patchlint.py:829` (undeclared-dependency suppression). I checked the patchlint path specifically: `_top_level_package` (`patchlint.py:853-866`) returns `""` for any module whose first character is `.` or `/`, so the relative-import failures do **not** produce false "undeclared dependency" findings. That is the one place the bug is contained. `resolve.py` is not contained and should be re-checked by whichever block owns it after H1/H2 are fixed — some of its resolution-tier behavior may currently be tested against the broken resolver.

**The `set(known_paths)` rebuild (B09-M3) is a shared cost, not a block-local one.** `resolve.py:306` and `resolve.py:348` reconstruct the same set per statement and per imported name respectively. Whoever fixes the signature should fix all three call sites together.

**Duplicated per-file symbol indexing.** `refs.symbols_by_qualname` (dead), `resolve.py:673 _owners`, and `patchlint.py:928 _module_level_symbols` are three implementations of "index one file's symbols", with three different key and tie-break rules. Not a defect on its own — the rules genuinely differ — but the dead one in `refs` should go rather than stand as a fourth candidate answer in the most-depended-on module.
