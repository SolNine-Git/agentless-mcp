## High

### B05-H1 — `render_ref_groups` and `render_symbol_cards` report a truncated count as the total

`src/agentless_mcp/application/render.py:783-795` and `:776-780`

```python
def render_ref_groups(groups: Sequence[RefGroup], target: str) -> str:
    ...
    total = sum(len(group.sites) for group in groups)
    blocks = [f"{total} references to {target}"]
```

Both renderers receive only an already-truncated tuple and recompute the total from what survived. `symbol_service.py:247` builds the groups from `sites[:limit]` (default `DEFAULT_REFS_LIMIT = 50`) and `symbol_service.py:190` builds the cards from `matches[:limit]` (default `DEFAULT_FIND_LIMIT = 20`). `RefsResult` and `FindResult` both carry the honest `total` and `limit`, and both `as_dict()` forms emit them — but neither value is passed to the text renderer, and neither adapter supplies an `envelope.Truncation` (`main.py:739` builds `_Answer(text, result.as_dict(), "groups")` with `truncation` left at `None`; `server.py:295-298` calls `self._wrap(ctx, body)` with no truncation either) — even though both adapters do supply one for the map view (`main.py:642`, `server.py:226`), so the honest channel exists and was simply not extended here.

The module already knows this is a defect. `SharedCallerListing`'s own docstring (209–216) says:

> "A `Sequence` rather than a bare tuple because the renderer receives nothing but this object and the target name, and **an omitted count that lived anywhere else would be a truncation the text render could not announce**."

The same author wrote, at `RefGroup` (129–139): *"Fan-in still lists every name match -- a missed caller is the expensive error."* The wrapper was built for the secondary adjacency view and never applied to the primary fan-in view it was written to describe.

Reproduced (7 real references, `limit=3`):

```
total: 7 limit: 3
--- TEXT ---
3 references to helper

user.py  (3 references, resolved-via-import)
    1| (module level)    user.py:1
    4| c0  [py:user.py::c0]    user.py:4
    7| c1  [py:user.py::c1]    user.py:7
--- JSON total --- 7
```

Failure scenario: an agent asks `find_referencing_symbols("save_config")` on a repository where the symbol has 120 call sites. The tool answers `50 references to save_config`, lists 50, and says nothing else. The agent concludes it has enumerated the blast radius, patches the 50, and ships a change that breaks 70 unlisted call sites. `render_map`, `render_communities`, `render_cycles`, `render_shared_callers` and `_render_tiers` all announce their cuts (`"... N more …"`); these two are the exceptions, so the silence reads as "there was nothing more".

Recommendation: give fan-in and find the same treatment `SharedCallerListing` already has — a frozen listing wrapper carrying `rows`/`total`/`limit` with the shared `omitted` property, passed whole to the renderer, and append the established `f"  ... {omitted} more references not listed"` line. Do not fix this by threading a second `total` argument into the renderer signature; the whole point of the existing wrapper is that the count cannot get separated from the rows. While consolidating, the identical `omitted` property now copy-pasted into `SharedCallerListing` (222–225), `TierGroup` (281–284), `CycleReport` (420–423) and `CommunityReport` (469–472) should collapse into one base — four copies is past the rule-of-three.

### B05-M1 — the import sections of an explanation have no omitted count in *either* rendering

`src/agentless_mcp/application/render.py:296-307` (`ImportRow`), `:738-755` (`_render_imports`), truncated at `graph_service.py:449` (`return tuple(rows[:limit])`, `DEFAULT_EXPLAIN_LIMIT = 20`)

```python
def _render_imports(explanation: Explanation) -> str:
    lines = ["imports"]
    if explanation.imports_out:
        lines.extend(... for row in explanation.imports_out)
    else:
        lines.append("    declares  none resolved inside this repository")
```

`Explanation.imports_out` / `imports_in` are bare `tuple[ImportRow, ...]`. Unlike the fan-in case (B05-H1), the total is not merely *unpassed* — it is never computed. `graph_service._imports` slices `rows[:limit]` and discards `len(rows)`, so `Explanation.as_dict()` (365–378) is dishonest too: `{"imports": {"declared": […], "importers": […]}}` carries no count and no cap. There is no honest channel at all.

Failure scenario: `explain_symbol` on a widely-imported module (a `config.py`, a `models.py`) reports exactly 20 importers under `imported by`, and both the text and JSON consumers read that as the complete importer set. This is the same "missed caller is the expensive error" class as B05-H1, one layer down, and it is worse in that the JSON escape hatch is closed.

Recommendation: fix alongside B05-H1 — `Explanation` should hold an import listing that carries `total`, `_render_imports` should emit the `"... N more"` line, and `as_dict` should surface the count. Attribute the slicing change to the graph-service block (cross-flagged below); the view-model shape is this block's.

### B05-M2 — `strip_fence` accepts only a document that is *nothing but* a fence, which is not what the feature is documented to do

`src/agentless_mcp/application/render.py:623-643`, consumed at `adapters/cli/main.py:882`

```python
    if not lines or not lines[0].startswith(FENCE):
        return text
    closing = len(lines) - 1
    while closing > 0 and not lines[closing].strip():
        closing -= 1
    if closing == 0 or lines[closing].strip() != FENCE:
        return text
```

The docstring says *"a diagram committed into a document -- fenced, as a document needs it -- can be compared byte for byte against a fresh render"*, and `docs/agent-guide.md:541-543` promises *"A leading ```mermaid fence is stripped before comparing, so a diagram committed into a `.md` file can be checked exactly as it stands."* Neither is true of a document. Measured:

```
strip_fence(docs/diagrams/architecture.md) unchanged? True     # file opens "# Architecture"
render_diagram roundtrip (no caveat):      True
render_diagram roundtrip (with caveat):    False
```

Two concrete failures. (a) Every committed diagram in this repo's own `docs/diagrams/` opens with a markdown heading and prose, so `--check` on any of them returns the whole file and reports drift. (b) `render_diagram` (608–620) appends the caveat line *after* the closing fence whenever `grouped and elided > 0`, so its own output no longer round-trips through its documented inverse. Line 642 — the branch that rejects (b) — is one of the untested lines.

Worse than the refusal is *how* it refuses: `_check_diagram` (`main.py:883`) treats "no fence found" as identical to "drifted", so the caller gets `has drifted from the current diagram`, `committed 41 lines, regenerated 12 lines`, `first difference at line 1: …`. The user is told their diagram is stale when the real answer is "this file is not a bare diagram and I did not look inside it". `docs/agent-guide.md:502` also points `--check` at `docs/diagrams/modules.md`, a path that does not exist.

Recommendation: decide which contract is real. Either narrow the docstring and the guide to "a file containing only a fenced diagram" and have `strip_fence` report *unfenced* distinctly so `_check_diagram` can say "no fenced diagram found in FILE" instead of fabricating a drift, or extend it to locate the first ```` ```mermaid ```` block in a document and its matching close. Do not leave the code and the two prose claims disagreeing. Cover line 642 either way.

### B05-M3 — the module docstring claims an ownership invariant the codebase does not hold, and acting on it would create an import cycle

`src/agentless_mcp/application/render.py:10-12`

```
The view models live here rather than in the services because this module owns
the output vocabulary: a service decides *what* is worth showing, this decides
what it looks like.
```

It does not own the output vocabulary. `render_expansion` lives at `symbol_service.py:370`, `render_tree` at `core/treewalk.py:160`, `line_wrap_content` at `core/slices.py:77`, the skeleton's line rendering at `core/skeleton.py:284`, and `_render_locations` at `adapters/cli/main.py:1354`. Five renderers outside the module that "owns" rendering, with no stated rule for the split.

Per the skill's Pass-1 guidance this is scored at the severity of the bug it induces, and that bug is specific: a maintainer who reads the docstring literally and moves `render_expansion` into `render.py` makes `render.py` depend on `symbol_service.ExpandResult`, and `symbol_service.py:45` already imports `render` — an import cycle in the application layer, which the `[tool.importlinter]` layer contract (`pyproject.toml:244`) will fail loudly but only after the work is done. The current placement is the DAG-correct one; the sentence is what is wrong.

Recommendation: replace the ownership claim with the actual rule — this module holds the vocabulary shared across services, and a renderer whose input type is owned by one service stays with that service so the dependency keeps pointing one way. One sentence, and it makes the layering legible instead of inviting a cycle.

### B05-L6 — two small convention drifts, one of them a portability trap

`src/agentless_mcp/application/render.py:619` and `:142`

```python

`chr(10)` is there because a backslash inside an f-string expression is a `SyntaxError` before Python 3.12, and `pyproject.toml:14` sets `requires-python = ">=3.10"`. ## Cross-block observations

- **The omitted-count contract is repo-wide, not local.** Five listings announce their cuts and three do not, and the three that do not are split across blocks: the slicing lives in `symbol_service.py:190,247` and `graph_service.py:449`, the silence in `render.py:738,776,783`, and the unused honest channel in `envelope.Truncation` (`envelope.py:53`) which no adapter ever populates for these views. Worth an explicit rule during synthesis: *a service that slices must return the pre-slice total, and a renderer that receives a sliced sequence must receive that total with it.* `SharedCallerListing` is the existing model of the fix.
- **`envelope.Truncation` is the existing honest-truncation channel, wired for exactly one view.** Both adapters populate it for the map (`main.py:642`, `server.py:226`, `Truncation(shown=result.included, total=result.candidates, unit="symbols")`) and for nothing else; `_Answer.truncation` (`main.py:1332`) stays `None` for refs, find, explain, cycles, communities and lint. So the mechanism B05-H1 and B05-M1 need already exists, is already carried through `envelope.wrap`, and was simply never extended past the first view that needed it. That is the cheapest fix path and it belongs to the adapter blocks as much as to this one.
- **`docs/agent-guide.md:502` cites `docs/diagrams/modules.md`, which does not exist**, and the repo's three real committed diagrams (`architecture.md`, `funnel.md`, `validate-vote.md`) are hand-written, not `agentless-mcp diagram` output. The "never-stale committed diagram" story documented at lines 541–546 has no working instance in this repository, and per B05-M2 could not have one in `.md` form. Docs block.
- **No CI.** `.github/workflows/` does not exist, so `requires-python = ">=3.10"`, the import-linter contract, ruff, and mypy are enforced only by whoever remembers to run `pre-commit` locally. Several findings in this block (B05-L6 especially) are Low *only* because a matrix build would catch them — without one they are unguarded. Repo-level.
- **`N| ` line numbering is knowledge with four homes** (`render.py:767,857`, `core/skeleton.py:296,299`, `core/slices.py:53`, plus dead `render.number_lines`). The formats already differ — `render.py` right-aligns to width 5, `slices.py` appends a trailing space under `add_space`, `skeleton.py` emits a bare `N| ` for blank lines. Any block that touches line-numbered output should be checked against the others.
