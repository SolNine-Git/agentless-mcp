## High

### B19-H1 — `explain` truncates both import sections silently, in the one module whose docstring promises it never does

`src/agentless_mcp/application/graph_service.py:430-452` (`_imports`), reached from `graph_service.py:146-147`.

    rows = [ render.ImportRow(...) for edge in matching ]
    return tuple(rows[:limit])

`render.ImportRow` (`src/agentless_mcp/application/render.py:296-307`) carries `path, line, module, other` and nothing else — no `total`, no `omitted` — and `render._render_imports` (`render.py:738-755`) prints one line per row and stops. Every other bounded section in this file reports its bound: `_tier_groups` builds `render.TierGroup(total=len(buckets[tier]))`, `cycles()` sets `total=len(cycles)`, `communities()` sets `omitted=max(0, community.size - members)`. The module docstring at `graph_service.py:43` states the invariant outright: "Every one of them is bounded and says what it left out." The imports section is the counterexample.

Measured on a generated repository where 30 files carry `from core import helper`, `explain(ctx, "helper")` (default `limit=20`):

    imports_in rows: 20 (real importers: 30)
    fan_in totals: [('imported', 60, 20, 40)]

The fan-in section correctly announces `60` total and `40` omitted; the rendered `imports` block lists 20 `imported by` lines and says nothing about the other 10. `Explanation.as_dict()` (`render.py:365-378`) is worse: `"imports": {"declared": [...], "importers": [...]}` are bare lists, so a JSON consumer has no field that could carry the count.

Failure scenario: an agent calls `explain_symbol` on a widely-imported module-level helper to size a blast radius, reads "imported by" and counts 20 files, and edits the signature believing it has seen every importer. The tool description sold this as "the import relationships of the file it lives in" — unqualified. Twenty of thirty is the exact failure the package's envelope docstring says it exists to prevent ("a bounded view is never mistaken for a complete one").

Recommendation: give the imports sections the same shape the tier groups already have — count `matching` before slicing and carry `total` (or an `omitted`) on a small `ImportSection` value object, then have `_render_imports` emit the `... N more` line the tier renderer already emits. Do not fix this by raising the default limit.

### B19-H2 — a focused diagram reports an elision count and a cause that the diagram itself contradicts

`src/agentless_mcp/application/graph_service.py:256-263`:

    return render.DiagramView(
        text=text,
        nodes=len(drawn),
        elided=max(0, len(ranked.graph.nodes) - len(drawn)),
        ...

`elided` is computed against every node in the repository. The mermaid renderer computes its own elision against the *candidate* set, which a focus restricts first — `core/mermaid.py:192, 203-205`:

    candidates = _candidates(graph, settings)   # neighbourhood when focus is set
    ...
    elided = len(candidates) - len(selected)
    if elided > 0:
        lines.append(f'{_INDENT}{ELISION_ID}["... {elided} more modules"]')

Measured on a 14-file generated repository (`a.py` imports `b.py`, twelve unrelated files), `diagram(ctx, focus="a.py")`:

    FOCUS diagram: nodes= 2 elided= 12 focus= a.py
    flowchart LR
        %% solid: imports, dashed: references
        n0["a.py"]
        n1["b.py"]
        n0 --> n1

The picture carries no elision node — correctly, since nothing in `a.py`'s neighbourhood was dropped — while the same call's `elided` field says 12. The CLI prints that number on the receipt (`adapters/cli/main.py:861-865`, `f"diagram of {view.nodes} modules{focus}{grouped}; {view.elided} elided"`), so one response says both "nothing was left out" and "12 elided". With `group_by_communities=True` the same run emits:

    note: subgraph titles name whole communities, including the 12 module(s) the rank bound left out of this diagram

The rank bound left out zero modules here; the focus neighbourhood left out twelve. `DiagramView.caveat` (`render.py:503-517`) names a cause it cannot observe, and the `analyze_structure` tool description promises "PageRank-bounded with an explicit elision marker" — the marker is absent exactly when the field is loudest.

Failure scenario: an agent (or a human reading the CLI receipt) asks for a focused diagram of a subsystem, sees "12 elided" plus a caveat blaming the rank bound, and raises `max_nodes` to recover them. Nothing changes, because the missing modules are outside the focus neighbourhood, and the retry costs a full repository re-scan. Conversely, a reader who trusts the picture concludes 12 modules were dropped for rank reasons and mistrusts a diagram that is in fact complete for what it claims to show.

Recommendation: have the service report what the renderer actually elided rather than re-deriving it. `mermaid.selected_nodes` already exists so a caller need not parse its own output; add the peer that returns the candidate count (or return both from one call), set `elided = candidates - drawn`, and, if the repo-wide number is still wanted, carry it as a separate, differently-named field (`outside_focus`) so the caveat can attribute each number to its own cause. Pin the focused case with a test — `test_a_focus_keeps_the_seed_and_its_neighbourhood` asserts only `focus` and the text.

## Medium

### B19-M1 — the service accepts bounds it does not own, so the invariant is enforced in one adapter and in core, not in the one place both callers cross

`graph_service.py:218-263` (`diagram`), `177-185` (`cycles`), `187-216` (`communities`).

`diagram` passes `max_nodes` straight into `mermaid.DiagramOptions`, and `core/mermaid.py:253-255` raises a bare `ValueError("max_nodes must be at least 1")`. The CLI guards it first (`adapters/cli/main.py:819-820`, `if args.max_nodes < 1: return fail(...)`); the MCP adapter does not — `analyze_structure` accepts `max_nodes: int = DEFAULT_MAX_NODES` off the wire (`adapters/mcp/server.py:618`) and hands it through `_operation_diagram` unchecked. Measured:

    === max_nodes=0
    ValueError max_nodes must be at least 1

That exception leaves the tool as an unhandled `ValueError` rather than the repo's own agent-facing `AtlasError`, which every other refusal on this surface uses (`server.py:320, 385`).

The same asymmetry covers `members`, which no adapter passes but which produces fabricated honesty numbers when negative (`community.members[:members]` with `omitted=max(0, community.size - members)`):

    members=-1 rows: [(2, ('a.py',), 3), (1, (), 2), (1, (), 2)]

A community of one file listing zero members and claiming two were omitted is the module's stated contract inverted. The CLI blocks it (`main.py:799-800`); a library caller and any future adapter do not.

Failure scenario: an MCP client that computes `max_nodes` from a token budget sends 0 and gets a transport-level error instead of an answer; a second front door (or the same one after a refactor) reaches `communities(members=-1)` and gets an elision count invented out of a negative slice.

Recommendation: validate at the service entry, where both adapters and library callers cross — reject `max_nodes < 1`, `limit < 0`, `members < 0` with `AtlasError` (or clamp and say so), and delete the duplicated CLI guards so the rule has one home. Guard on the invariant ("a bound is a non-negative count"), not on which adapter happens to check.

### B19-M2 — `resolution` is coerced, never parsed: negative, infinite and NaN values produce scores the report presents as modularity

`graph_service.py:197` and `graph_service.py:241`:

    setting = communities.DEFAULT_RESOLUTION if resolution is None else float(resolution)

`float()` is a coercion, not a boundary parse. `core/communities.detect_communities` validates nothing either, and `CommunityPartition.modularity` is documented (`communities.py:117-122`) as the number a caller uses to tell "this repository has structure (roughly 0.3 and up)" from noise. Measured on the same 14-file repository:

    0.0 -> communities 13 modularity 1.0
    -5.0 -> communities 13 modularity 6.0
    inf -> communities 14 modularity nan
    nan -> communities 14 modularity nan

`resolution` is a wire parameter on `analyze_structure` (`server.py:616`, `resolution: float | None = None`) and pydantic's float allows inf/NaN by default, so all four rows are reachable from a client. `render.CommunityReport.as_dict()` does `round(self.modularity, 6)`, and `json.dumps` of a NaN emits the bare token `NaN` — not valid JSON for a strict parser on the other side of the CLI's `--json`.

Failure scenario: an agent experimenting with `resolution` to get a coarser rollup passes a negative value, reads `modularity 6.0` against a documented 0-to-1 scale, and concludes the repository is extraordinarily well-partitioned; or a NaN modularity lands in a JSON response that the consuming parser rejects wholesale, losing the entire answer rather than one field.

Recommendation: parse rather than coerce at this boundary — accept a finite `resolution > 0`, refuse anything else with `AtlasError` naming the accepted range. One check in `graph_service`, since `communities()` and `diagram()` both take the knob and both call `float()` today.

### B19-M3 — `test_a_section_limit_is_reported_rather_than_silent` cannot fail

`tests/unit/test_graph_service.py:130-136`:

    explained = graphs.explain(repo, "helper", limit=1)
    group = explained.fan_in[0]
    assert len(group.rows) == 1
    assert group.total >= 1
    rendered = render.render_explanation(explained)
    assert "more at this tier" in rendered or group.omitted == 0

Measured against that fixture: `tier same_file total 1 rows 1 omitted 0`. The right-hand disjunct is true, so the assertion passes whether or not the renderer announces anything. `assert group.total >= 1` is likewise satisfied by any non-empty group. Delete the elision line from `render._render_tiers` and this test stays green — the revert test fails.

Failure scenario: the section-elision marker (the mechanism B19-H1 shows is missing from the imports block) regresses in the tier block too, and the test named for exactly that behavior does not notice.

Recommendation: build a fixture where one tier genuinely overflows the limit (several same-file callers), then assert `group.omitted == expected` and assert the rendered `... N more at this tier` line unconditionally. No disjunction.

### B19-M4 — the ambiguous-focus branch is the only unexecuted code and is the branch a caller is most likely to hit

`graph_service.py:552-554`, the two uncovered statements:

    if len(matches) > 1:
        listed = ", ".join(matches)
        return _Focus(node="", message=f"{entry} matches several modules: {listed}")

`focus_paths` returns every path sharing a module stem, so `focus="server"` in a repository with `adapters/mcp/server.py` and `adapters/http/server.py` lands here. The message is the only thing standing between that and mermaid's `ValueError("focus is not a module in this graph")`, and via the CLI it becomes `fail(view.message)` — an exit code path with no test.

Recommendation: one test with two same-stem modules asserting the message lists both, plus its CLI/MCP counterpart. Cheap, and it pins the refusal the sibling `_endpoint` ambiguity branch already has tests for.

## Low

### B19-L1 — the exhausted-path message prescribes a remedy one of the two front doors does not offer

`graph_service.py:499-503`:

    f"no path from {found.source} to {found.target} within the search bound "
    f"({found.visited} nodes visited); raise the bound or pick a nearer endpoint"

`max_visited` is a CLI flag (`main.py:332`) but is not a parameter of `analyze_structure` — `_operation_path` (`server.py:381-390`) calls `graphs.path(...)` without it. An MCP agent reading "raise the bound" has no way to raise it and will either retry identically or hallucinate an argument. Either expose the knob on the wire or make the message name the remedy that surface actually has.

### B19-L2 — the `graph` module is shadowed by a parameter in a file that also calls it

`graph_service.py:53` imports the module (`from agentless_mcp.core import communities, graph, ...`) and `graph_service.py:281-285` calls `graph.build_graph` / `graph.personalized_pagerank`. `_imports` (`graph_service.py:430-436`) then binds `graph: resolve.ResolvedGraph` as a parameter, and `_Ranked.graph` (line 103) reuses the name as a field. No bug today, because `_imports` never reaches for the module; the trap is that the next edit inside it that types `graph.` gets a `ResolvedGraph`. Rename the parameter (`resolved`) to match how `_resolve`/`_endpoint` already spell it.

### B19-L3 — `rank_candidates` is public with no caller outside this module

`graph_service.py:318`. `grep -rn "rank_candidates" src/ tests/` returns hits in `graph_service.py` only. Its two users are `explain` (line 135) and `_endpoint` (line 370), both in this file, while the genuinely shared helpers this module imports — `focus_paths`, `symbol_card` — are public precisely because other modules use them. Make it `_rank_candidates` unless a second consumer is imminent; the long docstring justifying the ordering stays either way.

### B19-L4 — the diagram's node selection is computed twice per call

`graph_service.py:248-255` calls `mermaid.selected_nodes(...)` and then `mermaid.render_flowchart(...)`, which internally repeats `_candidates` + `_bounded` (`mermaid.py:192-193`). For a focused diagram that is two BFS traversals of the undirected adjacency plus two full sorts of the candidate set on top of a per-call repository scan. `selected_nodes` exists so the caller need not parse its own output, which is right; the fix for the duplication is for `render_flowchart` to accept (or return) the selection rather than for the service to stop asking. Note this is also the cleanest place to fix B19-H2.

### B19-L5 — `max_nodes` is a caller's knob while `max_edges` is a fixed constant behind it

`graph_service.py:247` builds `mermaid.DiagramOptions(max_nodes=max_nodes, focus=...)` and leaves `max_edges` at its default 40. A caller who raises `max_nodes` to 200 to see a large repository crosses the edge bound and gets *every* reference edge dropped (`mermaid.py:406-416`), announced only inside a `%%` comment in the text — `DiagramView` has no field for it and `as_dict()` reports none. The text is honest; the structured view is silent. Either scale the edge bound with the node bound or expose it, and consider carrying the dropped-edge count on `DiagramView` alongside `elided`.

### B19-L6 — an empty repository renders as a bare `flowchart LR` with no message

`graph_service.py:256-263` returns `text="flowchart LR\n"`, `nodes=0`, `elided=0`, `message=""` when the graph has no nodes. `render_diagram` fences it, because `view.text` is non-empty. Every sibling view answers this case in words (`render_cycles` → "no import cycles", `render_map` → "no ranked files: nothing in this repository parsed into symbols"). One `if not ranked.graph.nodes` returning `_empty_diagram` with a message would match the file's own convention.

## Cross-block observations

- **The file-graph pipeline has two homes.** `graph_service._ranked` (lines 272-287) reproduces `map_service`'s `scan_repo` → `build_ref_index` → `build_graph(stoplist=ctx.config.stoplist)` → `personalized_pagerank` sequence (`map_service.py:125-134`), differing only in the seed vector. Communities and diagrams are therefore ranked by a hand-mirrored copy of the map's construction; a change to how the map weights or stoplists edges will silently not reach them. Candidate for one `build_file_graph(ctx, extractor, seeds=None)` owned by whichever block owns `map_service` — worth flagging to the synthesis pass rather than fixing inside B19.
- **Sibling-service imports check out, and the phase-1 hint over-reads them.** `graph_service` imports `map_service.focus_paths` and `symbol_service.symbol_card`, but both are module-level pure functions, neither sibling imports `graph_service` (verified by grep), so the dependency graph stays a DAG and the import-linter layers contract (`pyproject.toml:262-266`) constrains only cross-layer edges. There is no duplicated context construction on this path: each public method builds its own `_Resolved`/`_Ranked` and nothing is built twice per call. The real smell is milder — two shared application helpers live inside service modules rather than in a shared one — and it should stay unfixed until a third consumer appears.
- **Bound validation for `analyze_structure` lives only in the CLI.** B19-M1 is written against `graph_service` because that is where the fix belongs, but the missing half is in the MCP adapter block: `analyze_structure` accepts `max_nodes`, `limit` and `resolution` off the wire with no range check, while the CLI checks all three. Whichever block owns `adapters/mcp/server.py` should be told that its input validation is currently borrowed from a sibling adapter.
- **`render.DiagramView.caveat` states a cause it has no evidence for.** The wording "the N module(s) the rank bound left out" is in `render.py:514-517`, one block away from the service that supplies `N`. Fixing B19-H2 properly means the render block gains a field (or the caveat loses its causal claim); the two changes have to land together.
- **`json.dumps` of a NaN modularity is invalid JSON** (B19-M2). If any block owns the CLI's `--json` emission or the envelope's `wrap_json`, a global `allow_nan=False` there would turn a silently-malformed response into a loud failure and would cover more than this one field.
