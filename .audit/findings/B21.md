## High

### B21-H1 — an infrastructure error in a candidate's test run is laundered into a rankable verdict, and the run says nothing about it
`src/agentless_mcp/application/validate_service.py:491-509`, `:292-294`, `:310-344`

```python
regression_run = sandbox.run_command(tree, request.test_cmd, timeout=request.timeout)
...
regression=Verdict.of(regression_run),
```

`RunStatus.ERROR` means the command *never started* — `sandbox.run_command` returns it for a spawn failure (`sandbox.py:256-259`: `OSError` from `Popen`, e.g. `EAGAIN` under a high `--jobs`, `ENOMEM`, or a patch that renamed the runner). `Verdict.of` maps it straight to `Verdict.ERROR`, which then travels to the JSON Lines record as `"regression": "error"`, and `_vote_candidate` (`:625`) reduces it to `regression_passed=False`. The vote cannot distinguish it from a patch that ran and broke tests.

The module is otherwise scrupulous about exactly this distinction — `Verdict`'s own docstring (`:119-122`) says `not_evaluated` "is deliberately not ``failed``: nothing was measured, and a report that says otherwise is inventing evidence" — but that care stops at the apply step and is never applied to the run step.

Failure scenario, executed against the real `vote` module:

```
$ # three candidates, all regression="error" (nothing ran), repro_valid=False
4. applied applied cleanly (nothing passed the regression suite) winner: c0
```

The vote reports tier `applied`, tier detail "applied cleanly (nothing passed the regression suite)", and crowns `c0` as winner. Nothing was measured on any of them. `ValidateReport.any_passed` is False, `summary_line()` prints "baseline ok; 3 of 3 candidates applied, 0 passed the regression suite", and `warnings()` (`:310-344`) has no branch for this at all — its four branches are flaky baseline, unverified baseline, `does_not_reproduce` and `unrunnable`, all baseline-side. An agent following the documented pipeline reads "here is the best of what did not break anything" when in fact nothing was run.

Recommendation: count `Verdict.ERROR` (and, if you want the harder line, `Verdict.TIMEOUT`) verdicts in `ValidateReport` and emit a warning naming the candidates — "N of M candidates were never measured: the test command could not be started". Then carry it across the format: `_vote_candidate` should exclude an `error` candidate from the ladder the way an unapplied one is excluded, rather than ranking it in the apply-ok tier. `error` at candidate level is especially loud evidence because the *baseline already proved the same command starts in a worktree of the same repo*.

### B21-H2 — `load_verdicts` accepts a corrupt verdict value and silently demotes the ladder, which is the exact failure its docstring says it prevents
`src/agentless_mcp/application/validate_service.py:620-627`

```python
applied=_string(apply_field, "status", position) == ApplyStatus.OK.value,
...
regression_passed=_string(record, "regression", position) == Verdict.PASSED.value,
reproduction_passed=reproduction == Verdict.PASSED.value,
```

against the function's own contract at `:571-576`:

> Strict on purpose, and the only reader of this format. Every field the vote depends on must be present and of the right type: a document whose ``repro_valid`` went missing must not read as ``False`` and quietly demote the ladder by one rung.

`repro_valid` is indeed strict (`_boolean`), and `baseline` is coerced through the enum. The three fields that decide each candidate's rung are not: any string that is not exactly `"passed"` / `"ok"` reads as False. Measured:

```
2.  regression="pased"      -> VoteCandidate(..., regression_passed=False)   # no error
2b. apply.status="applied"  -> VoteCandidate(..., applied=False)             # no error
```

Failure scenario: a future rename of an enum value (say `passed` -> `pass`, or `ok` -> `applied`), or a verdicts file produced by a different version of the tool, silently turns every winning candidate into a losing one. The ladder falls to `applied` or `none`, the CLI exits 1, and there is no error anywhere — the run just reports that nothing worked. This is the Boundary-integrity rule failing in the one function whose whole job is the boundary.

Recommendation: parse these fields into their enums (`Verdict(...)`, `ApplyStatus(...)`) inside a try that raises `AtlasError` with the line number, and derive the booleans from the typed values. That also gives B21-H1 the `error` value it needs to act on.

### B21-H3 — `load_verdicts` leaks a raw `ValueError` past the typed-error boundary, crashing the CLI with a traceback
`src/agentless_mcp/application/validate_service.py:595`

```python
baseline=BaselineStatus(_string(header, "baseline", 0)),
```

Every other refusal in this function raises `AtlasError` with a line number. This one calls the enum constructor directly. Measured:

```
1. ValueError 'green' is not a valid BaselineStatus
```

`_cmd_vote` (`cli/main.py:1059`) calls `load_verdicts` outside any try, and `run` (`cli/main.py:127-130`) catches only `AtlasError`; `cli_main` (`bootstrap.py:110-127`) catches only `AtlasError` around counter selection. Failure scenario: `agentless-mcp vote --verdicts <file>` on a hand-edited, truncated-and-repaired, or version-skewed document prints a Python traceback and exits 1 through the interpreter rather than the tool's own exit-code mapping — the difference between "your file is wrong at line 1" and "the tool is broken".

Recommendation: wrap the two enum coercions (`BaselineStatus` here, and the `Verdict`/`ApplyStatus` ones B21-H2 recommends adding) in a small `_enum(record, field, position, cls)` helper that raises `AtlasError` naming the field, the bad value and the line.

## Medium

### B21-M1 — an UNVERIFIED run tells the vote that every candidate "did not apply", which is false
`src/agentless_mcp/application/validate_service.py:815-826`, with `ApplyStatus` at `:103-111`

```python
def _not_evaluated(candidate: Candidate) -> CandidateVerdict:
    """Return the verdict every candidate gets when the baseline is unverified."""
    return CandidateVerdict(
        ...
        apply_status=ApplyStatus.FAILED,
        apply_reasons=("not evaluated: the baseline test run was UNVERIFIED",),
```

`ApplyStatus` has only `OK` and `FAILED` — there is no `not_evaluated` member, although `Verdict` has one for precisely this reason. The honest reason survives in `apply.reasons`, but `_vote_candidate` (`:603-627`) never reads `reasons`, so `vote._exclusion` reports the generic string. Measured on a two-candidate unverified document:

```
5. none (('c0', 'the patch did not apply'), ('c1', 'the patch did not apply'))
```

No patch was ever attempted. `_cmd_vote` does print a separate UNVERIFIED note (`cli/main.py:1070-1074`), so a human at the CLI is covered; a caller consuming `VoteReport.as_dict()`'s `excluded` list is told something untrue about each candidate. Recommendation: add `ApplyStatus.NOT_EVALUATED` and carry `apply.reasons[0]` into the exclusion reason, so the vote quotes the real cause instead of inventing one.

### B21-M2 — one bad candidate aborts the whole run and discards every verdict already computed
`src/agentless_mcp/application/validate_service.py:452-484`

```python
scoped = resolve_repo(tree, None)
try:
    parsed = load_edits(candidate.text)
except AtlasError as error:
    return _apply_failed(candidate, (str(error),), started)
...
normalized = self._patches.normalize(parsed.edits, scoped)
```

The `try` covers `load_edits` only. `normalize` and `apply` call `PatchService._canonical` (`patch_service.py:372-387`), whose `contained_path` refuses a path outside the root by raising, and `apply(in_place=True)` calls `_require_clean` (`patch_service.py:352-366`), which raises when `dirty_count` is 0 or `None`. None of these is caught here, so they propagate out of `_evaluate`, out of `validate`, and terminate the command.

For containment this is deliberate — the comment at `:453-457` argues it is "a refused invocation" — but the cost is not stated and is not small: candidates are model-sampled, evaluated one full test-suite run each, and the results live only in memory until `report.jsonl()` at the very end. A batch of twenty candidates that has already spent forty minutes loses all of it because candidate seventeen wrote `### ../setup.py`. Every other patch defect (missing file, non-matching search block, no edits, unparsable JSON) is a per-candidate `apply_reasons` line; path escape alone is fatal to the batch.

Worse, `_require_clean`'s message is written for a CLI flag the caller never passed. If `gitinfo.snapshot` cannot read the fresh worktree's status, `agentless-mcp validate` dies with:

> `--in-place refused: this repository's dirty-file count could not be read, so a clean tree cannot be proven. Drop --in-place to apply in a worktree.`

Recommendation: catch `SecurityRefusal` per candidate and record it as an apply failure with the refusal text (the candidate is refused; the *invocation* was fine — the guard should key on "this patch escapes the root", not on "somebody must be punished for it"). If the whole-run abort is genuinely wanted, pin it with a test, since nothing does today. Separately, `_require_clean` should not be reachable from `validate` at all — see B21-M6.

### B21-M3 — `as_vote_candidate` is dead code and a second home for the eligibility rule
`src/agentless_mcp/application/validate_service.py:181-190`, `:348-355`

```python
def as_vote_candidate(self) -> VoteCandidate:
    """Reduce this verdict to what the ladder and the cluster vote need."""
```

Zero callers in `src/` and zero in `tests/` (line 183 is in the uncovered set). The pipeline always goes `validate -> JSONL file -> load_verdicts -> vote`, so the in-memory reduction is never used — and it is a duplicate of `_vote_candidate` (`:603-627`), which does the same mapping from strings. Two implementations of one rule that no test compares. Same block: `LoadedVerdicts.repro_cmd` (`:354`) is parsed strictly and never read by any consumer (`cli/main.py` reads `candidates`, `repro_valid`, `test_cmd`, `baseline`).

Justify-its-existence test: deleting `as_vote_candidate` removes a divergence risk and breaks nothing. Recommendation: delete it, or delete `_vote_candidate` and make the reader build `CandidateVerdict`s and call this — one home either way.

### B21-M4 — the module docstring denies a config-file lookup the shipped CLI performs
`src/agentless_mcp/application/validate_service.py:29-33`

```
**The commands come only from the invocation.** Nothing here reads a test
command out of the repository under analysis -- no config file lookup, no
``Makefile`` sniffing, no ``package.json`` scripts. The repository is the
thing being judged; letting it nominate its own judge is the injection path
this whole package is shaped to avoid.
```

`_cmd_validate` (`cli/main.py:1004`): `test_cmd = args.test_cmd if args.test_cmd is not None else ctx.config.test_cmd`, where `ctx.config` is `.agentless-mcp.json` read from the repository under analysis (`core/projectconfig.py:38,62`). The repository does nominate its own judge, and the command it names is executed under the invoking user's account. The behavior is a documented product decision (README:52, `docs/agent-guide.md:681`) and the CLI prints the command before running it, so this is a stale comment rather than a hidden backdoor — but it is the strongest security claim in the file and it is false. The next agent reading this module will generate against it.

Recommendation: narrow the claim to what the service actually guarantees ("this service takes its commands from `ValidateRequest`; the CLI's one config fallback is named and printed before the run") and point at the CLI. Do not leave the "shaped to avoid" sentence standing.

### B21-M5 — `--jobs > 1` drives a shared, mutable tree-sitter `Parser` from several threads
`src/agentless_mcp/application/validate_service.py:434-436`

```python
if request.jobs > 1 and len(candidates) > 1:
    with ThreadPoolExecutor(max_workers=request.jobs) as pool:
        verdicts = list(pool.map(evaluate, candidates))
```

This is the only concurrency in `src/` (`grep ThreadPoolExecutor|threading.` finds this line and `sandbox._WORKTREE_LOCK`). Each worker calls `PatchService.normalize` -> `normalize.file_key` -> `_parser_for` -> `grammars.get_parser(name)`, which is `@cache`-decorated (`core/grammars.py:196-199`) and therefore hands every thread **the same** `Parser` object. tree-sitter's C API does not permit one `TSParser` to be used from two threads at once, and py-tree-sitter documents no thread-safety guarantee.

Measured on this machine, tree-sitter 0.26.0: two threads parsing a 20k-function file gave `serial=0.385s parallel=0.386s speedup=1.00x` — the GIL is held across `parse`, so the race is **latent today, not active**. It is load-bearing on an implementation detail nobody wrote down, and `requires-python = ">=3.10"` will meet a free-threaded interpreter before this code is next touched. A corrupt parse would not crash loudly; it would change the equivalence key and put a candidate in the wrong cluster.

Recommendation: make the parser cache thread-local (or hand out a fresh `Parser` per call — construction is cheap next to a test-suite run), and state the concurrency contract in `grammars.get_parser`'s docstring. Calibration: arguable either way today, filed Medium rather than High because the measurement shows no parallel execution.

### B21-M6 — validate pays a `git status` and a discarded `git diff` per candidate, and re-applies the whole patch twice
`src/agentless_mcp/application/validate_service.py:458`, `:478-484`; `patch_service.py:294-300`, `:339-350`

```python
normalized = self._patches.normalize(parsed.edits, scoped)
...
applied = self._patches.apply(parsed.edits, scoped, in_place=True)
```

`normalize` reads every target file and runs `apply_edits` in memory; `apply(in_place=True)` reads them again, runs `apply_edits` again, writes, then computes `sandbox.diff(base)` — a `git diff` subprocess over the whole worktree — and returns it inside `ApplyReport.diff`, which `_evaluate` never reads. `resolve_repo(tree, None)` at `:458` additionally runs a full `gitinfo.snapshot` (and a `projectconfig.load`) on a worktree the service created two lines earlier and already knows everything about; the snapshot exists only so `_require_clean` can be satisfied by it.

Because `normalize` and `apply` read the same files from the same directory with nothing in between, `applied.ok` cannot be false when `normalized.ok` is true — which is why line 484 is in the uncovered set and cannot be covered without patching the filesystem underneath a running candidate.

Recommendation: `validate` wants "apply these edits to this tree and give me the key", not the diff-producing public API. Either give `PatchService` a write path that skips the diff, or have `_evaluate` write `normalized.result.new_contents` itself and drop the second apply, the `git diff`, and the `_require_clean`/`resolve_repo` round trip with it. That also removes the misleading `--in-place refused` failure mode in B21-M2.

### B21-M7 — two verdicts documents concatenated are silently merged into one ranking
`src/agentless_mcp/application/validate_service.py:582-600`

```python
header = records[0]
...
candidates = tuple(
    _vote_candidate(record, position)
    for position, record in enumerate(records[1:], start=1)
    if _string(record, RECORD_KEY, position) == RECORD_CANDIDATE
)
```

Only the first `run` record is read; any later one is skipped by the `record == "candidate"` filter, and candidate ids are never checked for uniqueness. Measured on `run+cand(c0,passed) ++ run(repro_valid=False)+cand(c0,failed)`:

```
3.  2 candidates, repro_valid=True, ids ['c0', 'c0']
3b. tier regression+reproduction, winner c0
```

Two runs' candidates ranked together under the first run's `repro_valid`, with a duplicated id. `load_candidates` goes to real trouble to refuse duplicate ids at the input side (`:539-548`: "the ids would collide in the report and one candidate's verdict would appear to be the other's") — the reader does not enforce the same invariant on the way back in, and duplicated ids inflate a cluster's size, which *is* the vote. Recommendation: refuse a second `run` record, refuse an unknown `record` value, and refuse a repeated candidate id, each with its line number.

## Low

### B21-L1 — no aggregate bound on a validation run
`src/agentless_mcp/application/validate_service.py:393-397`, `:434-436`; `cli/main.py:1398-1406`

`timeout` bounds one command. A run costs up to `repeat_baseline + 1 + candidates x 2` command executions, and `_validate_bounds` checks only that each flag is positive — no ceiling on `--jobs` (each job holds a full worktree checkout, so disk is `jobs x repo size`) and none on `--repeat-baseline`. Default `--timeout 300` with 20 candidates and a reproduction command is 200 minutes of worst-case wall clock with no progress output and no overall deadline. Recommendation: cap `--jobs` at something like `os.cpu_count()` with a note when the request is clamped, and either offer a whole-run budget or state the worst case in `--help`.

### B21-L2 — a reproduction command that times out on the baseline counts as reproducing the bug
`src/agentless_mcp/application/validate_service.py:768-781`

```python
if run.status is RunStatus.ERROR:
    return ReproVerdict.UNRUNNABLE
return ReproVerdict.REPRODUCES
```

`TIMEOUT` falls into `REPRODUCES`. The docstring argues "a failure or a timeout is the bug showing itself", which is fair for a hang that *is* the bug and wrong for a repro script that waits on something absent — and the second case then costs a full `timeout` per candidate, silently doubling the run's worst case. Recommendation: keep the verdict but warn on it, the way `does_not_reproduce` and `unrunnable` are warned on in `warnings()`.

### B21-L3 — `_optional_string`'s sentinel does nothing
`src/agentless_mcp/application/validate_service.py:652-660`

```python
value = record.get(field, ...)
if value is None:
    return None
if not isinstance(value, str):
```

A missing field yields `Ellipsis`, which falls through to the `isinstance` check and raises "must be a string or null" — the same as any other wrong type. The sentinel buys nothing over `record.get(field)`, except that a genuinely absent field is reported as a type error rather than as missing. Recommendation: either drop the sentinel or give the missing case its own message.

### B21-L4 — the file holds four separable concerns at 826 lines, and `vote` pays for all of them
`src/agentless_mcp/application/validate_service.py:517-561` (candidate directory loading), `:569-678` (the JSON Lines reader and five typed-field helpers), `:358-509` (the orchestrator), `:140-355` (the value types)

The verdicts format is a contract *between two CLI commands* — the module docstring says so at `:35-38` — but it lives inside the service that produces it, so `_cmd_vote` (`cli/main.py:67`) imports `load_verdicts` from a module that transitively pulls in `ThreadPoolExecutor`, `sandbox`, `PatchService` and the tree-sitter extractor in order to parse a JSON file. Recommendation: lift the record types plus `load_verdicts` into `application/verdicts.py`; `validate_service` imports it to write, `vote` imports it to read, and the read side stops depending on the entire write stack. That is also where B21-H2/H3's typed parsing belongs, and it puts the file back under the block target.

## Cross-block observations

* **The infrastructure-vs-verdict blur is a two-block defect.** B21-H1 originates here (`Verdict.of` at `:134-137`) but is only harmful because `core/vote.py:232-238` excludes on `applied` and `equivalence_key` alone — an `error` candidate is eligible for the `applied` tier. Whichever block owns `vote` should be asked the same question: should a candidate that was never measured be rankable? The fix is cheapest as a new exclusion reason there plus a typed `regression` value here.
* **`ApplyStatus` has no `not_evaluated` member while `Verdict` does** (B21-M1). The vote's exclusion vocabulary (`core/vote.py:_exclusion`) and this enum have to change together.
* **`grammars.get_parser` is `@cache`d and shared** (`core/grammars.py:196-199`). Whatever block owns `core/grammars` should carry the thread-safety note from B21-M5 — the cache is fine for a single-threaded caller and this block is the only caller that is not one.
* **`PatchService.apply(in_place=True)` is shaped for the CLI, not for validate** (B21-M6). Its `_require_clean` message names `--in-place`, a flag the validate caller never passed, and its unconditional `sandbox.diff` is dead weight on this path. The patch-service block should be asked for a diff-free write entry point rather than this block working around it.
* **`test_cmd` from `.agentless-mcp.json`** (B21-M4) is the one place the repository under analysis influences what gets executed. It is documented in README/agent-guide and printed at runtime, but whichever block owns `core/projectconfig` should confirm the value is validated (it reaches `shlex.split` and `Popen` with no shell, `sandbox.py:236-255`, so injection is bounded to "runs the argv it names" — which is still arbitrary execution by design).
* **`resolve_repo(tree, None)` passes `allowlist=None`** (`:458`), skipping the authorisation branch in `repo_context.py:73-74`. Correct here — the path is a worktree this service just created, not caller input — but it is the same call shape the MCP surface uses with a real allowlist, so any block auditing `resolve_repo` should know one caller deliberately opts out.
