## High

### B14-H1 — A killed or timed-out `git worktree add` leaves a locked worktree record inside the analysed repository, forever
`src/agentless_mcp/core/sandbox.py:184-191`

```python
    path = scratch / f"wt-{uuid.uuid4().hex}"
    with _WORKTREE_LOCK:
        run_git(top, ["worktree", "add", "--detach", str(path), "HEAD"])
    try:
        yield path / resolved.relative_to(top)
    finally:
        with _WORKTREE_LOCK:
            _release(top, path)
```

The `try` starts *after* the add. Every failure of the add itself — the 120 s `GIT_TIMEOUT_SECONDS` expiring on a large checkout (`subprocess.run` SIGKILLs git on timeout), a Ctrl-C reaching the foreground process group, a disk filling mid-checkout — leaves whatever git had already created with no cleanup at all.

Measured, not inferred. In a throwaway repo (766 MB checkout), killing `git worktree add --detach ../wt2 HEAD` after 80 ms:

```
killed mid-checkout
--- worktree list ---
.../repo  6cca40d [main]
.../wt2   6cca40d (detached HEAD) locked
--- admin records ---     wt2
--- dir ---               340M ../wt2
```

and after deleting the directory and running the same `git worktree prune` that `_release` runs:

```
--- after prune (dir deleted) ---
.../wt2  6cca40d (detached HEAD) locked
wt2
initializing
```

`git worktree prune` **skips locked worktrees**, so the record is permanent. Two guarantees fail at once: the module docstring's "Removal happens in a `finally`, so a patch that raises mid-apply still leaves nothing behind" (sandbox.py:20-22), and README:107-110 "no cache or scratch state is written inside the repository under analysis". Recovery is manual (`git worktree unlock` + `prune`, or `rm -rf .git/worktrees/<id>`), and each failed attempt also strands a partially populated multi-hundred-MB directory under `$XDG_CACHE_HOME/agentless-mcp/worktrees` that nothing in the package ever sweeps.

Failure scenario: an agent runs `validate` against a monorepo whose checkout exceeds 120 s; every retry adds one permanent phantom entry to the user's `git worktree list` and one orphaned scratch tree to their cache.

Recommendation: wrap the add in its own `try/except`, and on any failure run `worktree remove --force` (which does handle a locked record) plus `shutil.rmtree` on `path` before re-raising — i.e. move the release into a scope that also covers creation. Separately, either raise `GIT_TIMEOUT_SECONDS` for `worktree add` specifically or accept that this path must self-clean; a bound that can be hit is not an excuse for leaving state behind. A test that stubs `run_git` to raise on `worktree add` and asserts the repository's `.git/worktrees` is unchanged pins it.

### B14-H2 — Captured output is unbounded on disk; `DEFAULT_MAX_CAPTURE` bounds only what is read back
`src/agentless_mcp/core/sandbox.py:87-89, 244-255, 364-380`

```python
# The default cap on captured output, per stream. The tail is what is kept:
DEFAULT_MAX_CAPTURE = 100_000
...
    with tempfile.TemporaryFile() as out, tempfile.TemporaryFile() as err:
```

The comment says "cap on captured output"; the code caps only the tail `_tail` reads back. The child writes into an unbounded `tempfile.TemporaryFile` in `TMPDIR` for the whole `timeout` window (default 300 s, and the CLI only checks `--timeout > 0`, `main.py:1400`, so there is no ceiling). A test suite with a runaway `print` loop, or one dumping a binary artefact to stdout, writes at disk/tmpfs speed until the bound expires; on the many systems where `/tmp` is tmpfs that is RAM exhaustion, and `--jobs N` multiplies it by `2N` concurrent streams.

This is the one bound the module's own thesis ("The bound is hard ... a hung test run is the case this machinery exists to catch") does not actually provide. The file-over-pipe choice is right — the missing half is a size bound to go with the time bound.

Failure scenario: validating candidates for a bug in an output-heavy suite fills `/tmp`, taking down unrelated processes on the machine, and the run reports a timeout with no indication of why the box fell over.

Recommendation: bound the writer, not just the reader — set `RLIMIT_FSIZE` on the child (POSIX `preexec_fn`/`resource`), or have the wait loop truncate/stop the process when the temp file passes a multiple of `max_capture`. Whichever is chosen, fix the comment on line 87 so it describes the tail, not a cap that does not exist.

## Medium

### B14-M1 — `git worktree prune` is a repository-global mutation used as per-worktree cleanup, and the lock protecting it is process-local
`src/agentless_mcp/core/sandbox.py:92-97, 419-430`

```python
# ``git worktree add`` and ``git worktree prune`` race each other: prune walks
# the repository's worktree records and can remove one that a concurrent add
# has created but not yet populated. Serialising the bookkeeping within this
# process is what lets `validate --jobs N` give every candidate its own
# worktree.
_WORKTREE_LOCK = threading.Lock()
```

The comment names the race precisely and then guards it with a `threading.Lock`, which cannot see another process. Two `agentless-mcp validate` invocations on the same repository — or a CLI run alongside anything else that uses this module — reproduce exactly the described race: process A's `_release` prune can drop process B's record while B's `worktree add` is still populating it, leaving B with a working directory git no longer knows about and a `worktree remove` that fails. This is the global rule "guards key on the invariant, not a proxy" failing: the invariant is exclusive access to the repository's worktree bookkeeping, and a per-process mutex is a proxy for it.

The prune is also unnecessary in the happy path: `worktree remove --force` already deletes the record, which `test_the_repository_forgets_the_worktree_afterwards` demonstrates. It only matters after the `rmtree` fallback at line 425.

Recommendation: reach for the repository-scoped `util/filelock` primitive the tag cache already uses (`core/cache.py` single-writer discipline) instead of `threading.Lock`, and run `prune` only on the fallback branch where the record is actually known to be stale.

### B14-M2 — `git worktree add` executes the analysed repository's hooks and honours its config, contradicting the module's stated invariant
`src/agentless_mcp/core/sandbox.py:26-28, 186` (versus `194-202`)

```python
Every git call is a fixed argv with a timeout and no shell. Nothing derived
from repository content or from patch text reaches it.
```

The argv is fixed, but git is not a pure function of its argv: it reads the target repository's config and runs its hooks. Verified:

```
$ printf '#!/bin/sh\necho PWNED > ../pwned.txt\n' > .git/hooks/post-checkout; chmod +x ...
$ git worktree add --detach ../hookwt HEAD; echo exit=$?
exit=0
$ cat ../pwned.txt
PWNED
```

Arbitrary code from the repository under analysis runs with the user's privileges during worktree creation — before any test command is involved, and on the `patch apply` path too (`application/patch_service.py:299`), which a reader of the "read-only posture" section would not expect. `core.fsmonitor` is the same class of hazard.

The inconsistency is what makes this a finding rather than a platform fact: `diff()` twelve lines later explicitly neutralises `color.diff` and `diff.external` because "a worktree reads the repository's own configuration", so the author knew about config-driven git behaviour and applied the hardening to exactly one call.

Recommendation: pass `-c core.hooksPath=/dev/null -c core.fsmonitor=` on the `worktree add` (and document the residual, since `clone` does not transfer hooks but locally installed ones — pre-commit, committed `core.hooksPath` setups — are common), or amend the docstring and the README security section to state that worktree creation runs the target repo's hooks.

### B14-M3 — `run_command`'s "caller-supplied command" is routinely the analysed repository's own config value
`src/agentless_mcp/core/sandbox.py:205-234`, with `adapters/cli/main.py:1005` and `core/projectconfig.py:38,62`

```python
def run_command(...):
    """Run one caller-supplied command in ``cwd`` under a hard time bound.
```

`test_cmd = args.test_cmd if args.test_cmd is not None else ctx.config.test_cmd`, and `ctx.config` is `.agentless-mcp.json` read out of the repository being validated. So the argv this function execs can be chosen by the author of the repo under analysis, executed against a worktree of that same repo, with the parent process's full environment. The only mitigation is an advisory `note()` on stderr (main.py:1012-1019), which an agent driving the CLI will not act on.

The docstring's framing matters because it is what the next reader reasons from: "caller-supplied" reads as "the human typed it". The MCP surface exposing read tools only is the thing that keeps this from being High.

Recommendation: say plainly in the docstring that the command may originate from the repository's project config, and consider requiring an explicit opt-in flag (`--allow-repo-test-cmd`) before executing a command that came from the analysed tree rather than from the invocation.

### B14-M4 — `shlex.split` is POSIX-only, so Windows commands are silently mangled on a platform this module explicitly branches for
`src/agentless_mcp/core/sandbox.py:236`

```python
        argv = shlex.split(cmd)
```

```
>>> shlex.split(r'C:\Python\python.exe -m pytest')
['C:Pythonpython.exe', '-m', 'pytest']
```

`shlex.split` defaults to `posix=True`, which treats backslash as an escape. The module carries a dedicated Windows path (`_group_kwargs`, `_kill_leader`) and README:74-104 enumerates the Windows caveats — the argv split is not among them, so a Windows user reading that list would conclude command execution works. In the common case the mangled path fails to start and surfaces as `RunStatus.ERROR`; in the quoting cases it silently changes what runs.

Recommendation: on the Windows flavour, use `shlex.split(cmd, posix=False)` (or `subprocess.list2cmdline` semantics), and add the caveat to the README list next to the process-group one.

### B14-M5 — The vote ladder cannot see whether the baseline was verified, and the report does not carry it
`src/agentless_mcp/core/vote.py:156-184, 130-141`

`rank()` takes only `repro_valid`. Nothing about the baseline reaches it, and `VoteReport.as_dict()` emits `tier`, `repro_valid`, `considered`, `survived`, `winner`, `clusters`, `excluded` — no baseline field. Today a zero-evidence winner is impossible only because `validate_service._not_evaluated` (validate_service.py:815-826) stamps `apply_status=FAILED` on every candidate when the baseline is UNVERIFIED, so `_exclusion` drops them all. That is protection by upstream convention, keyed on a proxy (`apply.status`) rather than on the invariant (was there a trustworthy baseline to measure against).

A verdicts file — a caller-supplied JSONL document, per `load_verdicts` — carrying `"baseline": "unverified"` in the header and candidate records with `apply.status = "ok"` produces a ranked list with a named winner at `tier: applied`. The CLI's only guard is a `note()` on stderr (`main.py:1069-1074`), which is absent from `--json` output, and `_cmd_vote` returns `EXIT_OK` either way.

Failure scenario: an agent pipes `vote --json` into its next step, reads `winner`, and applies a patch that was never measured against a working baseline.

Recommendation: pass the baseline status into `rank()` and either refuse to rank (returning `TIER_NONE` with a reason) or carry it into `VoteReport.as_dict()` and `summary_line()` so the machine-readable answer says on what evidence it was produced.

### B14-M6 — Duplicate candidate indices make the ranking depend on input order, defeating the stated tiebreak
`src/agentless_mcp/core/vote.py:275-282`

```python
    ordered = sorted(
        grouped.items(),
        key=lambda item: (-len(item[1]), min(entry.index for entry in item[1])),
    )
```

The module's stated invariant is "Sampling twice as much must not change which of two equal clusters wins" (vote.py:20-22), enforced by `index` as the tiebreak. `load_candidates` refuses duplicate *stems*, but `load_verdicts`/`_vote_candidate` (validate_service.py:603-628) reads `index` straight from the file with no uniqueness check. Two verdicts files merged from parallel machines — the literal act of sampling twice as much — both start at index 0, so equal-sized clusters tie on `min(index)`; `sorted` is stable, so the ranking and each cluster's `representative` fall back to line order. `test_input_order_does_not_change_the_ranking` only covers distinct indices, so this passes today.

Recommendation: make the tiebreak total — `(-size, min_index, min_id)` for cluster order and `(index, id)` for member order — or reject duplicate indices at the verdicts boundary. Add a test that ranks the same candidate set with duplicated indices in two orders and asserts identical `as_dict()`.

## Low

### B14-L1 — The child inherits the parent's entire environment, undocumented
`src/agentless_mcp/core/sandbox.py:248-255`. `Popen` is called with no `env=`, so a test command out of the analysed repository (B14-M3) runs with whatever the invoking agent's environment holds, including API tokens. Full scrubbing is not practical (tests need `PATH`, `HOME`), but the README security section lists the process-group caveat and omits this one. Recommendation: state the passthrough in README's security section.

### B14-L2 — The vote docstring describes the fall-through tier as something it is not
`src/agentless_mcp/core/vote.py:10-12`: "Falling through is normal: it says 'nothing fixed the bug, here is the best of what did not break anything'". At `TIER_APPLIED` every survivor *did* break something (or timed out, or errored) — `_TIER_DETAIL[TIER_APPLIED]` says so correctly: "applied cleanly (nothing passed the regression suite)". The docstring describes only the `TIER_REGRESSION` rung. A reader generating against the docstring would treat an `applied`-tier winner as regression-clean.

### B14-L3 — `_tail` with a non-positive limit returns a banner and no output
`src/agentless_mcp/core/sandbox.py:375-380`: `start = max(0, end - max(limit, 0))` with `limit=0` yields `start == end`, so the return is `"[... N earlier bytes dropped ...]\n"` with an empty body. `max_capture` is a public keyword argument; either reject non-positive values at the top of `run_command` or return the banner only when there is text after it.

### B14-L4 — `worktree()` can raise a bare `ValueError` out of a function whose contract is `AtlasError`
`src/agentless_mcp/core/sandbox.py:188`: `resolved.relative_to(top)` raises `ValueError`, not `RepoResolutionError`, if `root` resolves outside `git_root(root)` — reachable where symlinks or case-insensitive filesystems make the two disagree. The `finally` still releases, so nothing leaks; the exception type escapes the module's error contract. Recommendation: catch and re-raise as `RepoResolutionError` naming both paths.

### B14-L5 — `_clusters` silently merges keyless candidates instead of failing
`src/agentless_mcp/core/vote.py:271-273`: `key = candidate.equivalence_key or ""`, commented "Eligibility already established a key; the check is for the type." If that eligibility check is ever relaxed, every keyless candidate is clustered together under `""` and reported as a majority. A `raise` (or an assertion the type checker accepts) turns a future refactor into a loud failure rather than an invented consensus.

### B14-L6 — Timing-dependent flake in the process-group test
`tests/unit/test_sandbox.py:150-167, 250-258`: `HANG_SCRIPT` spawns the stubborn grandchild *before* writing the pgid marker, and the test uses `timeout=2`; on a loaded machine where interpreter start-up plus the nested spawn exceeds the bound, `int(marker.read_text().strip())` raises `ValueError` on an empty file rather than failing with a useful message. Write the marker first, then spawn the child, or poll for the marker before asserting.

## Cross-block observations

- **`_vote_candidate` coalesces a missing `reproduction` field to "did not pass"** (`application/validate_service.py:614-628`): `reproduction = record.get("reproduction")` with no presence check, whereas `id`, `index`, `regression` and `apply.status` all go through `_string`/`_integer` and refuse. A rename or a producer bug on that one field reads downstream as "no candidate fixed the reproduction test", silently empties the top rung and changes the answer with no error — the global boundary-integrity rule, in the one field where the default is indistinguishable from a real verdict. Belongs to whichever block owns `validate_service`, but it is what feeds B14's ladder.
- **`_cmd_vote` returns `EXIT_OK` unconditionally** (`adapters/cli/main.py:1049-1075`), including at `TIER_NONE` with no winner and on an UNVERIFIED run. A shell pipeline gated on the exit status cannot distinguish "ranked a fix" from "ranked nothing". Pairs with B14-M5.
- **No ceiling on `--timeout`** (`adapters/cli/main.py:1398-1406` checks only `> 0`), which is what makes B14-H2's disk exhaustion window arbitrarily long.
- **Nothing ever sweeps `scratch_root()`**. There is no cache/scratch GC command anywhere in `src/`; the only removal is the per-run `_release`. Every path that skips it (B14-H1, a SIGKILLed CLI) strands a full checkout under `$XDG_CACHE_HOME` permanently. Whichever block owns the cache lifecycle should own a sweep of `worktrees/` older than N hours.
- **`README.md:107-110` overstates the read-only posture** ("no cache or scratch state is written inside the repository under analysis"). Even in the happy path `git worktree add` writes `.git/worktrees/<id>` into the target repo for the duration of the run; on the B14-H1 path it stays. Documentation blocks should reconcile with the measured behaviour.
