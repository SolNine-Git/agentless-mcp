## Critical

### B08-C1 — A stale `entries` snapshot turns a cache miss into a confident "this file defines nothing"
`src/agentless_mcp/core/cache.py:320-368` (with `:486-493`)

`CachedSource` decides freshness from an `entries` dict snapshotted once at `open_source` time, then reads rows in separate autocommit statements. When the gate passes but the rows are gone, the empty result set is returned as the answer:

```python
def _fresh_digest(self, text: str, path: str) -> str | None:
    entry = self._state.entries.get(path)
    if entry is None or entry.grammar_version != self._state.grammar_version:
        return None
    digest = content_digest(text)
    return digest if entry.digest == digest else None

def _symbol_rows(self, path: str, digest: str) -> list[ASTSymbol]:
    cursor = self._connection.execute(
        "SELECT ... FROM tags WHERE path = ? AND sha256 = ? ORDER BY ordinal", (path, digest))
    return disambiguate([_symbol_from_row(row, path) for row in cursor.fetchall()])
```

There is no `BEGIN` pinning a WAL snapshot across the two, so the `files` snapshot and the `tags`/`imports`/`refs` reads are from different points in time. Zero rows is indistinguishable from "the file legitimately defines nothing" — a case the design *deliberately* records (module docstring: files "that define no symbols at all ... are recorded with their digest"), so no downstream check can recover it either.

Reproduced (scratchpad script, real extractor, real database):

```
index: 2 files
before:                          ['f']
after prune, same live source:   []       <- a.py still contains `def f()`
refs after prune:                []
ground truth:                    ['f']
```

The prune was an ordinary second `build_index` run while a `CachedSource` was open. This directly contradicts the module's headline guarantee at `cache.py:22-30` — *"cannot serve a wrong answer"* — and it fails silently: the receipt still says `fresh`.

Failure scenario: an agent calls `find_referencing_symbols` against the long-running MCP server while a developer runs `agentless-mcp index` in another terminal. The tool answers "no callers" for a symbol that has callers, and the agent deletes the code as dead. Same mechanism zeroes `repo_map` entries and `get_symbols_overview`.

Recommendation: make the row read and the freshness decision one snapshot. Cheapest correct fix is to open the read connection with an explicit `BEGIN` held for the source's lifetime (sources are per-request and short-lived, which is the right scope) so `_load_entries` and every row query see one WAL snapshot. Failing that, treat a zero-row result as a miss unless a same-statement `files` check confirms the row is still present at that digest, and fall through to `self._extractor` — never return `[]` on an unconfirmed miss.

Severity note: argued as Critical rather than High because the wrong answer is silent, is the exact thing the module claims is impossible, and the blast radius is code deletion by an agent. It requires concurrency, which is the only reason it is not worse.

## High

### B08-H1 — A reader deletes the database and its WAL out from under an in-progress index run; the run then reports success having written nothing
`src/agentless_mcp/core/cache.py:461-481`, `:867-882`, `:1094-1103`

`_discard` is called from the *read* path and takes no lock:

```python
def _discard(database: Path) -> None:
    for suffix in ("", "-wal", "-shm"):
        Path(str(database) + suffix).unlink(missing_ok=True)
```

Meanwhile `_open_for_write` creates the schema in autocommit *before* `_plan_index` runs (`build_index:595-598`), so from the moment the writer opens the database until it commits — the entire walk-and-parse phase, seconds to minutes — the `meta` table is empty. A concurrent reader hits `_read_meta` → `None` → `_rejection` → `MESSAGES.cache_discarded_no_index` → `_discard`. The module docstring at `cache.py:39-45` asserts the opposite: *"An index run holds an exclusive lock on `write.lock` next to the database for its whole duration ... Readers never block."* Readers do not block; they delete.

Reproduced:

```
db exists after writer opened schema: True
reader receipt: none (cache discarded: no index has been built)
db exists after reader: False
writer committed rows: _RowCounts(files=0, tags=0, imports=0, refs=0)
db exists after writer commit: False
```

The writer's own `_row_counts` reads back zero for every table because the committed WAL frames were unlinked, and `IndexReport.summary_line()` will happily print `indexed N, reused 0, ... 0 files, 0 tags`. Unlinking an active `-wal` is undefined behavior for SQLite, so the milder outcome above is not guaranteed — a corrupt database is also on the table.

Failure scenario: the MCP server is running, a developer runs `agentless-mcp index` on a large repo, an agent issues one `repo_map` during the walk. The index run finishes, prints a success line, and no database exists. Every later call reports `cache: none` and re-parses; the user re-runs `index` and it happens again.

Recommendation: `_discard` mutates shared state and must route through the same owner as every other mutation — take `_write_lock(database.parent, ...)` around it and degrade to on-demand parsing (without deleting) when the lock is unavailable. Additionally, do not leave a schema-only database visible for the duration of an index run: either write the meta row inside the same `BEGIN IMMEDIATE` as a `schema_version` sentinel that readers recognise as "build in progress", or build into a sibling file and rename over the target under the lock.

### B08-H2 — The grammar-version freshness gate is untested; deleting it leaves the suite green
`src/agentless_mcp/core/cache.py:328`

```python
if entry is None or entry.grammar_version != self._state.grammar_version:
    return None
```

The module docstring names this half of the guarantee (`cache.py:25-27`: *"and only when the grammar pack that produced it is still the installed one"*), and `SCHEMA_VERSION = 3`'s comment records that a changed *extraction* under unchanged content is precisely the failure this class of gate exists for. Verified by revert test: rewriting line 328 to `if entry is None:` and running `tests/unit/test_cache.py` gives `52 passed`. Coverage confirms line 329 is never reached.

Failure scenario: a grammar-pack upgrade changes what the extractor produces for an unchanged file (the exact Go-receiver defect that forced the v3 bump). Nothing in CI notices if the gate is removed or its comparison inverted during a refactor, and every stale-grammar row is served as fresh.

Recommendation: one test that indexes, monkeypatches `grammars.pack_version` to a different string, opens a source, and asserts via the parse spy that the file is re-extracted. The `spy` fixture already in `tests/unit/test_cache.py:93` makes this three lines.

### B08-H3 — `open_source` can raise, contradicting the documented "a read command never fails because of a cache" contract
`src/agentless_mcp/core/cache.py:449-455`, `:1053-1063`, `:1094-1103`

Two uncaught paths out of `open_source`, both against its own docstring (*"Every failure mode -- no database, a database from an older schema, a corrupt file, a key collision with another repository -- produces an on-demand source"*) and against `adapters/cli/main.py:1300-1307` (*"Every failure to open one degrades to on-demand parsing with the reason in the receipt, so a read command never fails because of a cache"*):

1. `_discard` uses `Path.unlink(missing_ok=True)`, which swallows only `FileNotFoundError`. On Windows, unlinking a file another process has open raises `PermissionError`; `EACCES` on a read-only cache directory raises on any platform. Both propagate out of `open_source` as an unhandled `OSError`. The block supports Windows deliberately — `util/platforms` and `util/filelock` exist for it — so this is not a theoretical platform.
2. `repo_generation(resolved, tree_oid)` at `:490` with `tree_oid=None` calls `_manifest_digest` → `walk_repo`, which "raises `WalkBoundExceeded` rather than truncating". A non-git repository that grew past `max_files`/`max_bytes` since it was indexed makes every read command that would otherwise not walk the tree (e.g. `read_slice`) fail — but only when a cache database happens to exist, so building an index turns a working command into a failing one. `_manifest_digest`'s own `stat()` is guarded (`:1057-1061`); `walk_repo`'s is not.

Recommendation: wrap `_discard` in `except OSError` and fold the reason into the note. Wrap the `repo_generation` call in `open_source` so a bound or OS failure yields `repo_generation=None` with a note rather than an exception — the generation is a cost signal, never a correctness one, and must not be able to fail a read.

## Medium

### B08-M1 — Every read against a non-git repository walks and stats the whole tree, to compute a cosmetic receipt field
`src/agentless_mcp/core/cache.py:407-417`, `:490`

`open_source` is called once per CLI command and once per MCP tool call (`adapters/mcp/server.py:204`, `adapters/cli/main.py:1312`). For `tree_oid=None` it runs `_manifest_digest`, which is a full `walk_repo` plus a `stat()` per file. `CacheStatus.fresh` — the only consumer — is documented at `cache.py:118-121` as *"a cost statement rather than a correctness one"*.

Failure scenario: a 40k-file non-git workspace pays a full directory walk and 40k stats on every `read_slice` call, and the answer it buys is one word in a receipt.

Recommendation: compute the repository generation lazily inside `CacheStatus`/`status()` so a call that never renders a receipt never pays for it, or cache the manifest digest against the root directory's own mtime.

### B08-M2 — `receipt` runs four unmemoized `COUNT(*)` scans, twice per response
`src/agentless_mcp/core/cache.py:270-273`, `:302-314`, `:1020-1033`

`CachedSource.receipt` calls `status()`, which calls `_row_counts()` unconditionally: four `COUNT(*)` queries including one over `refs`, described at `:945-947` as *"by far the largest table (tens of thousands of rows per repository against hundreds of symbols)"*. `application/envelope.py:63` reads `ctx.symbols.receipt` from both `receipt_block` and `receipt_fields`, and `adapters/cli/main.py`'s `_Answer` builds text and JSON forms unconditionally — so a single command costs at least eight full table scans. `receipt` does not need row counts at all: it reads only `enabled`, `generation`, `fresh`, `repo_generation`, `note`.

Recommendation: split the counts out of the receipt path — either memoize `_row_counts` on the source (rows cannot change under a source that holds a pinned snapshot, which B08-C1's fix supplies) or build the receipt from `_state` without touching the database.

### B08-M3 — A transient per-file failure deletes that file's previously-good rows and is reported as a prune
`src/agentless_mcp/core/cache.py:645-664`, `:694`

```python
read = read_bounded(root / repo_file.path)
if read.text is None:
    failures.append(...); continue          # never added to `seen`
...
except LanguageUnavailable as exc:
    seen.discard(repo_file.path)            # actively removed from `seen`
```

`_apply_plan` then computes `vanished = [path for path in previous if path not in plan.seen]` and deletes every row for those paths. A file that exists and was correctly indexed loses its rows because of an `EACCES`, a size bound, or a grammar that failed to download this run — `LanguageUnavailable` is raised by `grammars.get_language`, which is exactly the kind of transient, network-adjacent failure the Engineering Invariants call out. `IndexReport.pruned` then reports these as pruned files, which is a false statement about what happened to the repository.

Failure scenario: a grammar-pack cache is cold or the network is down. `agentless-mcp index` reports `pruned 900` on a repository where nothing was deleted, and 900 files re-extract on demand from then on.

Recommendation: distinguish "gone" from "could not be read this run". Keep the previous rows for a path that produced an `IndexFailure` — add failed paths to `seen` (or a separate `retained` set) so `vanished` means only paths the walk did not return — and count them under `errors`, never under `pruned`.

### B08-M4 — The whole schema-migration policy is unexercised
`src/agentless_mcp/core/cache.py:885-896`

`_ensure_schema`'s `if stale: connection.executescript(_DROP_SCHEMA)` is the only migration this package has (`cache.py:73-75`: *"That is the whole migration policy"*), and coverage shows lines 889-890 and 894 never execute. `TestSchemaVersion::test_a_schema_bump_drops_the_database_and_rebuilds_it` exercises the *reader's* `_rejection` + `_discard` route, not `_ensure_schema` — the file is already gone by the time a writer opens it. The writer-first path (bump the version, run `index` before any read) is live, untested, and the one that would run in CI or a fresh deploy.

Recommendation: a test that builds an index, bumps `SCHEMA_VERSION` via monkeypatch, calls `build_index` directly, and asserts the old rows are gone and the new meta row is present.

### B08-M5 — `FileSource` has no `close`, so read connections are released only by the garbage collector
`src/agentless_mcp/core/cache.py:159-186`, `:316-318`

`CachedSource.close()` exists and is called by exactly one test (`tests/unit/test_cache.py:381`). Neither adapter calls it — `grep -rn "\.close()" src/` returns only `util/filelock.py:68`. Because the `FileSource` protocol does not declare `close`, a holder of a `FileSource` cannot release it without an `isinstance` check, so the design makes the correct call impossible to express. The suite's output is the evidence: `52 passed, 36 warnings`, of which the majority are `ResourceWarning: unclosed database`.

Under CPython refcounting the connection is reclaimed when the per-request `RepoContext` dies, so this is a Medium and not a leak today — but it is a leak under any deferred-GC runtime, and the warnings mask real ones.

Recommendation: add `close()` to the `FileSource` protocol (a no-op on `OnDemandSource`) and have both adapters close the source when the request ends — `contextlib.closing` around `_with_source` in `adapters/mcp/server.py:202` and around the CLI's source open.

### B08-M6 — The cache test module cannot be collected on Windows, which the production code supports on purpose
`tests/unit/test_cache.py:14`

```python
import fcntl
```

Module-scope, no `pytest.importorskip`, no `sys.platform` guard. `fcntl` does not exist on Windows, so the entire 684-line, 52-test file fails at collection there — including all 15 equivalence and freshness tests that have nothing to do with locking. `util/platforms.family` and `util/filelock`'s POSIX/Windows split exist specifically so this block runs on Windows; the tests that would prove it do not run.

Recommendation: move `import fcntl` inside `TestSingleWriter` behind `pytest.importorskip("fcntl")`, or mark just that class `@pytest.mark.skipif(sys.platform == "win32", ...)` with a paired `msvcrt` variant.

### B08-M7 — No test covers a reader concurrent with a writer, which is the block's headline design claim
`tests/unit/test_cache.py:414-429`

`TestSingleWriter` is the only concurrency test and it is writer-vs-writer. The module docstring's claims at `cache.py:39-48` — *"A second concurrent run fails immediately ... Readers never block ... a reader that finds no database, a corrupt one or one written by an older schema simply reports `cache: none`"* — are half-tested. B08-C1 and B08-H1 both live in exactly the untested half, and both were found by hand-driving the interleaving rather than by any existing test.

Recommendation: two tests using a real subprocess or a monkeypatched `_plan_index` that blocks on an event: (a) a reader opening a source mid-index leaves the database intact and the index run's committed counts non-zero; (b) a source opened before an index run either serves correct symbols or misses to the extractor, never `[]`.

## Low

### B08-L1 — The `WITHOUT ROWID` rationale comment sits above the wrong table
`src/agentless_mcp/core/cache.py:945-949`

The comment reads *"References are by far the largest table ... A WITHOUT ROWID table keyed on exactly that clusters the rows"* and is immediately followed by `CREATE TABLE IF NOT EXISTS imports (...)`, a plain rowid table with a separate index. The table it describes is `refs`, two definitions further down. A reader tuning the schema will conclude `imports` is `WITHOUT ROWID` and reason wrongly about its storage. Move the comment above `CREATE TABLE ... refs`.

### B08-L2 — `head_sha` is write-only: stored, read back into `_Meta`, and never consumed
`src/agentless_mcp/core/cache.py:243`, `:578`, `:604`, `:757`, `:916`, `:992`

`head_sha` is threaded through `build_index`'s signature, `_Meta`, the `meta` table, and `_read_meta`, and no code anywhere reads `_Meta.head_sha` — `grep -rn "head_sha" src/` shows only the write side plus unrelated `RepoContext` uses. Six touch points and a schema column earning nothing. Either delete it, or state in the schema comment what future check it is reserved for (the `is_def` column at `:767-773` does exactly that and is fine as a result).

### B08-L3 — `_symbol_from_row`'s stated defence against old rows does not hold, and the drop-on-bump policy makes it moot
`src/agentless_mcp/core/cache.py:824-846`

The docstring claims *"Explicit conversions rather than a trusting unpack: these rows are our own data, but they came off disk and a row written by a build that predates a field is foreign data like any other."* But `signature=str(row[4])`, `docstring=str(row[6])`, `parent_class=str(row[5])` turn a `NULL` into the literal string `"None"` — a silent corruption, not a boundary parse, and precisely wrong in the "predates a field" case the comment names. Only `end_line` is handled correctly. Meanwhile `SCHEMA_VERSION`'s drop-and-rebuild policy means a row predating a field can never be read. Either drop the misleading half of the docstring or make the conversions raise on `NULL` in the columns the schema declares `NOT NULL`.

### B08-L4 — `DIRECTORY_MODE` is not applied to a pre-existing cache directory or to its parents
`src/agentless_mcp/core/cache.py:105-106`, `:592`

`database.parent.mkdir(parents=True, exist_ok=True, mode=DIRECTORY_MODE)` applies `0o700` only to the leaf, and only when it is newly created — `Path.mkdir(parents=True)` creates intermediates with the default mode, and `exist_ok=True` silently accepts a directory with any permissions. The comment at `:105` claims the directories *"are owner-only"*. A cache directory created by an older build, or by a process with a permissive umask, stays world-readable and holds derived facts about private repositories. Consider an explicit `os.chmod` on the leaf after `mkdir`.

### B08-L5 — Read paths open the database read-write, so a reader takes write locks and creates WAL sidecars
`src/agentless_mcp/core/cache.py:849-864`

`_connect` is shared by `open_source` and `_open_for_write` and always opens read-write, then issues `PRAGMA journal_mode=WAL` — which requires a write lock and can block up to `SQLITE_TIMEOUT_SECONDS` behind a writer, on a connection whose caller only ever `SELECT`s. Opening the read path with a `file:...?mode=ro` URI (and skipping the journal pragma there) would make "readers never block" structurally true rather than incidentally true, and would make B08-H1's accidental deletion the only way a reader can damage the store.

### B08-L6 — Core renders a remediation naming a CLI command MCP clients cannot run
`src/agentless_mcp/core/cache.py:110`, `:142`; `src/agentless_mcp/prompts/messages.json:14`

`REMEDIATION = MESSAGES.cache_stale_remediation` = `"rerun agentless-mcp index or pass --no-cache"`, and `RECEIPT_BYPASSED = "bypassed (--no-cache)"` at `:109` hardcodes a CLI flag spelling in the storage layer. The MCP adapter never calls `build_index` (`grep -n "build_index" src/agentless_mcp/adapters/mcp/server.py` → no matches), so every stale receipt served to an agent instructs it to run a command that is not on its tool surface. `--no-cache` at least maps to the `no_cache` parameter, but spelled as a CLI flag. Phrase the remediation in adapter-neutral terms (`"re-run the index, or request this call with no_cache"`) or let each adapter supply its own remediation string.

## Cross-block observations

**Ruling on the `core.cache` → `prompts` edge (Phase-1 hint (a)): not a layering leak.** `pyproject.toml:255-267` places `prompts` below `core` in the import-linter layers contract with a written rationale — *"agentless_mcp.prompts sits below core and above util because it is the most stable module in the package: it imports nothing but the standard library and holds only the agent-facing text, so every layer that renders a string for an agent -- the MCP adapter's tool descriptions, the application's envelope, core's cache-staleness remediation -- can depend on it without inverting anything."* The dependency points toward stability, the contract is machine-enforced by `import-linter`, and `prompts/__init__.py` imports only stdlib plus its own loader. That satisfies the global Architecture rule (*"Each repo's layer order lives in its dependency contract ... conform to it or change the design there"*). The defensible objection is about *content*, not direction, and is filed as B08-L6: the strings core pulls in are adapter-specific, so core is coupled to CLI vocabulary through a dependency that is otherwise clean. If B02 rules the other way, the disagreement is about whether a cross-cutting text catalog may hold adapter-specific phrasings — not about whether the import is allowed.

**Concurrency contract is unowned across the block boundary.** B08-C1 and B08-H1 both arise because `open_source` (core) and `build_index` (core) are invoked independently by the adapters with no coordination, while the module's docstring describes a coordination that only half exists. `util.filelock` provides the primitive and `core.cache` uses it on one side only. Whichever block owns `adapters/cli/main.py`'s `index` command should be flagged: the "one owner per state change" rule is violated for the cache database itself — `build_index` mutates it under the lock, `open_source` mutates it (via `_discard`) without.

**`walk_repo` is called twice per index run and once per read.** `_plan_index` and `_manifest_digest` each walk the tree independently (`cache.py:640` and `:1056`), and `open_source` walks again for non-git roots. If B03/B04 (treewalk/fslimits) is considering memoizing or streaming the walk, the cache is the heaviest caller and would benefit most.

**`_row_counts` on the read path.** The application layer (`envelope.py:63`) evaluates `ctx.symbols.receipt` at least twice per response without knowing it costs four full table scans (B08-M2). The `FileSource` protocol advertises `receipt` as a cheap property; whichever block owns `application/envelope.py` should know it is not.
