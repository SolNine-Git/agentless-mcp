## Critical

### B04-C1 — `walk_repo`'s git path serves files symlinked outside the repository root
`src/agentless_mcp/core/treewalk.py:79-104` (with `src/agentless_mcp/core/refs.py:115-118` and `src/agentless_mcp/core/cache.py:640-645` as the consumers)

`git ls-files` lists symlinks like any other tracked entry, and the only filter applied to them is `candidate.is_file()`, which follows the link:

```python
    if is_git_repo(resolved):
        relatives = _git_listed_paths(resolved)
...
        candidate = resolved / relative
        if not candidate.is_file():
            # git lists index entries for files deleted in the working tree.
            continue
...
        size = candidate.stat().st_size
```

The sibling walk in `util/fslimits.py:195-203` refuses exactly this (`_file_stays_inside` → `_is_within(target, root)`), and `contained_path` refuses exactly this for caller-supplied paths (`fslimits.py:48-57`), so the same file is *refused* through `read_slice`/`skeleton` and *served* through `repo_map`/`refs`/the index. The module docstring claims otherwise: "Either way the security bounds in :mod:`agentless_mcp.util.fslimits` still apply." `application/repo_context.py:10-14` makes the promise even more explicit — a server "serves those two directories and nothing under, beside or symlinked from them."

Reproduced (scratch script, this HEAD): a repo with `leak.py -> /tmp/.../secret.txt` committed gives

```
walk_repo(root): [('.gitignore', 9), ('app.py', 4), ('leak.py', 10), ('sub/b.py', 4)]
read leak: TOPSECRET
```

— the reported size is the *outside* target's size, and `read_bounded(root / "leak.py")` returns the outside content.

Failure scenario: an agent points `repo_map` (or any indexing command) at a cloned repository containing a tracked symlink such as `settings.py -> ~/.config/app/settings.py`. The file's path and size land in the tree view, its full text is read into memory, and its identifiers, imports, signatures and refs are extracted into the response and persisted into the tag cache — all for a file outside the allowlisted root, on a server whose whole authorization model is "these exact roots and nothing symlinked from them."

Recommendation: apply the same containment test the fallback path already uses — after `candidate = resolved / relative`, reject anything where `candidate.is_symlink()` and `candidate.resolve(strict=True)` is not within `resolved`. Reuse `fslimits._file_stays_inside` rather than writing a second copy (promote it to a public helper). Pin it with a test that commits a symlink escaping the root and asserts it is absent from `walk_repo`.

## High

### B04-H1 — `is_git_repo` guards on a proxy, so a subdirectory root silently loses gitignore and indexes `.git` internals
`src/agentless_mcp/core/treewalk.py:55-87`

```python
def is_git_repo(root: Path) -> bool:
    """True when ``root`` carries a ``.git`` entry (directory or worktree file)."""
    return (root / ".git").exists()
```

The invariant the branch needs is "this path is inside a git work tree"; the condition tests a correlate, "there is a `.git` entry at exactly this path". A package inside a monorepo — an explicitly supported root, see `core/sandbox.py:160-165` ("when `root` is a subdirectory -- a package inside a monorepo...") — takes the `bounded_walk` fallback, which by design consults no repository content.

Reproduced: for a repo whose root `.gitignore` holds `node_modules/`,

```
walk repo:        ['.gitignore', 'pkg/a.py']
walk pkg subdir:  ['a.py', 'node_modules/x/big.js']
```

and with a vendored inner repository under `pkg/`, `walk_repo(outer/"pkg")` returns 20 paths including `vendored/.git/HEAD`, `vendored/.git/config` (which is where a remote URL's embedded credentials live) and every `vendored/.git/hooks/*.sample`.

Failure scenario: `agentless map --repo monorepo/services/api` on a JS or Python service walks `node_modules/` or `.venv/`, either exploding past `DEFAULT_MAX_FILES`/`DEFAULT_MAX_BYTES` and failing the whole command with `WalkBoundExceeded`, or — under the bounds — indexing vendored code and git internals as if they were the project. The docstring's contract, "List every file under `root` that git would not ignore", is false for every non-top-level root.

Recommendation: decide the branch by asking git, not the filesystem — `gitinfo.git_root(resolved) is not None` already exists in this same block and answers the real question (it also covers worktrees, submodules and bare-adjacent cases for free). `git -C <subdir> ls-files --cached --others --exclude-standard` already restricts output to that subdirectory, so no other change is needed. If the fallback is kept for the git-absent case, exclude `.git` directories in it.

### B04-H2 — Repository-controlled config warnings are unbounded and blow the response ceiling
`src/agentless_mcp/core/projectconfig.py:199-205` (consumed at `application/envelope.py:84-86, 136-137`)

Every bounded field in this module has a cap; the warning list itself has none:

```python
    unknown = sorted(key for key in document if key not in KNOWN_KEYS)
    warnings.extend(
        f"unknown key {key!r} in {CONFIG_FILENAME}: ignored (known keys: {', '.join(KNOWN_KEYS)})"
        for key in unknown
    )
```

Each warning re-embeds the full `KNOWN_KEYS` list, and the envelope emits every one of them in the receipt of *every* response for that repository:

```python
    lines.extend(
        ENVELOPE.receipt_config_warning.format(warning=warning) for warning in ctx.config.warnings
    )
...
    budget = max_tokens - counter.count(header)
    kept, dropped = _fit(body, counter, budget - _MARKER_TOKEN_ALLOWANCE)
```

Measured: a 34,890-byte `.agentless-mcp.json` (well under `MAX_CONFIG_BYTES = 65536`) holding 3,000 one-character unknown keys yields 3,000 warnings totalling 394,890 characters — roughly 99k tokens of header. `_fit` returns `("", len(body.splitlines()))` for a non-positive budget (`envelope.py:208-209`), so the header is emitted whole and the answer body is dropped entirely.

Failure scenario: a repository the agent was asked to analyse (cloned, or simply carrying a config written for a newer build) makes every single MCP response ~4x the advertised token ceiling and empty of content, with the truncation note attributing it to the ceiling rather than to the config. The module docstring's premise — "The file is repository content... it arrives from the same place as the source this package is careful never to trust" — is exactly the reason this needs a bound.

Recommendation: cap the warnings the same way `stoplist` is capped: emit at most N (8 is plenty) plus one "and M more" line, and put the cap in this module beside `MAX_STOPLIST_ENTRIES` so it stays where the other bounds live. Add a test asserting a config full of unknown keys produces a bounded warning tuple.

## Medium

### B04-M1 — `projectconfig.load` follows a symlinked config file out of the repository
`src/agentless_mcp/core/projectconfig.py:145-147`

```python
    path = repo_root / CONFIG_FILENAME
    if not path.is_file():
        return EMPTY
```

`is_file()` and `read_text()` both follow symlinks, and the file is never crossed through `contained_path`. Reproduced: `repo2/.agentless-mcp.json -> /tmp/.../outside.json` is read, `config.present` is `True`, and the outside document's key names come back in the receipt (`unknown key 'secret_key_name_from_elsewhere' ...`).

This contradicts the module's own stated defence: "No key is path-typed: a repository cannot name a file for this tool to read, which removes the whole class of 'config points somewhere else' escapes before it starts." A symlink is precisely a repository naming a file for this tool to read; the escape was closed at the key level and left open at the file level. Impact is smaller than B04-C1 (the leak channel is key names, JSON error text and the resulting settings, not full content), which is why this is Medium.

Recommendation: refuse the config when `path.is_symlink()` and the strict resolve is not within `repo_root` — or route the read through `fslimits.contained_path(repo_root, CONFIG_FILENAME)` and turn its `SecurityRefusal` into a warning, which keeps the "never fails a read command" property.

### B04-M2 — `git_root` throws away the degradation note, so callers state a falsehood
`src/agentless_mcp/core/gitinfo.py:58-64`, consumed at `adapters/cli/main.py:1277-1286` and `core/sandbox.py:172-179`

```python
    outcome = _run(start, ["rev-parse", "--show-toplevel"])
    if outcome.text is None:
        return None
```

The module's thesis is that unknown is a value with a reason attached — "a machine without git installed and a call that timed out all produce `None` plus a note saying which of those happened". `git_root` is the one function that drops the note, collapsing four distinct outcomes (not a repo, git missing, timed out, git errored) into a bare `None`. Both callers then assert the specific one:

```python
        fail(f"{cwd} is not inside a git repository, so there is no root to default to; "
             "pass --repo PATH", EXIT_USAGE)
```

Failure scenario: on a machine without git on `PATH`, or when `rev-parse` times out under load, the CLI tells the user their repository is not a repository and `patch apply` refuses with "no worktree can be created for it" — the user checks `git status`, finds it works, and has nothing to go on. Recommendation: return the `_Outcome` (or a `(Path | None, str)` pair) from `git_root` and have both callers surface the note; the note text already exists.

### B04-M3 — `treewalk`'s git invocation omits `--no-optional-locks`, and the test that claims to cover this only covers `gitinfo`
`src/agentless_mcp/core/treewalk.py:126-135`

```python
    command = [
        "git",
        "-C",
        str(root),
        "ls-files",
```

`gitinfo`'s module docstring states the rule as absolute: "``--no-optional-locks`` is passed on every invocation: reading the state of a repository must not take a lock or refresh an index in a tree we are only ever allowed to read." `tests/unit/test_gitinfo.py:88-111` enforces it — but its docstring overstates the scope ("Both properties are asserted on every argv the module produces"; it means the `gitinfo` module, and `treewalk` produces the argv that runs on every `map`, `tree`, `refs` and index build). A repo-wide invariant enforced in one of the two modules that spawn git is not enforced.

Recommendation: add `--no-optional-locks` to the `ls-files` argv and lift the argv assertion into a shared test that covers both modules' git calls.

### B04-M4 — `treewalk` leaks raw `OSError` from two places its sibling module guards
`src/agentless_mcp/core/treewalk.py:136-149` and `:104`

`_git_listed_paths` catches `FileNotFoundError` and `TimeoutExpired`; it does not catch `OSError` (a non-executable git, `ENOMEM` on fork, `EACCES` on `-C`), while `gitinfo._run:139-140` catches exactly that and converts it to a note. Separately, `size = candidate.stat().st_size` is unguarded: a file listed by `git ls-files` and passing `is_file()` can vanish before the `stat` (a build running in the tree, a checkout in flight), and `fslimits._size_of:206-211` exists specifically to guard that same call.

Failure scenario: an `OSError`/`FileNotFoundError` escapes `walk_repo` typed as neither `RepoResolutionError` nor `WalkBoundExceeded`, past every `except` the adapters were written against, and surfaces to the MCP client as an unclassified crash mid-index. Recommendation: catch `OSError` in `_git_listed_paths` (mirroring `gitinfo._run`) and use `fslimits._size_of` for the stat, skipping the entry when it fails.

### B04-M5 — `snapshot` re-implements the three public readers' argv and adds a fourth subprocess for a guard it does not need
`src/agentless_mcp/core/gitinfo.py:82-102` vs `:67-79`

```python
    head = _run(root, ["rev-parse", f"--short={SHORT_SHA_LENGTH}", "HEAD"])
    tree = _run(root, ["rev-parse", f"--short={SHORT_SHA_LENGTH}", "HEAD^{tree}"])
    status = _parse_dirty(_run(root, ["status", "--porcelain"]))
```

These are byte-for-byte the bodies of `head_sha`, `tree_oid` and `dirty_count`, which nothing in `src/` calls (`grep` across `src/` finds `snapshot` and `git_root` only; `tree_oid` has exactly one caller, a helper in `tests/unit/test_cache.py`). One knowledge, two homes — a change to the SHA length or to an argv has to be made twice, and the second home is the one production runs. The leading `git_root(root)` probe adds a fourth process purely to produce a nicer note; the `rev-parse HEAD` that follows already fails outside a repository with a usable message.

Recommendation: have `snapshot` call the three public functions (returning their `_Outcome`s), or delete the three and keep `snapshot` as the only reader plus whatever the cache test needs. Either is fine; keeping both copies is not.

### B04-M6 — No aggregate bound on git time per call, contradicting the module's own justification of the per-call bound
`src/agentless_mcp/core/gitinfo.py:25-28, 82-94`; `src/agentless_mcp/core/treewalk.py:31-32`

The comment defends 5 s as "far below anything a caller would wait through", but `snapshot` issues four bounded calls, so `resolve_repo` alone can block 20 s before any work starts, and a `tree`/`map` adds `treewalk`'s 30 s `ls-files` on top — 50 s for a call the caller was told is bounded by a courtesy timeout. On a network filesystem or a repository with a cold index this is the realistic path, not the pathological one.

Recommendation: bound the snapshot as a whole (a deadline shared across its calls, or drop the redundant `git_root` probe per B04-M5 and state the real worst case in the comment). Also decide one number: 5.0 s here and 30 s in `treewalk` are two spellings of the same policy in one block (see B04-L3).

### B04-M7 — `render_tree`'s truncation count contradicts the comment that defends it
`src/agentless_mcp/core/treewalk.py:219-238`

```python
        if budget.remaining <= 0:
            budget.omitted += _count_entries(child) + 1
...
            # Depth elision is marked where it happens; only entries dropped
            # for the entry budget feed the trailing count, so the two
            # truncations never double-report the same files.
```

Once the budget is exhausted, `_count_entries(child)` counts the *entire* subtree, including descendants below `depth` that would never have been rendered. Measured: five `dN/x/y/z.py` files with `depth=2, max_entries=3` renders

```
d0/
    x/
        ...
d1/
... 15 more entries truncated (max_entries=3)
```

15 counts four levels' worth of names for `d1`-`d4`, while `d0`'s depth-hidden `y` and `z.py` are counted nowhere. The number is therefore neither "files hidden" nor "entries that would have been shown", and the comment asserting the two truncations are disjoint is what a maintainer will read instead of the code.

Recommendation: count only what the current `depth` would have rendered (recurse with the remaining depth in `_count_entries`), or state plainly in the marker that it counts all descendants. Fix the comment either way.

## Low

### B04-L1 — `dirty_count` under-reports: `git status --porcelain` collapses untracked directories
`src/agentless_mcp/core/gitinfo.py:77-79, 113-118`

The docstring promises "the number of modified or untracked paths". Default porcelain output is `-unormal`, which emits one `?? newdir/` line for a whole untracked directory. Measured: 50 new files under one new directory report `dirty_count: 1`. In a module whose stated purpose is letting an agent tell a stale answer from a fresh one, "dirty: 1" for 50 unindexed files is the wrong signal. Recommendation: either pass `--untracked-files=all` (accepting the cost) or reword the docstring and the receipt to "changed entries", so the number is not read as a file count.

### B04-L2 — `walk_repo` silently drops two classes of listed entries
`src/agentless_mcp/core/treewalk.py:92-95, 156-157`

Non-UTF-8 filenames survive `stdout.decode("utf-8", errors="replace")` as replacement characters, fail `candidate.is_file()`, and vanish. An untracked nested git repository is emitted by `ls-files --others` as a single `vendorlib/` entry (confirmed), also fails `is_file()`, and vanishes with its contents. Both share the `continue` whose comment mentions only deleted index entries. The module's opening position is "A view that silently drops entries is worse than a short one" — that applies to `walk_repo`, not just `render_tree`. Recommendation: return the skipped entries (the codebase already has the `SkippedFile` shape in `core/refs.py`) or at least distinguish the deleted-file case from the undecodable/nested-repo cases in the comment.

### B04-L3 — Two `GIT_TIMEOUT_SECONDS` constants, different values and types
`src/agentless_mcp/core/gitinfo.py:28` (`5.0`) and `src/agentless_mcp/core/treewalk.py:32` (`30`)

Same name, same policy, same block, two homes and a 6x difference with no stated reason. Recommendation: one constant, one comment explaining the number; if `ls-files` genuinely needs longer, name it differently and say why.

### B04-L4 — `walk_repo`'s three bound parameters are never passed a non-default value in production
`src/agentless_mcp/core/treewalk.py:60-66`

All four production call sites (`view_service.py:115`, `refs.py:115`, `cache.py:640`, `cache.py:1056`) call `walk_repo(root)`. Only tests pass `max_files`. The parameters are also enforced *twice* on the fallback path — once by `bounded_walk`, again by the loop below it. Recommendation: keep `max_files` for the tests if you like, but the double enforcement is dead code on the fallback path and should go.

### B04-L5 — Two hermeticity soft spots in the tests
`tests/unit/test_gitinfo.py:51-59` and `tests/unit/test_treewalk.py:18-27`

`test_a_repository_without_commits_reports_the_reason` runs `git init` with the developer's inherited environment, unlike every other repository builder in the suite (`tests/conftest.py:103-133` pins identity per invocation; `test_treewalk.py`'s helper replaces `HOME` and sets `GIT_CONFIG_NOSYSTEM=1`). A machine with `init.templateDir` or a global excludes file participates in the result. Separately, `test_treewalk.py`'s helper hardcodes `"PATH": "/usr/bin:/bin"`, which is a machine assumption (git under `/usr/local/bin` or a Nix store fails the fixture, not the code) in a repo that otherwise carries platform-dispatch tests. Note also that `walk_repo` itself runs git with the *ambient* environment, so `test_gitignored_paths_are_excluded`'s exact-list assertion depends on the developer's global `core.excludesFile` — inherent to honouring global excludes in production, but worth knowing before it is debugged as a flake.

### B04-L6 — The degradation notes are unpinned by tests
`tests/unit/test_gitinfo.py:68-86`

Both degradation tests assert only that the value is `None`; neither asserts the note says "git is not installed" or "timed out". The note *is* the feature — a `None` with an empty note is exactly the silent failure the module docstring says it exists to prevent, and it would pass both tests. Recommendation: assert the note substring in each.

### B04-L7 — `_build_tree` silently drops a file whose name collides with a directory name
`src/agentless_mcp/core/treewalk.py:194-207`

`render_tree([RepoFile("a", 1), RepoFile("a/b", 1)])` returns `'a/\n    b\n'` in either input order: the file `a` disappears. Not reachable on a POSIX filesystem, so Low, but the `setdefault`/`isinstance` dance reads as if it handled the case when it just picks a winner. Recommendation: leave the code and drop the ambiguity from the comment, or render the collision.

## Cross-block observations

- **The containment invariant is enforced per-entry-point, not per-read.** `contained_path` guards caller-supplied paths and `bounded_walk` guards the fallback traversal, but the git-listed traversal (B04-C1) reaches `read_bounded` in `core/refs.py:118` and `core/cache.py:645` with no guard at all. Whichever block owns `refs`/`cache` should be checked for the same assumption ("anything `walk_repo` returned is inside the root"), and the containment test probably belongs at the read, not at each of the three entry points that currently remember to call it.
- **Two modules spawn git with opposite degradation policies.** `gitinfo` turns every git failure into a note and answers anyway; `treewalk` turns git-absent into a hard `RepoResolutionError`, so on a machine without git every non-repo directory works and every repository fails. Blocks that own the adapters should decide which policy is the product's, because right now the answer depends on which module the command happened to route through. `core/sandbox.py:386` already carries a comment acknowledging it is a third policy.
- **`tree_oid` is HEAD's tree and does not move with uncommitted edits**, yet `core/cache.py:407-416` uses it as the cache generation. It is sound only because the index also digests file content per entry; any consumer that treats the generation as a content identity without a digest check will serve stale symbols on a dirty tree. Worth confirming in the cache block.
- **Config warnings are an unbounded repository-controlled channel into every response** (B04-H2). The envelope block computes its token budget as `max_tokens - count(header)` and has no floor on the result; a header bound there would be defence in depth even after `projectconfig` caps its warnings.
- **`gitinfo.head_sha`, `tree_oid` and `dirty_count` have no production callers.** If the audit is producing a dead-code list, these three belong on it (with `tests/unit/test_cache.py:680-682` as the one thing to rehome first).
