## Critical

### B20-C1 — `apply` writes U+FFFD over every non-UTF-8 byte in an edited file and reports `ok=True`

`src/agentless_mcp/application/patch_service.py:339-343`

```python
sources = self._read(base, edits)
result = apply_edits(edits, sources.contents, intervals=intervals)

for path, content in result.new_contents.items():
    contained_path(base, path).write_text(content, encoding="utf-8")
```

`_read` goes through `read_bounded`, which decodes lossily
(`src/agentless_mcp/util/fslimits.py:105`):

```python
return BoundedRead(path=path, text=data.decode("utf-8", errors="replace"), skipped=None)
```

`errors="replace"` is correct for the read-only analysis surface `read_bounded` was built for — a
stray byte must not fail a repo scan. It is wrong the moment the decoded string is written back,
because the round trip is not lossless: every undecodable byte becomes `EF BF BD` on disk, in
regions of the file no edit named.

Measured, in-place apply against a repo whose `app.py` ends with a latin-1 `café`:

```
before = b'def f():\n    return 1\n# caf\xe9\n'
after  = b'def f():\n    return 2\n# caf\xef\xbf\xbd\n'
report.ok = True
```

**Failure scenario.** A repository with any latin-1 / cp1252 / shift-jis source file, test fixture,
or file carrying a stray byte. `agentless-mcp patch apply --in-place` mutates bytes outside the
patch, exits 0, and the receipt says `applied 1 of 1 edits`. The same corruption lands in the
worktree diff on the default path, so a caller who pipes that diff into `git apply` propagates it.
It also lands in `validate_service._evaluate`, which calls `apply(..., in_place=True)` into the
worktree candidates are judged in — so a candidate can be failed by corruption the tool introduced.
Partially mitigated: `--in-place` requires a clean tree, so `git checkout .` recovers, and the
extra hunk is visible in the text diff. Neither the JSON form nor `ok` discloses it.

**Recommendation.** The write path must not use the lossy reader. Give `patch_service` a strict
read — `data.decode("utf-8")` with a `UnicodeDecodeError` turned into an `unreadable` entry
("not UTF-8 text; this patch tool cannot edit it safely") — so a non-UTF-8 file is refused per file
rather than silently rewritten. Do not change `read_bounded` itself; its lossy default is right for
the analysis side. Test: apply an edit to a repo containing a latin-1 file and assert the untouched
bytes are byte-identical after.

## High

### B20-H1 — `apply` discards `_Sources.unreadable`, so an oversized or unreadable file is reported as "no such file"

`src/agentless_mcp/application/patch_service.py:339-340` (compare `check`, 258-272)

```python
sources = self._read(base, edits)
result = apply_edits(edits, sources.contents, intervals=intervals)
```

`_read` returns both halves, but `_apply_at` uses only `sources.contents` and drops
`sources.unreadable` on the floor. `apply_edits` then sees no entry for the path and emits
(`core/patches.py:364-368`) `EditStatus.NO_SUCH_FILE` with
`reason=f"no such file in this patch's scope: {path}"`.

Measured, against a 1,200,006-byte tracked `big.py`:

```
apply  = [('no_such_file', "no such file in this patch's scope: big.py")]
check  = [('big.py', 'skipped: 1200006 bytes exceeds the per-file cap of 1000000 bytes')]
```

The file exists and is tracked. `check` tells the truth; `apply` tells the caller something false
about their own repository, and the two commands the CLI advertises as a pipeline disagree about
the same input.

**Failure scenario.** An agent runs `patch check` (green, one honest note), then `patch apply`, and
is told the file it just checked does not exist. The obvious next move — recreating the "missing"
file — is destructive. The same applies to an unreadable file (`unreadable: Permission denied`).

**Recommendation.** Have `_apply_at` carry `sources.unreadable` into the report the same way
`check` does, or pre-empt it: raise/annotate before `apply_edits` so the outcome reason names the
real cause. This is a shared-shape problem with `check` — both should consume one helper that
converts `_Sources.unreadable` into typed per-path outcomes. Test: apply to a >1 MB file and assert
the reason names the cap.

### B20-H2 — one JSON-shaped candidate aborts the entire lint run, contradicting the module's stated guarantee

`src/agentless_mcp/application/lint_service.py:129` inside `_findings`, reached from the
comprehension at `lint_service.py:61-67`.

Module docstring, `lint_service.py:19-22`:

> "Nothing here decides anything. The report has no verdict, ``lint`` exits 0 whatever it finds,
> and a candidate whose patch does not parse is reported with its parse errors rather than skipped."

`_findings` docstring, `lint_service.py:124-127`:

> "A block that did not parse is reported as a coverage gap in the same list as the findings: a
> patch half of which was unreadable, linted silently, is a clean report about a patch nobody read."

Both hold only for raw SEARCH/REPLACE input, where `load_edits` delegates to `parse_blocks` and
returns errors. For anything whose first non-space character is `{`, `load_edits`
(`patch_service.py:183-199`) *raises* `AtlasError`. The comprehension has no per-candidate guard, so
the exception escapes `lint()` and the CLI's `run()` (`adapters/cli/main.py:126-129`) turns it into
a failed command with no report at all.

Measured, a directory holding `01-bad.json` (`{"nope": []}`) and a valid `02-good.txt`:

```
$ agentless-mcp lint --candidates ./cands --repo .
agentless-mcp: edits document must be a JSON object with an 'edits' list
EXIT=1
```

The good candidate is never linted. A `SecurityRefusal` from `_canonical` (`lint_service.py:155-157`)
behaves the same way (measured: `EXIT=2`), though refusing the whole invocation there is defensible.

**Failure scenario.** A ten-candidate lint run over model output where one candidate is a malformed
edits.json produces nothing at all, and the caller has no signal which candidate poisoned it beyond
a message that names no id. This is a comment asserting an invariant the code does not hold — the
next agent generates against the docstring.

**Recommendation.** Wrap the per-candidate call so an `AtlasError` from `load_edits` becomes a
`CHECK_COVERAGE` / `NOT_CHECKED` finding on *that* candidate, exactly as block-level parse errors
already are at `lint_service.py:130-141`. Keep `SecurityRefusal` aborting if that is the intended
posture, but then say so in the docstring. Tests: a directory with one unparseable JSON candidate
still reports every other candidate; the bad candidate carries a `not_checked` finding naming it.

### B20-H3 — a failed or erroring in-place apply leaves the checkout half-patched, with no compensation and no error type

`src/agentless_mcp/application/patch_service.py:342-343`

```python
for path, content in result.new_contents.items():
    contained_path(base, path).write_text(content, encoding="utf-8")
```

Two distinct partial-failure outcomes, both measured:

*Failed edits.* `new_contents` holds every file at least one edit changed, regardless of whether
sibling edits failed. A two-file patch where the second block does not match:

```
report.ok = False        a.py = 'A = 2\n'   (written)   b.py = 'B = 1\n' (untouched)
```

The user's checkout now carries half a patch. `apply`'s docstring (275-293) describes the clean-tree
requirement and the worktree default but says nothing about this. Nothing rolls back and nothing
tells the caller the tree is now in a state neither HEAD nor the patch describes.

*Erroring writes.* The loop has no error handling. A read-only file second in iteration order:

```
PROBE4 raised: PermissionError [Errno 13] Permission denied: '.../z.py'
   a.py = 'A = 2\n' (written)   z.py = 'Z = 1\n' (not written)
```

`run()` (`adapters/cli/main.py:126-129`) catches only `AtlasError`, so this is a raw Python
traceback. No `ApplyReport` is returned, so the caller never learns which files were written before
the failure. Same for `OSError`/`ENOSPC` mid-loop.

**Failure scenario.** `agentless-mcp patch apply --in-place && pytest` — the tests run against a
tree carrying an arbitrary prefix of the patch. Under the traceback variant the operator gets a
stack trace with no receipt and no list of touched files.

**Recommendation.** Two changes, both small. (1) Decide the invariant and state it: either refuse
to write anything when `not result.ok` in `in_place` mode, or document all-or-nothing as explicitly
not guaranteed and have `_patch_receipt` print a loud "the working tree now holds a partial patch;
`git checkout --` to restore" line. (2) Wrap the write loop so an `OSError` becomes an `AtlasError`
naming the failing path *and* the paths already written. Tests: a two-file patch whose second edit
fails leaves the checkout untouched (or, if partial is intended, asserts the warning); a
non-writable target raises `AtlasError` naming both files.

### B20-H4 — the `Sequence[Edit]` signature erases parse errors, so the layer that owns the write cannot refuse half a patch

`src/agentless_mcp/application/patch_service.py:248, 275, 302` — `check`, `apply` and `normalize`
all take `edits: Sequence[Edit]`, while `load_edits` (173-204) returns a `ParseResult` carrying
`errors`. The type the write methods accept cannot represent "and three blocks did not parse".

`core/patches.py:112-117` states exactly why that matters:

> "A parse that returns edits and drops the malformed blocks silently is the failure mode this type
> exists to prevent: a truncated patch would otherwise apply its first half and report success."

The CLI's `_patch_call` (`adapters/cli/main.py:1215-1219`) notes the errors to stderr and returns
`parsed.edits`. Measured, with a patch whose second block is truncated:

```
$ agentless-mcp patch apply -f /tmp/b20p.txt --repo . --in-place
agentless-mcp: block 1 (a.py): block is not terminated by >>>>>>> REPLACE (truncated output?)
# applied 1 of 1 edits to 1 files in the working tree, against the working tree
EXIT=0
```

Exit 0, half the patch on disk. `validate_service._evaluate` (`validate_service.py:466-471`) does
guard this (`if parsed.errors: return _apply_failed`), and `lint_service._findings` reports the
errors — so two of three consumers hand-roll the same guard and the third forgets. That is the
signature's fault, not only the CLI's: a rule that every caller must remember is a rule that will
be forgotten, and it was.

**Failure scenario.** An agent scripting `patch apply --in-place && pytest` gets a green exit for a
truncated model output, runs the suite against a half-patched tree, and reports a result about a
patch that was never applied.

**Recommendation.** Make the write side accept the parse result, not a bare edit list — e.g.
`apply(parsed: ParseResult, ctx, *, allow_partial: bool = False)` refusing when `parsed.errors` and
not explicitly overridden. One owner enforcing the invariant, instead of three callers remembering
it. Cross-block: the CLI fix at `main.py:1215-1219` is needed either way. Test: a truncated patch
through `patch apply --in-place` leaves the checkout unchanged and exits non-zero.

## Medium

### B20-M1 — the clean-tree guard reads a snapshot taken before an unbounded stdin read

`src/agentless_mcp/application/patch_service.py:352-366`

```python
def _require_clean(self, ctx: RepoContext) -> None:
    if ctx.dirty_count == 0:
        return
```

`ctx.dirty_count` is a field of `RepoContext`, populated once by `resolve_repo`
(`repo_context.py:80-88`) via `gitinfo.snapshot`. `RepoContext`'s own docstring calls it
"Snapshotted once per call". The guard therefore keys on *"the tree was clean when the context was
resolved"*, a proxy for the invariant it protects, which is *"the tree is clean now, at the instant
I overwrite these files"*.

The window is not theoretical. `_patch_call` (`adapters/cli/main.py:1204-1219`) resolves the
repository *first* and reads the patch *second*, and `_patch_text` (`main.py:1193`) falls through to
`sys.stdin.read()` — which blocks until EOF. `agentless-mcp patch apply --in-place` fed from a pipe
holds a clean-tree verdict computed before an arbitrarily long wait, then overwrites files.

**Failure scenario.** A model streams a patch into the CLI over thirty seconds while the developer
saves a file in their editor. `--in-place` proceeds on the stale verdict and overwrites uncommitted
work — the precise outcome the guard exists to prevent, and it is unrecoverable because the work was
never committed.

**Recommendation.** Re-read the dirty count inside `_require_clean` (`gitinfo.dirty_count(ctx.root)`
already exists at `gitinfo.py:77-79`) rather than trusting the snapshot, or have the CLI resolve the
context after reading stdin. The snapshot stays right for receipts; it is wrong as a write guard.
Test: mutate the tree between `resolve_repo` and `apply(..., in_place=True)` and assert the refusal.

### B20-M2 — the containment-and-canonicalisation rule has two homes

`src/agentless_mcp/application/patch_service.py:372-387` and
`src/agentless_mcp/application/lint_service.py:146-158` — identical bodies:

```python
return tuple(
    replace(edit, path=contained_path(root, edit.path).relative_to(root).as_posix())
    for edit in edits
)
```

`lint_service._canonical`'s docstring even says so: *"The same rule
:class:`agentless_mcp.application.patch_service.PatchService` applies, and for the same two
reasons"*. This is a security rule (path-escape refusal) plus an identity rule (`app.py` and
`./app.py` are one file) maintained in two places. The global DRY rule's exception — "wait for the
third genuinely identical use" — does not cover knowledge this load-bearing; the two uses are
*already* identical, verbatim, and one is a refusal boundary.

**Failure scenario.** A fix to the containment rule (say, adding a case-insensitive-filesystem
normalisation, or a Windows drive check) lands in one copy. Lint and apply then disagree about which
paths are one file, and a lint report is clean about a patch apply would refuse — or worse, the
other way round.

**Recommendation.** Move it to one function in `patch_service` (or a small shared module) and have
`lint_service` import it. One home, one test.

### B20-M3 — two `load_candidates` with the same name, the same documented rule, and different behaviour

`src/agentless_mcp/application/lint_service.py:87-114` vs
`src/agentless_mcp/application/validate_service.py:517-560`.

`lint_service.load_candidates`'s docstring claims parity:

> "The same two shapes ``patch parse`` accepts, and the same id rule ``validate`` uses: one file is
> one candidate and its stem is its id, so a lint report and a verdicts document name the same
> candidate the same way."

Three measured divergences:

1. **Stem collisions.** `validate_service.py:541-547` refuses two files sharing a stem, with a
   message explaining that ids would collide. `lint_service` does not. Measured, with `fix.txt` and
   `fix.json` in one directory: `lint --json` emits two `candidates` entries both with `"id": "fix"`,
   exit 0 — while `validate` on the same directory hard-refuses. The docstring's "name the same
   candidate the same way" is false in exactly the case validate exists to guard.
2. **Encoding.** `lint` reads via `read_bounded` (lossy `errors="replace"`, 1 MB cap);
   `validate` uses `read_text(encoding="utf-8")` and refuses with "candidate X is not UTF-8 text".
   Lint silently mangles a candidate validate refuses.
3. **Shape.** `lint` accepts a file or a directory; `validate` requires a directory. This one is
   deliberate and documented.

**Failure scenario.** A caller lints a candidate directory (clean, exit 0, two rows named `fix`),
maps the findings back onto candidates by id, and attributes one candidate's findings to the other.
Then `validate` refuses the same directory outright.

**Recommendation.** Extract the shared rule — sorted directory listing, stem-as-id, collision
refusal, strict UTF-8 read — into one function both services call, differing only in the wrapper
type they build. Failing that, fix the docstring so it stops claiming a parity that does not exist.

### B20-M4 — `intervals` is dead parameter surface on all three write methods

`src/agentless_mcp/application/patch_service.py:253, 258, 281, 297, 300, 307, 312, 335, 340`

`intervals` is declared on `check`, `apply` and `normalize`, threaded through `_apply_at`, and
handed to `apply_edits`. Grep across `src/` and `tests/` finds **no caller anywhere** that passes a
non-default value: not the CLI (`main.py` passes it only to `read_slice`), not `validate_service`,
not `tests/unit/test_patch_service.py`. `apply_edits`'s interval handling is genuinely tested — but
only in `tests/unit/test_patches.py:297-359`, at the core level, never through this service.

**Failure scenario.** Not a live bug; it is nine lines of unexercised branching on the most
dangerous write path in the repo, and a claim of a capability nothing delivers. If someone wires it
up later, the "scoped writes" path reaches the filesystem for the first time in production.

**Recommendation.** Delete it from the three public signatures until a caller exists (the interval
plumbing lives in `apply_edits` and is not lost). If it is meant to be the `resolve-locs` →
`patch check` bridge, wire that path and test it end to end; a parameter no caller can reach is not
a feature.

### B20-M5 — `PatchService.parse` bypasses `load_edits`, so `patch parse` silently mishandles the edits.json form every sibling accepts

`src/agentless_mcp/application/patch_service.py:244-246`

```python
def parse(self, text: str) -> ParseResult:
    """Parse patch text into edits and per-block errors."""
    return parse_blocks(text)
```

One caller (`adapters/cli/main.py:925`), and it is the only write subcommand that does not go
through `_patch_call`/`load_edits`. `load_edits`'s docstring (173-182) sells the dual-format
behaviour as the point:

> "The two forms are told apart by the first non-space character, so ``patch parse | patch check``
> and ``patch check`` on raw model output are the same command."

`parse` does not do that. Measured, feeding a generated `edits.json` back to `patch parse`:

```
agentless-mcp: 1 blocks did not parse
  block 0 ("reason": "block is not terminated by): block has no <<<<<<< SEARCH marker
{"edits": [], "errors": [{"index": 0, "path": "\"reason\": \"block is not terminated by", ...}]}
```

A JSON fragment presented as a filename. On a *well-formed* edits.json the output is worse —
`{"edits": [], "errors": []}`, exit 0: a silently empty result for input every other subcommand
reads correctly.

**Failure scenario.** An agent normalises to edits.json, then re-runs `patch parse` on it (to
re-check after an edit, or because a script is uniform) and receives an empty edit list with a
success exit.

**Recommendation.** Route `_cmd_patch_parse` through `load_edits` and delete `PatchService.parse` —
a one-line wrapper with one caller whose only distinguishing property is being wrong. Test: an
edits.json document round-trips through `patch parse` unchanged.

### B20-M6 — the checkout is written with non-atomic truncate-then-write

`src/agentless_mcp/application/patch_service.py:343`

```python
contained_path(base, path).write_text(content, encoding="utf-8")
```

`write_text` opens with `"w"` — truncate, then write. An interrupt (Ctrl-C on a slow apply), a
crash, or `ENOSPC` between the two leaves a truncated or empty file where a source file was. The
full new content is already in memory, so nothing forces this shape.

**Failure scenario.** `--in-place` on a large file, interrupted; the file is now empty. Recoverable
via git only because the clean-tree requirement happens to hold — the write path itself provides no
guarantee, and the same code runs against `validate`'s worktrees where a truncated file silently
becomes the tree a candidate is judged in.

**Recommendation.** Write to a sibling temp file in the same directory and `os.replace` it into
position (atomic on POSIX and Windows). Small change, and it composes with the B20-H3 fix: write all
temps first, rename only when every write succeeded, which gets all-or-nothing nearly for free.

## Low

### B20-L1 — CRLF files can never be patched, and the failure reason does not say so

`patch_service.py:403` (`read_bounded` → `read_bytes().decode(...)`, no newline translation) plus
`core/patches.py` whole-line matching. Measured, a `c.py` of `b"A = 1\r\nB = 2\r\nC = 3\r\n"` and an
edit searching for `B = 2`:

```
ok = False   [('not_found', 'search text not found')]   bytes unchanged
```

Failing closed is the right call — a lossy CRLF/LF round trip would be a variant of B20-C1. But
"search text not found" sends the caller hunting for a typo in a patch that is correct. Suggest
detecting `\r\n` in the source when an edit reports `NOT_FOUND` and naming line endings in the
reason. Arguable either way; filed low.

### B20-L2 — `frozen=True` dataclasses holding mutable dicts

`patch_service.py:57-62` (`_Sources.contents`, `_Sources.unreadable`), `151-156`
(`NormalizeReport.file_keys`), and inherited from `core/patches.py:179-190`
(`ApplyResult.new_contents`). `frozen=True` promises immutability the type does not deliver — any
holder can mutate the dict, and these are the file contents about to be written. Convention in this
codebase is otherwise strong on immutability (`tuple[...]` everywhere else in the same file), so
these read as oversights. Suggest `Mapping[str, str]` at minimum, so the type says what is true.

### B20-L3 — the write side cannot create files, and nothing says so

`new_contents` (`core/patches.py:179-190`) only ever holds paths that were read, and `_read`
(389-409) only admits existing files. An edit naming a new file therefore reports
`no_such_file` — same status and reason string as a genuine typo. For a patch tool aimed at
model-authored repairs, "add a new module" is a routine patch shape. The limitation may well be
deliberate; it belongs in the `patch_service` module docstring alongside the containment and
clean-tree rules, and the outcome deserves its own reason wording.

### B20-L4 — `_texts` holds the whole repository's source in memory for the duration of a lint

`lint_service.py:174-181` reads every scanned file into one `dict[str, str]` and hands it to
`RepoFacts`, which lives across every candidate. Sharing the scan is the right call and the
docstring justifies it well; the memory shape is the cost. Bounded only by
`bounded_walk`'s `DEFAULT_MAX_BYTES` (200 MB). Not a bug at current scale — noting it because the
docstring argues the sharing decision without naming this side of it.

## Cross-block observations

- **`read_bounded`'s `errors="replace"` is a read-surface decision that leaked to the write
  surface.** `util/fslimits.py:105` is correct for analysis and wrong for round-tripping. Whichever
  block owns `fslimits` should consider splitting the two readers explicitly (`read_bounded` /
  `read_bounded_strict`) rather than leaving the write path to remember. Consumers to check: this
  block (B20-C1), `lint_service._texts` and `_candidate`, and anything else that writes back what
  `read_bounded` returned.
- **The CLI drops parse errors on the write path.** `adapters/cli/main.py:1215-1219`
  (`_patch_call`) notes `parsed.errors` to stderr and returns `parsed.edits`, producing exit 0 on a
  truncated patch that half-applied in place (B20-H4). The CLI block should carry its own finding;
  the service-signature half is filed here.
- **Three consumers of `load_edits`, three different error postures.** `validate_service` refuses on
  `parsed.errors`, `lint_service` reports them as coverage gaps, the CLI notes and proceeds. Only
  one of the three can be right. Worth a cross-block decision rather than three local fixes.
- **`load_candidates` is defined twice** (`lint_service.py:87`, `validate_service.py:517`) with the
  same name, the same documented id rule, and different collision/encoding behaviour (B20-M3).
  Whoever reviews B-validate should see the same finding from the other side.
- **`validate_service` inherits B20-C1 and B20-M6.** `validate_service.py:485` calls
  `self._patches.apply(parsed.edits, scoped, in_place=True)` into a fresh worktree, so any
  corruption or truncation the write path introduces lands in the tree a candidate's verdict is
  computed from. A candidate can be marked failing for damage the tool did.
