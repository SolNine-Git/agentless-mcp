## High

### B15-H1 — A malformed `pyproject.toml` makes the linter accuse every declared dependency of being hallucinated, and drops the parse warning on the floor
`src/agentless_mcp/core/patchlint.py:487-526`, `529-542`

`read_declared_dependencies` appends the manifest to `sources` on the *failure* path as well as the success path:

```python
found, problems = parse_pyproject_dependencies(read.text)
packages.update(found)
warnings.extend(problems)
sources.append(PYPROJECT_NAME)          # <- unconditional
```

and `DeclaredDependencies.known` is `bool(self.sources)`. So a manifest that did not parse yields `packages=frozenset()` with `known=True`, which is precisely the state `_undeclared_imports` treats as "the repository genuinely declares nothing".

This contradicts the function's own docstring two lines above the code:

> "A manifest that cannot be parsed produces a warning and contributes nothing, rather than being treated as an empty one -- an empty declared set would make every third-party import in the patch look hallucinated."

Reproduced on Python 3.13 (`tomllib`, not the fallback) with a `pyproject.toml` missing one `]`:

```
declared: DeclaredDependencies(packages=frozenset(), sources=('pyproject.toml',),
                               warnings=('pyproject.toml did not parse: TOMLDecodeError',))
known (check will run): True
  [undeclared_imports/warning] the patch imports 'requests', which is neither a declared
  dependency, nor part of the standard library, nor imported anywhere else...
```

The warning that would have explained it is unreachable: grep over `src/` finds **no consumer of `DeclaredDependencies.warnings`** (`lint_service._facts` constructs `RepoFacts` and never reads it; `patchlint` never reads it; `render.LintReportView` has no field for it). The repo's own convention is the opposite — `projectconfig`'s warnings reach the user through `application/envelope.py:85`.

Failure scenario: a developer runs `agentless lint` while mid-edit on `pyproject.toml`, or on a repo whose manifest uses a TOML feature the reader trips on, and gets a WARNING per third-party import in the patch, each asserting the package is undeclared. The one signal that would identify the real cause exists in memory and is discarded. `requirements*.txt` has the same shape at line 519-520, though `parse_requirements` cannot fail.

Recommendation: append to `sources` only when the manifest actually parsed, and carry `DeclaredDependencies.warnings` into `LintReport` as `CHECK_UNDECLARED_IMPORTS` / `Severity.NOT_CHECKED` findings — the module already has `_gap` for exactly this, and the module docstring already commits to "Silence is the one outcome that would be a lie."

### B15-H2 — `dangling_references` reports a local bound above the edited block as a hallucinated helper, at WARNING
`src/agentless_mcp/core/patchlint.py:1321-1338`, `1352-1375`

`_bound_names` collects bindings from the *fragment only*. An edit's replacement block is normally a slice of a function body, so any local bound earlier in that body is invisible, and a call to it takes the full WARNING path.

Reproduced against a repo containing `app.py`:

```python
def outer():
    local_fn = lambda: 1
    value = local_fn()
    return value
```

with the edit `search="    value = local_fn()\n    return value"`, `replace="    value = local_fn()\n    return value + local_fn()"`:

```
[dangling_references/warning] app.py:3 :: the patch calls 'local_fn', which nothing in this
repository defines, the patch itself does not define, and which is neither a builtin nor a
standard library module || no existing name is within two edits of it
```

The module docstring reasons carefully about exactly this blind spot and then leaves the door open:

> "A bare identifier read is almost always a local, and this module cannot see a function's scopes; a check that reported every local variable as undefined would be a check nobody reads"

The reasoning applies verbatim to a local in *call* position; restricting to call position does not restore the missing scope. The claim in the message ("nothing in this repository defines") is an absolute the check cannot support from a fragment.

Recommendation: gate on evidence that the fragment is self-contained. The module already computes it — `_is_module_level` reads `fragment.replace_columns`; when the fragment's first non-blank line is indented, the edit is a body slice and the enclosing scope is unreadable. Either emit `Severity.NOT_CHECKED` for those fragments (consistent with the module's own coverage-honesty rule) or drop such findings to `ADVISORY` and reword the message to "does not resolve from this block".

### B15-H3 — `dangling_callers` counts unrelated locals and attribute accesses as callers, and can fire with zero real callers
`src/agentless_mcp/core/patchlint.py:1546-1550`

```python
def _reference_sites(name: str, facts: RepoFacts, paths: Sequence[str]) -> tuple[str, ...]:
    return tuple(
        f"{path}:{ref.line}" for path in paths for ref in facts.files[path].refs if ref.name == name
    )
```

Name equality against the raw reference table, with no check that the referencing file imports the symbol and no use of `Ref.locally_bound` — a field that exists for this purpose. `core/extractor.py:344-348`:

> "``locally_bound`` is True when an enclosing function's parameter list binds this name at this occurrence: the occurrence spells the local binding (or declares it), not any repository-level definition sharing the name. Recorded rather than dropped, so **the resolver can refuse to point such a use at an unrelated symbol**."

Reproduced with a repo whose only other file is unrelated to `helpers.py`:

```python
# unrelated.py
class Thing:
    def go(self):
        helper = 5
        return self.helper + helper
```

Renaming `helper` in `helpers.py` (no importer anywhere in the repo):

```
[dangling_callers/warning] helpers.py:1 :: the patch removes or renames 'helper', which
3 reference(s) in files this patch does not touch still name
|| still referenced at unrelated.py:3, unrelated.py:4, unrelated.py:4
```

All three sites are a local integer and an attribute of an unrelated class. The constant comment at line 158 states "The count in the message is always exact" — it is exact about the wrong quantity.

Failure scenario: on any real repo, common helper names (`run`, `load`, `parse`, `helper`, `name`) collide with locals and attributes everywhere, so this check's warnings are dominated by noise on exactly the renames a reviewer most wants checked, and a reviewer who spot-checks two sites and finds them irrelevant will stop reading the check.

Recommendation: filter `ref.locally_bound`, and require the referencing file to either import the symbol (`resolve_import_target`, already imported at line 111) or resolve the name through `facts.resolver` to the definition the patch removed — `RepoFacts.resolver` is already on hand and both other name-level checks use it.

### B15-M1 — `arity` guesses on a lambda argument and reports a wrong count, breaking its stated "silence rather than guess" contract
`src/agentless_mcp/core/patchlint.py:1213-1223`, `1243-1261`

`_split_top_level` splits on every bracket-depth-zero comma. A lambda's parameter commas are at depth zero:

```
lambda with comma                   -> ['lambda a', 'b: a']
```

End to end, against a repo where `compute(values)` takes one parameter:

```
### lambda arg (should be clean; compute takes 1)
   [arity/advisory] util_math.py:5 :: the patch calls 'compute' with 2 positional
   argument(s); the definition it resolves to takes 1
```

The module docstring promises the opposite:

> "Advisory, and deliberately timid: varargs, keyword arguments, decorators, methods and every other source of bound-argument ambiguity are passed over in silence rather than guessed at."

and `_positional_arguments`' own docstring: "None is 'do not judge this call'". `f(lambda a, b: a)` is one positional argument by Python's grammar.

Arguable as High — it is a demonstrably wrong claim about the patch from a six-token expression — but filed Medium because the severity emitted is `ADVISORY` and nothing gates on it.

Recommendation: return `None` from `_positional_arguments` when any top-level segment contains the token `lambda` (the same shape as the existing `*`/`=` bail-outs), and add the case to `TestArity` next to `test_an_unpacked_argument_makes_the_call_unjudgeable`.

### B15-M2 — The 3.10 TOML scanner can silently zero the declared set, which its docstring says is impossible
`src/agentless_mcp/core/patchlint.py:397-415`, `428-461`

The `else` branch's docstring claims a bounded failure mode:

> "What it does not understand -- inline tables, multi-line basic strings, a ``#`` inside a requirement string -- either yields nothing for that key or, at worst, an extra name in the declared set, **which can only make this check quieter and never make it accuse a real dependency**."

Measured against `tomllib` on the same input (probe compares both parsers directly):

| input | `tomllib` | `_scan_toml` |
| --- | --- | --- |
| `dependencies = ["requests"]  # TODO [see issue` | `{'deps': ['requests'], 'opt': {'mcp': ['fastmcp']}}` | `{}` |
| `"requests",  # pin [was 1.0` inside a multi-line array | `{'deps': ['requests'], 'opt': {'mcp': ['fastmcp']}}` | `{}` |
| `[project]  # the metadata` (trailing comment on a header) | `{'deps': ['requests']}` | `{}` |
| `project.dependencies = ["requests"]` (dotted key) | `{'deps': ['requests']}` | `{}` |
| `"pkg ; extra == \"x\""` (escaped quote) | `['requests', 'pkg ; extra == "x"']` | `['requests', 'pkg ; extra == \\', '']` |

Three of the five are total loss of the declared set, which combined with B15-H1 means "every third-party import in the patch is reported as hallucinated". Two mechanisms: the comment stripper at line 445 only fires when the line *starts* with `#`

```python
line = raw.split("#", 1)[0].rstrip() if raw.lstrip().startswith("#") else raw.rstrip()
```

so a bracket in a trailing comment corrupts the `depth` arithmetic at 438/455 and swallows the rest of the document into `pending`; and `_TABLE_HEADER` (`^\[\[?([^\]]+)\]\]?\s*$`) rejects a header carrying a trailing comment, so the following assignments are filed under the previous table.

Also, on this repository's *own* `pyproject.toml` the scanner and `tomllib` disagree today: the scanner reports a phantom dependency `this`, harvested from the quoted phrase in the comment at `pyproject.toml:52` sitting inside a multi-line array. The guarding test (`tests/unit/test_patchlint.py:241`, `test_the_scanner_agrees_with_tomllib_on_the_fixture`) uses a curated 18-line fixture and does not see it.

Reachable only on Python 3.10 (`sys.version_info >= (3, 11)` at line 388, the only version gate in `src/`), and there is no `.github/workflows` directory — nothing runs this package on 3.10 at all, so the gate behind this docstring's claim is one hand-picked fixture.

Recommendation, in order of preference: (a) drop the fallback and require `tomllib`, i.e. raise `requires-python` to `>=3.11` — the package supports 3.10 nowhere else and nothing else in `src/` is version-gated; (b) if 3.10 must stay, make the scanner fail loudly instead of quietly: return a parse warning when `depth` is still positive at EOF or when a `[project]`-family table was seen but no `dependencies` key resolved, and run the existing `TestTomlFallback` differential against this repository's real `pyproject.toml` rather than a fixture. Either way, fix the docstring, which currently states a guarantee the code does not hold.

### B15-M3 — `DEGRADED_ERRORS` swallows this module's own defects into a `not_checked` line, which its comment says it does not
`src/agentless_mcp/core/patchlint.py:176-188`, `662-674`

```python
# Failure modes a check may hit on hostile or merely odd input, each of which
# must degrade that check rather than the whole report. Named explicitly
# instead of catching Exception: an error class not in this list is a defect
# in this module and must surface as one.
DEGRADED_ERRORS: tuple[type[Exception], ...] = (
    AtlasError, ValueError, TypeError, KeyError, IndexError, AttributeError,
    UnicodeDecodeError, RecursionError, OSError,
)
```

The list contains `TypeError`, `KeyError`, `IndexError` and `AttributeError` — the four exception classes a defect in this module raises. The stated distinction ("an error class not in this list is a defect ... and must surface as one") therefore holds for approximately nothing: a `None` dereference, an off-by-one into `replace_columns`, a renamed field on `ASTSymbol`, all become

```
not checked: the check could not run over this patch (AttributeError)
```

with no traceback and no indication of which line inside the check failed. This is the global **Errors surface** invariant failing: the crash becomes a coverage note, and because `_guarded` wraps each of the seven checks independently, six checks still produce a clean-looking report.

Neither `_guarded` (666-667) nor `_fragment`'s handler (707-708) is executed by any test, so a regression that turns a check into a permanent `not_checked` line would not fail the suite.

Recommendation: narrow the list to what foreign input actually raises through this module's boundaries (`AtlasError`, `ValueError`, `RecursionError`, `OSError`), and if `AttributeError`/`KeyError` must stay for the extractor's tolerance of odd fragments, log the traceback into the finding's `evidence` so a real defect is diagnosable from the report. Add a test that a check raising a non-degraded error propagates, and one that a degraded error becomes exactly one gap.

### B15-M4 — Per-candidate work that is invariant across candidates: `_existing_bodies` is 92% of a lint call
`src/agentless_mcp/core/patchlint.py:948-1035`, `1014-1035`, `1406-1412`, `869-884`, `1716-1719`

Measured on this repository (110 files scanned):

```
scan: 0.39s over 110 files
lint_patch call 0: 0.154s      lint_patch call 1: 0.142s      lint_patch call 2: 0.142s
_existing_bodies: 0.141s
_defined_names:   0.000s
```

`_existing_bodies` re-normalises and SHA-256s **every function body in the repository** on every `lint_patch` call, and its result depends only on `RepoFacts` — never on the edits. `_available_packages`, `_defined_names` and the *pre*-patch half of `_cycle_delta` (`resolve.import_cycles(resolve.import_graph(list(facts.files.values())))`, line 1716) are the same shape.

`LintService.lint` loops candidates (`application/lint_service.py:61-67`) sharing one `RepoFacts`, and its docstring makes exactly this argument for the scan:

> "The scan happens once per call and is shared by every candidate, because the repository the candidates are judged against is the same repository for all of them -- and because scanning it per candidate would make a ten-candidate lint ten scans of the same unchanged tree."

The reasoning is right and stops one layer too early: a ten-candidate lint currently re-normalises the same unchanged tree ten times. On this 110-file repo that is 1.4s of pure repetition; the cost is linear in repository size, so on a few-thousand-file target it is the dominant cost of the command.

Recommendation: hang the four repo-derived indexes off `RepoFacts` as lazily-computed `functools.cached_property`-style values (the dataclass is frozen, so a small `_Indexes` value built once in `LintService._facts` and passed in is the cleaner shape). No behavior change; `RepoFacts` is an internal surface with one constructor site.

### B15-M5 — `_locate` does not resolve `...` elisions, so every finding on an elided edit silently loses its line number
`src/agentless_mcp/core/patchlint.py:758-774`, `729-755`

`_locate`'s docstring claims parity with the applier:

> "``(0, 0)`` when the search text is absent or occurs more than once, which is the same whole-line, ambiguity-refusing rule :mod:`agentless_mcp.core.patches` applies"

`patches._apply_one` does not match `edit.search` directly — it first calls `_resolve_elisions(edit.search, edit.replace, padded, scopes)` (`core/patches.py:407`), and elisions are a documented, supported patch form (`core/patches.py:42-44`: "``...`` **elisions** are honoured: a search block of just ``...`` is anchored to a unique unindented line in scope, and a leading ``...`` line on either side is dropped"). `_locate` searches the unresolved text and finds nothing.

Reproduced — same rename, once with a leading `...` line and once without:

```
apply_edits ok: True | new text: 'def helper_renamed():\n    return 1\n'
elided:  [dangling_callers/warning] helpers.py   :: the patch removes or renames 'helper'...
control: [dangling_callers/warning] helpers.py:1 :: the patch removes or renames 'helper'...
```

The finding survives; its location degrades from `helpers.py:1` to `helpers.py` with nothing said about why. `search_span` also degrades to `(0, 0)`, which disables the span half of `_is_the_replaced_site` (line 987-989) and leaves only name matching.

Recommendation: resolve elisions in `_fragment` before calling `_locate` and before `symbols_for(search_text, ...)`, by reusing `patches._resolve_elisions` (promote it to a public name — `patchlint` already imports `Edit` and `apply_edits` from that module, so no new coupling). Add a test asserting an elided edit's findings carry the same line as the non-elided form.

### B15-M6 — Module docstring states an isolation invariant the module violates
`src/agentless_mcp/core/patchlint.py:11-13`, `304-308`, `487-526`

```
"...this module never opens a cache, a repository or a file of its own."
```

and `RepoFacts`: "this module must not be able to open anything."

`read_declared_dependencies` (line 487) stats and reads `root/pyproject.toml` and every `root/requirements*.txt` through `read_bounded`. `lint_service`'s docstring repeats the claim from the other side — ":mod:`agentless_mcp.core.patchlint` owns the checks and knows nothing about repositories; this owns the one thing it must not -- reading the repository the patch is about" — and then calls `patchlint.read_declared_dependencies(ctx.root)` at line 82.

The code is not the wrong part: `core/cache.py` and `core/refs.py` also use `read_bounded`, so filesystem access in `core` is the established convention. The invariant is stated twice, in two modules, and is false both times — the specific hazard called out in Pass 1, since the next agent generating against these docstrings will assume `patchlint` is pure and testable without a filesystem.

Recommendation: either move `read_declared_dependencies` (and `parse_pyproject_dependencies` / `parse_requirements` / `_scan_toml`) into `application/lint_service.py` or its own `core/manifests.py` so the claim becomes true, or correct both docstrings to say that the *checks* open nothing and the manifest reader does. The first is preferable and pairs with B15-M7.

### B15-M7 — Three unrelated concerns in one 1761-line module
`src/agentless_mcp/core/patchlint.py` (whole file)

The module is the second largest in `core/` (extractor.py 2090, patchlint.py 1761, cache.py 1102) and holds:

1. **Dependency-manifest reading** — lines 384-622: filesystem access, a TOML scanner, a requirements parser, PEP 503 normalisation. Its only in-module consumer is one check, and its entry point (`read_declared_dependencies`) is called by the *service*, not by `lint_patch`. It is a separate module wearing this one's name.
2. **A hand-rolled Python expression/signature parser** — lines 1056-1299: `_structure`, `_literal_end`, `_inner_span`, `_split_top_level`, `_names_keyword_argument`, `_positional_arguments`, `_parameter_shape`. Reusable, independently testable, and the source of B15-M1.
3. **Seven checks plus the report value objects** — the rest.

The *public* interface is genuinely small (`lint_patch`, `RepoFacts`, `FragmentSource`, `Finding`, `LintReport`, `Severity`, `read_declared_dependencies`, the `CHECK_*` names), so the Deep Modules rule is satisfied at the boundary; the finding is internal cohesion, and it is what makes (1) and (2) hard to test in isolation — which is where the coverage gaps sit.

Recommendation: split into a `core/patchlint/` package (`manifests.py`, `pyexpr.py`, `checks.py`, `report.py`, `__init__.py` re-exporting today's names) with no change to the public surface. Gate the split on first pinning the unexecuted paths named in the coverage class — the string/comment scanner in particular, since it is the mechanism that keeps a docstring's brackets out of the arity parser and nothing would notice if a refactor broke it.

## Cross-block observations

- **B15 <-> B13 (`core/patches`).** `patchlint._locate` re-implements `patches._apply_one`'s matching rule and gets it partly wrong (B15-M5): the elision resolution is missing. This is the DRY rule failing in its dangerous direction — the same knowledge ("where does this search block land in the file") maintained in two places, with the copy already drifted. `_resolve_elisions` should become part of `patches`' public surface.
- **B15 <-> B10 (`core/refs`) / B01 (`core/extractor`).** `Ref.locally_bound` was added specifically so consumers could refuse to point a local use at a repository symbol (`extractor.py:344-348`), and `patchlint._reference_sites` ignores it (B15-H3). Worth checking every other consumer of `FileFacts.refs` across blocks for the same omission — a flag that only one of N consumers honours is a flag that does not exist.
- **B15 <-> B07 (`core/resolve`).** `patchlint` holds `facts.resolver` and uses it for `dangling_references` and `arity`, but not for `dangling_callers`, which is the one check where "does this reference actually point at the symbol" is the whole question. Cross-check whether other blocks resolve names by string equality against `refs` where a resolver was available.
- **Warning-channel convention.** `projectconfig.ProjectConfig.warnings` reaches the user through `application/envelope.py:83-86`, and the validate report has its own channel at `adapters/cli/main.py:1045`; `patchlint.DeclaredDependencies.warnings` has neither. Phase 6 should sweep every `warnings: tuple[str, ...]` field in `core/` for a delivery path — a warnings tuple with no consumer is a class of bug this codebase has at least twice-shaped machinery for.
- **Python floor.** `patchlint.py:388` is the only `sys.version_info` gate in `src/`, and it exists solely to avoid `tomllib`. There is no CI workflow directory in the repository, so no interpreter other than the developer's is exercised. Whether `requires-python = ">=3.10"` is a real contract or an aspiration is a repo-level decision that B15 cannot make alone, but the fallback it forces is this block's second-highest-risk code (B15-M2).

## Adversarial tests proposed

1. `test_a_lambda_argument_makes_the_call_unjudgeable` — `compute(lambda a, b: a)` against a one-parameter `compute` produces no `arity` finding.
