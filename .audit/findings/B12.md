## High

### B12-H1 — A trailing comment on a function's first body line destroys the sentinel and silently truncates the function
`src/agentless_mcp/core/skeleton.py:188-200` (with `_Plan.replace`, `skeleton.py:81-85`)

```python
def _plan_comment(node: Node, lines: list[str], plan: _Plan) -> None:
    ...
    plan.drop_range(first + 1, last)
    plan.replace(first, line[:column].rstrip())
```

`_walk` yields parents before children, so `_plan_function` runs first and sets `replaced[body_first] = "    ..."`. The comment node is a descendant, arrives later, and `plan.replace` overwrites that entry with the real source line — and `replace` also calls `self.dropped.discard(line)`, un-dropping it.

Measured:

```
skeletonize("def f(x):\n    y = compute(x)  # note the tax\n    return y\n", "python")
-> 'def f(x):\n    y = compute(x)\n'
```

The elision marker is gone entirely, `return y` has vanished with no marker, and the leaked body line is presented as the whole function. A one-line-body function and a truncated twenty-line body are now indistinguishable in the output — the exact failure the module docstring claims not to have ("every function body is replaced by a `...` sentinel"). The variant where the comment sits on a later body line leaks that line instead:

```
skeletonize("def f(x):\n    y = compute(x)\n    return y  # done\n", "python")
-> 'def f(x):\n    ...\n    return y\n'
```

Failure scenario: `get_skeleton` over any real repository (trailing comments are ubiquitous) hands the agent a function that looks complete and is not; the agent localizes or patches against code that does not exist as shown.

Recommendation: give `_Plan` a precedence rule instead of last-write-wins — a line already claimed by a function-body elision is owned by that elision and neither comment trimming nor docstring handling may write it. Concretely, have `_plan_function` record `body_first..body_last` in an `owned` set that `replace` refuses to overwrite, and skip comment planning for nodes inside an owned range.

### B12-H2 — An unsatisfiable interval renders the whole file as if it were the requested slice
`src/agentless_mcp/core/slices.py:119-130`

```python
    for start, end in merge_intervals(intervals):
        low = max(1, start)
        high = total if end == -1 else min(total, end)
        if low <= high:
            clipped.append((low, high))
    return clipped or [(1, total)]
```

`clipped or [(1, total)]` conflates two opposite requests: "no interval was asked for, show me the file" and "the interval asked for cannot be satisfied". Commit b7a97ca fixed exactly this dishonesty, but only in one caller (`view_service.read_slice` now reports `start > total` per item); the primitive still lies, and two live paths reach it.

Reachable through MCP — `adapters/mcp/server.py:557-559` builds intervals from `list[list[int]]` with no ordering or sign validation (the CLI's `_parse_ranges`, `main.py:1383`, does validate `start < 1 or end < start`):

```
ViewService.read_slice(ctx, "big.py", intervals=[(60, 30)], context=10)  # 100-line file
-> 101 lines rendered; first "1|SECRET_1 = 1", last "101|"   # entire file, no elision marker
```

Reachable through stale symbols — `locs.py:140-146` clamps only the high end of a widened span (`min(target.total_lines, end + context)`), never the low end, so a symbol whose line numbers outlive the file on disk produces a reversed interval that is reported as a resolution and rendered as the whole file:

```
symbol at lines 900-910, file now 30 lines
-> spans=((900, 910),) intervals=((890, 30),) unrecognized=()
   line_wrap_content(text, [(890, 30)]) -> all 30 lines, no marker
```

Failure scenario: an agent asks for lines 60-30 (transposed arguments, or a stale span after an edit) and receives the whole file with no indication that its request was discarded — the token blow-up the slice API exists to prevent, plus a false belief that the returned lines are the requested region.

Recommendation: split the two meanings. Keep `intervals is None/empty -> whole file`, and make a non-empty request that clips to nothing an error the caller must handle (raise, or return a typed "unsatisfiable" result) rather than a silent whole-file fallback. Separately, clamp both ends in `resolve_locs` and report a span that no longer fits the file through `unrecognized`, and validate `1 <= start <= end` at the MCP boundary the way the CLI already does.

### B12-H3 — Nested functions emit a stray over-indented sentinel, producing output that is not valid source
`src/agentless_mcp/core/skeleton.py:150-185`

The outer function's body is dropped and replaced with one sentinel; the inner function node is then visited and `plan.replace(inner_body_first, indent + SENTINEL)` un-drops a line inside the already-elided outer body.

```
skeletonize("def outer(a):\n    def inner(b):\n        return b + 1\n    return inner(a)\n", "python")
-> 'def outer(a):\n    ...\n        ...\n'
```

That is an `IndentationError` if anyone re-parses it, and it is meaningless to a reader: the `inner` signature the second sentinel belongs to was elided. Every closure, decorator factory and callback-heavy JS/TS file hits this.

Failure scenario: skeletons of any module using nested functions or JS arrow-function callbacks contain orphan sentinels; a consumer that re-parses the skeleton (or an agent asked to patch relative to it) sees broken structure.

Recommendation: same ownership fix as B12-H1 — once a range is claimed by an enclosing elision, inner function planning is a no-op. Alternatively walk top-down and prune descendants of any node already planned.

### B12-H4 — tree-sitter columns are byte offsets, sliced as character indices; any non-ASCII on the line corrupts the output
`src/agentless_mcp/core/skeleton.py:158-171`, `188-200`, `272-281`

```python
    body_column = body.start_point[1]
    ...
    prefix = signature_line[:body_column].rstrip()
    opens_brace = signature_line[body_column : body_column + 1] == "{"
```

`start_point[1]` is a byte column; `signature_line` is a `str`. Every multi-byte character before the body or comment start shifts the slice right by one position per extra byte.

```
skeletonize('package main\n\nfunc Café(s string) string { return s }\n', "go")
-> 'package main\n\nfunc Café(s string) string { ...\n'     # unbalanced brace
skeletonize('package main\n\nfunc Cafe(s string) string { return s }\n', "go")
-> 'package main\n\nfunc Cafe(s string) string { ... }\n'   # ASCII control, correct

skeletonize('def f():\n    s = "café ☕ naïve"  # trailing comment\n    return s\n', "python")
-> 'def f():\n    s = "café ☕ naïve"  # tr\n'                # comment sliced mid-word
```

Failure scenario: any repository with accented identifiers, emoji in string literals, or non-English comments yields skeletons with unbalanced braces and half-comments — and the Go/TS case silently loses the `}` that makes the brace-language skeleton parseable.

Recommendation: convert byte columns to character indices once at the boundary (`len(line_bytes[:column].decode("utf-8"))`, or keep the encoded `data` from `skeletonize` and slice bytes throughout instead of `source.split("\n")`). Add a non-ASCII fixture to the golden corpus so the conversion is pinned.

## Medium

### B12-M1 — The trailing newline is counted as a line, so every whole-file view ends in a phantom line
`src/agentless_mcp/core/slices.py:93-94`, `src/agentless_mcp/core/locs.py:283-285`

```python
    lines = content.split("\n")
    total = len(lines)
```

A POSIX file ending in `\n` splits to a trailing `""`. Measured on a real two-line file:

```
line_wrap_content("a\nb\n")               -> '1|a\n2|b\n3|'
resolve_locs(["line: 3"], target)         -> spans=((3, 3),)          # a line that does not exist
resolve_locs(["line: 4"], target)         -> "line 4 is outside f.py (1-3)"
```

The 100-line probe file in B12-H2 rendered a final `101|`. So every whole-file `read_slice` emits a phantom last line, `line: N+1` resolves silently, and the out-of-range message advertises a line count one greater than `wc -l`.

Failure scenario: an agent told the file has 101 lines requests line 101, gets an empty line back, and reasons about a file boundary that is off by one; a patch anchored on the reported last line targets nothing.

Recommendation: drop a single trailing empty element when computing `total` (keep it in `lines` for indexing, or use `splitlines()`), and do it once — `view_service` computes `len(text.split("\n"))` twice more, so the definition belongs in this block and should be exported.

### B12-M2 — `class:` and `variable:` silently pick the first match and reject the ordinal spelling their own ids use
`src/agentless_mcp/core/locs.py:185-192`, `288-302`

```python
    if not matches:
        return _Hit(reason=f"no class named {name!r} in {target.path}")
    return _Hit(span=_span(matches[0]), stable=_id(matches[0], target))
```

The module docstring promises "Nothing is dropped silently", and `_resolve_unqualified_method` states the principle ("an ambiguous location is a question for the caller, not a coin flip") — but only the function branch honours it. `_resolve_function` also splits the `#N` ordinal "at the one door every function-shaped location comes through"; `class:` and `variable:` never call `split_ordinal`. Measured on a file defining `Dup` twice and `MAX` twice:

```
'class: Dup'      -> ids=('py:d.py::Dup',)     # second Dup unreachable, no note
'class: Dup#2'    -> "no class named 'Dup#2' in d.py"
'variable: MAX#2' -> "no module-level constant named 'MAX#2' in d.py"
```

`id_qualname`/`apply_ordinal` spell the second symbol `Dup#2`, so an id read off `get_symbols_overview` cannot be fed back as a `class:` location, while the equivalent function id can.

Failure scenario: a conditionally-defined class (`if TYPE_CHECKING:` / platform branches) resolves to whichever copy came first, and the agent reads the wrong body without any ambiguity warning.

Recommendation: route both branches through `split_ordinal` + `_pick`, exactly as `_resolve_function` does; `_pick` already produces the right reason for a missing ordinal and the right ambiguity behaviour.

### B12-M3 — Sticky headers repeat lines already rendered as content, so line numbers go backwards
`src/agentless_mcp/core/slices.py:133-164`; test `tests/unit/test_slices.py:89`

`shown_scopes` is populated only by `_scope_header_lines`, never by the main render loop, so a header emitted as ordinary slice content is re-emitted as a header later:

```
line_wrap_content(SRC, [(1, 2), (6, 6)], symbols=syms)
1|class Widget:
2|    def render(self):
...
1|class Widget:
2|    def render(self):
...
6|        d = 4
...
```

The docstring's claim — "never repeating a header the same render already showed" — is false, and `test_scope_headers_are_not_repeated_across_intervals` only covers the case where both showings are headers. With `no_line_number=True` the duplication is invisible: the output reads as source with two copies of the class header.

Failure scenario: a consumer (or an agent) reading the slice sees non-monotonic line numbers and duplicated content; the `no_line_number` form is an outright false reconstruction of the file.

Recommendation: record every rendered line number in `shown_scopes` (or a shared `emitted` set) as the main loop emits it, so a header already visible is never repeated.

### B12-M4 — `_Plan` has three writers and no ownership rule
`src/agentless_mcp/core/skeleton.py:70-85`, `107-113`

```python
    def replace(self, line: int, text: str) -> None:
        """Replace one line, un-dropping it if an earlier rule dropped it."""
        self.dropped.discard(line)
        self.replaced[line] = text
```

Function planning, comment planning and docstring planning all write the same `dropped`/`replaced` maps, last write wins, and `replace` is documented to *undo* another rule's decision. There is no statement anywhere of which rule outranks which. B12-H1 and B12-H3 are both instances of this single design gap, which is the global "one owner per state change" rule failing: the invariant "an elided body emits exactly one sentinel and no source" has no owner.

Recommendation: make the precedence explicit in `_Plan` (an `owned` range set that `replace` and `drop_range` respect, or per-rule priority levels), and assert it — a plan that would resurrect a line inside an elided body should be a test failure, not silent output.

### B12-M5 — Prefixed docstrings are rendered as syntactically broken output
`src/agentless_mcp/core/skeleton.py:259-269`

```python
    quote = '"""' if '"""' in text else ("'''" if "'''" in text else text[:1])
    inner = text.strip()
    if quote and inner.startswith(quote) and ...
```

For `r"""..."""` / `b"""..."""` / `f"""..."""` the text starts with the prefix letter, so `inner.startswith(quote)` is false, the quotes are never stripped, and the result is wrapped again:

```
skeletonize('def f():\n    r"""Raw doc."""\n    return 1\n', "python", docstrings=True)
-> 'def f():\n    """r"""Raw doc.""""""\n    ...\n'
```

Failure scenario: with `docstrings=True` (the `--docstrings` view), any regex- or bytes-heavy module produces skeleton lines that are not valid Python and that a reader parses as two adjacent strings.

Recommendation: strip an optional string prefix (`[rRbBuUfF]{1,2}`) before quote detection, and preserve it in the rendered form or drop it deliberately.

### B12-M6 — The trailing-comment path is executed but unasserted; the golden corpus excludes every failing shape
`tests/characterization/test_skeleton.py`, `tests/characterization/fixtures/`

`tests/unit` executes `skeleton.py:199-200` (full-suite coverage shows only 239 and 254 missing) yet no test asserts the output of that branch, which B12-H1 shows is wrong. The golden fixtures contain zero trailing comments, zero nested functions, zero non-ASCII characters, zero tabs and zero CRLF. 99% line coverage on this module is therefore not evidence about correctness — the corpus was curated to idiomatic, ASCII, flat-function code.

Recommendation: add fixture files (or a `TestSkeletonSemantics` case per shape) covering: a trailing comment on a body's first and later lines, a nested function, a non-ASCII identifier in a brace language, a tab-indented function, and a CRLF file. Each of the four High findings above is a one-assert regression test.

## Low

### B12-L1 — The `end == -1` interval sentinel is dead and collides with negative input
`src/agentless_mcp/core/slices.py:127`. No production caller passes `-1` (`view_service` widens intervals before calling, so the sentinel can never survive), and no test exercises it — `slices.py` reports 100% line coverage because the branch shares a line. Meanwhile a genuinely negative interval like `(-9, -1)` is read as "to end of file" and then discarded, landing in the B12-H2 whole-file fallback. Delete the sentinel or give it a test and a documented caller.

### B12-L2 — `if target.total_lines` disables the line bound check for a value no caller produces
`src/agentless_mcp/core/locs.py:143`, `283`. Both `view_service.resolve_locations` and the CLI compute `total_lines` from the file, so the `total_lines == 0` fallback (which silently turns off clamping and the "outside the file" check) is unreachable defensive code. Either make `total_lines` non-optional in `LocTarget` and drop the guard, or model "unknown length" explicitly.

### B12-L3 — The trailing-blank trim does not work with `number_lines=True`
`src/agentless_mcp/core/skeleton.py:301-302`. `rendered[-1].strip().rstrip("|")` is clearly meant to catch the numbered blank line `f"{number}| "`, but `"3| ".strip().rstrip("|")` is `"3"` — truthy — so the loop stops:

```
skeletonize("def f():\n    return 1\n\n\n# trailing comment\n\n\n", "python", number_lines=True)
-> '1| def f():\n2|     ...\n3| \n'
```

The unnumbered form trims correctly. Compare the number, not the text.

### B12-L4 — `compression_ratio` is production code with no production caller
`src/agentless_mcp/core/skeleton.py:118-125`. Used only by `tests/characterization/test_skeleton.py:76` and `tests/unit/test_tier2_languages.py:156`. Two lines of arithmetic; move it into the test helper or name a real consumer.

### B12-L5 — The citation gating the compression band is garbled
`tests/characterization/test_skeleton.py:13`: "SWEzze 2603.28119: ~6x beats full context, 22-50x is harmful". The arXiv id is real — 2603.28119 is *Compressing Code Context for LLM-Based Issue Resolution* (verified against the corpus reference list in `code-as-agent-harness--2605.18747.pdf`) — but "SWEzze" names no paper, and the closest corpus source for compression-ratio bands is SWE-Pruner (2601.16746), which reports 4x and 8x constraints, not 6x/22-50x. A hard-coded `MIN_RATIO = 3.0` / `MAX_RATIO = 9.0` assertion should cite a source a reader can check. Fix the title or drop the numbers.

### B12-L6 — Tab-indented and CRLF sources render oddly
`src/agentless_mcp/core/skeleton.py:176`, `284-304`. `indent = " " * body_column` turns a tab-indented body into a one-space sentinel (`'def f():\n ...\n'`), and CRLF input keeps the `\r` on surviving lines while replaced lines get plain `\n` (`'def f():\r\n    ...\n'`), so the skeleton has mixed line endings. Both are cosmetic today; both become B12-H4-adjacent once byte columns are fixed. Reuse the source line's own leading whitespace instead of synthesising spaces.

## Cross-block observations

- **Boundary validation asymmetry between the CLI and the MCP adapter.** `adapters/cli/main.py:1372-1386` validates `start >= 1 and end >= start`; `adapters/mcp/server.py:557-559` accepts any `list[list[int]]` of length two. Every finding in B12-H2 that is reachable at all is reachable only through MCP. Whoever reviews the adapter blocks should check whether this is a general pattern — the CLI parsing the input the MCP tool trusts.
- **Fix-in-the-caller pattern.** b7a97ca fixed the silent whole-file fallback in `view_service.read_slice` rather than in `slices._clamp`, leaving the primitive with the same trap for the next caller. If other blocks show the same shape (guard added at one call site, invariant left unenforced in the primitive), that is a codebase-level finding.
- **`end_line_number is None` has two contradictory meanings across this block.** `slices.py:147` treats a symbol with no end line as enclosing everything after it (so it becomes a sticky header for every later slice); `locs.py:307` treats it as a one-line span. The extractor always sets an end line, so this is reachable only from a cache row written by an older build (`core/cache.py:837` decodes NULL to `None`) — worth confirming with whoever reviews the cache block whether NULL end lines can still be persisted.
- **The skeleton golden corpus is shared infrastructure.** Adding the fixture shapes recommended in B12-M6 will churn goldens used by the map/graph/lint characterization suites in other blocks; the new shapes are better added as separate fixture files than by editing `repo_py/repo_ts/repo_go`.
