## High

### B22-H1 — client-advertised roots are added to the authorization allowlist with no containment check, so `--root` is not a confinement boundary
`src/agentless_mcp/adapters/mcp/server.py:187`

```python
allowed = list(dict.fromkeys([*self._roots, *client_roots]))
```

`client_roots` comes straight from `effective_client_roots()` (line 443), which is whatever the connected client answered `roots/list` with. It is unioned into `allowed` and then handed to `resolve_repo(..., allowed)`, where `_authorise` (`application/repo_context.py:96`) accepts any exact member. Nothing anywhere compares an advertised root against the configured `--root` set before trusting it.

The `--root` flag's own help text (line 674) reads `"a repository this server may serve; repeatable"`, and `repo_context.py`'s module docstring states the model as *"A server started with `--root /a --root /b` serves those two directories and nothing under, beside or symlinked from them."* That statement is true of the CLI and false of this adapter.

**Failure scenario.** An operator runs `agentless-mcp-server --root /srv/checkouts/billing`, intending to confine the process to one repository. A user then opens their home directory as the workspace in the MCP client. The client advertises `file:///home/alice`; `allowed` becomes `[/srv/checkouts/billing, /home/alice]`; the model calls `read_slice` with `repo_root=/home/alice, path=".ssh/id_rsa"` — `contained_path` passes because `/home/alice/.ssh/id_rsa` is inside `/home/alice` — and the private key is returned inside a tool result the model reads. No operator action, no warning in the receipt, no log line above `debug`.

**Recommendation.** Decide which of the two models this is and enforce it. If `--root` is a confinement boundary, intersect rather than union: an advertised root may only *select* among configured roots (which is exactly what `_sole_selection`'s `candidates` computation already does) and may never authorize a path outside them; when no static root is configured, either refuse to serve or require an explicit `--allow-client-roots` opt-in. If it genuinely is additive, say so in `--root`'s help text and in `docs/agent-guide.md`, and make `capabilities` mark client-advertised roots as authorizing rather than listing them alongside the configured ones as if they were informational.

### B22-H2 — `effective_client_roots` turns malformed URIs into authorized roots: `file://` becomes the server's cwd, and the URI authority is silently discarded
`src/agentless_mcp/adapters/mcp/server.py:458-463`

```python
parsed = urlparse(str(root.uri))
if parsed.scheme != "file":
    logger.info("ignoring non-file MCP root %s", root.uri)
    continue
paths.append(Path(unquote(parsed.path)).resolve())
```

Measured behaviour (`python3 -c` against the same `urlparse`/`unquote`/`Path.resolve` chain, run from the repo root):

```
'file://'             -> scheme=file netloc=''     path=''       -> /home/dallasmarlow/.../agentless-mcp
'file://host/etc'     -> scheme=file netloc='host' path='/etc'   -> /etc
'file:///a/../../etc' -> scheme=file netloc=''     path='/a/../../etc' -> /etc
```

Three separate defects in one four-line parse:

1. **Empty path resolves to the process cwd.** `Path("").resolve()` is `os.getcwd()`. A client that advertises `file://` — or any URI whose path component is empty — silently authorizes whatever directory the server happens to have been launched from. This is precisely the failure the module docstring says the design avoids: *"there is no cwd to infer a root from and inferring one would be a wrong-repository answer"* (lines 6-8). The code infers one, from a malformed input, and grants it authorization.
2. **The authority component is dropped.** `file://some-host/etc` is a root on `some-host`, not on this machine, and it is accepted as local `/etc` without so much as a log line. RFC 8089 permits a non-empty, non-`localhost` authority; the correct handling is to reject it, not to ignore it.
3. **No result validation.** The resolved path is never checked for existence, for being a directory, or for being anything other than `/`. `file:///` yields `Path("/")`, which combined with B22-H1 authorizes the entire filesystem.

This is the block's one parse of foreign data and it violates Boundary integrity on every count: no single parse-or-raise step, no typed refusal, malformed input coerced into a plausible-looking value.

**Failure scenario.** A buggy or hostile client advertises `file://`. The server's launch directory — for a systemd unit or a `uvx` invocation, often `/` or the operator's home — becomes an allowed root, and with a single configured root the `len(allowed) == 1` shortcut at line 105 no longer applies, so `_sole_selection` may even default to it (line 116-117). Nothing is logged above `DEBUG`/`INFO`.

**Recommendation.** Parse-or-drop, explicitly and with a warning: require `parsed.scheme == "file"`, require `parsed.netloc in ("", "localhost")`, require `parsed.path` non-empty and absolute, and require the resolved path to be an existing directory. Log every rejection at `warning` with the offending URI. Add unit tests over `effective_client_roots` with a stub `Context` covering `file://`, `file://host/x`, `http://…`, a percent-encoded path with spaces, and a path that does not exist.

### B22-H3 — `context.list_roots()` is awaited on every tool call with no timeout
`src/agentless_mcp/adapters/mcp/server.py:451, 483, 657`

```python
try:
    roots = await context.list_roots()
except McpError as exc:
    logger.debug("client does not advertise MCP roots (%s); using --root only", exc)
    return []
```

`list_roots()` is a JSON-RPC request *back* to the client over stdio — an out-of-process call, made on the critical path of all eleven tools via `context_for` (line 483). There is no `asyncio.timeout`, no `wait_for`, no cancellation. The global rule is unconditional: *"Every network or out-of-process call gets a timeout."*

The `except McpError` is also narrower than the failure set. A client that answers `roots/list` with a payload that fails pydantic validation raises a `ValidationError`, not an `McpError`, and takes down the tool call with an unrelated message; a transport that dies mid-request raises an `anyio` exception. The docstring's framing — *"A client without the capability answers with an McpError, which is a negative result rather than a failure"* — is correct for the one case it names and silent about the rest.

**Failure scenario.** A client that advertises the `roots` capability during initialize but never responds to `roots/list` (a real class of bug in early MCP client implementations) hangs every single tool call forever. The server has no other work to do, the model waits, and the only symptom is a tool that never returns.

**Recommendation.** Wrap the await in `asyncio.timeout(...)` with a small budget (a client-side capability query should answer in well under a second) and treat expiry the same way as `McpError` — log and fall back to static roots. Broaden the `except` to also catch `ValidationError` and `Exception` from the transport with the same fallback, since none of them are recoverable-by-retry and all of them mean "no advertised roots". Separately, consider caching the answer per session rather than re-querying on every call.

### B22-H4 — the `capabilities` tool description and the agent guide both promise "the caps in force"; the MCP handler emits no caps at all
`src/agentless_mcp/adapters/mcp/server.py:345-374`

### B22-M1 — `read_slice` silently discards malformed line ranges instead of refusing them
`src/agentless_mcp/adapters/mcp/server.py:557-559`

```python
intervals = [
    (pair[0], pair[1]) for pair in (lines or []) if len(pair) == _RANGE_PAIR_LENGTH
]
```

A client sending `lines=[[10, 20, 30]]`, `lines=[[10]]`, or `lines=[[]]` gets those entries dropped without a word. Worse, when *every* entry is malformed the list collapses to `[]`, and `ViewService.read_slice` documents `[]` as meaning "no intervals requested" — its own docstring warns that empty intervals "would leave no intervals and render the whole file as if it were the requested slice" (`view_service.py:158-161`). So `read_slice(path=X, lines=[[1,2,3]])` returns the *entire file*, which is exactly the substitute-content behaviour the tool description promises never to do: *"never answered with substitute content"*.

No ordering check either: `[20, 10]` passes the length test and is handed downstream as a backwards interval.

**Failure scenario.** A model emits a three-element range (an easy off-by-one against a `[start, end, step]` mental model), and instead of a correction it receives the whole file — silently blowing the context budget and giving the model no signal that its call was wrong.

**Recommendation.** Parse the ranges in one step that either yields typed intervals or raises `AtlasError` naming the offending entry: reject any pair whose length is not 2, whose members are not positive ints, or whose start exceeds its end. Delete `_RANGE_PAIR_LENGTH` as part of that — a named constant for "2" is only carrying the silent filter.

### B22-M2 — no numeric bound on any tool parameter, at the one boundary where every argument is model-generated
`src/agentless_mcp/adapters/mcp/server.py:512-513, 540, 553, 568, 583, 597, 616-618, 648`

Every integer and float on the wire is an unconstrained `int` / `float` / `int | None`: `depth`, `max_entries`, `limit` (five tools), `context_lines`, `budget`, `max_files`, `max_nodes`, `resolution`. `pydantic.Field` is already imported and used at line 86 to attach a description, so `Field(ge=1, le=...)` is one keyword away and is what publishes the bound into the JSON schema the client validates against — the only enforcement point that stops a bad value before it reaches a service.

The downstream handling is inconsistent. `core/mermaid.py:253` does validate (`if settings.max_nodes < 1: raise`). `symbol_service.py` does not: `matches[:limit]` (line 190), `stable_ids[:limit]` (206) and `sites[:limit]` (247) are raw slices. `limit=-3` on `expand_symbols` therefore drops the last three ids and reports them as `"not expanded: the per-call limit is -3 symbols"` — a nonsense receipt describing a nonsense truncation as if it were a policy. `limit=0` on `find_symbol` returns zero cards while claiming a total.

**Failure scenario.** A model retries with `limit=-1` after a truncation warning (a plausible "unlimited" idiom) and receives a result set silently missing its last element, with a receipt that asserts the answer is complete-to-limit.

**Recommendation.** Annotate each numeric parameter with a `Field` carrying `ge`/`le` matching the value's real domain, so the refusal happens in schema validation with a message the model can act on. Where a service already validates (mermaid), keep that check as the invariant's owner; where it does not, the boundary annotation is the only gate.

## Cross-block observations

**Ruling on the root-authorization model — what the code does vs what the docs claim.** They do not match, and the mismatch runs in the permissive direction on both counts.

*What the docs and docstrings claim.* `repo_context.py`'s module docstring: a server started with `--root /a --root /b` *"serves those two directories and nothing under, beside or symlinked from them"* — `--root` presented as the confinement boundary, containment explicitly rejected as too loose. `server.py`'s module docstring, first paragraph: `repo_root` *"is checked, exactly, against the roots the server was started with."* `--root`'s argparse help: *"a repository this server may serve."* `docs/agent-guide.md:136-140`: an omitted `repo_root` defaults *"when the client advertises an MCP workspace root that identifies exactly one **configured** root."*

*What the code does.* `server.py:187` unions the client's advertised roots into the allowlist before authorization, so any directory the client names becomes servable (B22-H1) — including a directory produced by a malformed URI, since `file://` resolves to the server's cwd and `file://host/path` silently discards the host (B22-H2). And `_sole_selection`'s final branch (line 116-117) defaults to a single advertised root that identifies *no* configured root, which is the opposite of the guide's "identifies exactly one configured root" (B22-M4).

*Ruling.* The intended model is **static roots authorize, client roots select** — that is what `_sole_selection`'s `candidates` computation implements, what the guide describes, and the only reading under which `--root` means anything. The code implements **static roots and client roots both authorize, and client roots also select**, and `server.py`'s own docstring contradicts itself inside four sentences about which it is. Every doc surface should be treated as describing the *intended* model, not the shipped one, until B22-H1 is resolved.

**Flags for other blocks:**

- **B22 → repo_context (application).** `_authorise` is a correct exact-match check over whatever list it is handed; the defect is entirely in what B22 hands it. But `repo_context.py`'s module docstring makes the `--root`-is-confinement claim on behalf of a caller that breaks it, so the fix touches both blocks. Whoever reviews `repo_context` should not read that docstring as evidence the property holds.
- **B22 → CLI adapter.** `_with_source` / `_context` duplication (B22-M3) and the diverged `capabilities` rendering (B22-H4) are one shared-knowledge problem spanning both adapters. The import-linter independence contract (`pyproject.toml:271-274`) means the shared home has to be in `application/`, so this is a cross-block fix, not a B22-local one.
- **B22 → symbol_service.** Unvalidated `limit` arriving from B22 is sliced raw at `symbol_service.py:190, 206, 247`, and `expand_symbols` reports the caller's negative limit back in a user-facing receipt string (line 214). Whether the bound belongs at the adapter (schema `Field`) or the service (`raise` on `limit < 1`) is a cross-block decision; `core/mermaid.py:253` already chose the service side for `max_nodes`, so the repo is currently inconsistent with itself.
- **B22 → view_service.** `ViewService.read_slice`'s documented handling of an empty `intervals` list (render the whole file) is safe only if every caller guarantees non-empty-after-filtering. B22 does not (B22-M1). The CLI's path into the same method should be checked for the same hole.
- **B22 → prompts.** `tests/unit/test_prompts.py` enforces key-set sync and verbatim publication but nothing about *truthfulness*. B22-H4 is the first confirmed case of a tool description promising behaviour the handler lacks; the same gate is absent for all eleven descriptions, so this is a class of defect the prompts block cannot currently catch.
