# Architect panel review — agentless-mcp

Independent structural-integrity pass over the 24-block audit (`.audit/progress.md`,
`.audit/findings/B01.md`-`B24.md`) plus the Phase-1 coupling metrics. Findings below are
systemic — cross-block patterns and single-module design failures large enough to shape how
the codebase evolves — not per-line defects, which the per-block reviewers already own.

finding_id: 1
persona: ARCHITECT
severity: CRITICAL
scope: system
files: [src/agentless_mcp/adapters/mcp/server.py, src/agentless_mcp/adapters/cli/main.py, src/agentless_mcp/application/symbol_service.py, src/agentless_mcp/application/graph_service.py, src/agentless_mcp/application/view_service.py, src/agentless_mcp/application/map_service.py, src/agentless_mcp/core/mermaid.py, src/agentless_mcp/core/communities.py]
category: coupling
issue: The design's stated invariant — "both adapters call the same application services and neither owns any behaviour of its own" (adapters/cli/main.py module docstring) — is false for input validation specifically. Bound and range checking for the same parameters is implemented in the CLI adapter and omitted on the MCP adapter, independently, on at least six different parameters across six different services. The application/domain layer trusts "the adapter checks" instead of owning its own invariants, so the service layer's correctness depends on which front door a caller used.
evidence: Independently sighted and measured in B11 (communities `resolution`: CLI unchecked too, only `core/mermaid._validate` for `max_nodes`), B12-H2/B17-H1 (`read_slice` intervals: CLI's `_parse_ranges` validates `start<1`/`end<start`, MCP's `server.py:557-559` accepts any `list[list[int]]`), B17-M1 (`repo_map` budget/max_files/granularity: `core/projectconfig.py` validates the config-file path strictly, the live request path does not), B18-M2/B22-M2 (`limit` is a bare unconstrained `int` on every MCP tool; `limit=0` or negative produces a confidently wrong "no matches"/"no references" answer with no error), B19-M1 (`max_nodes`/`members`: CLI guards with `fail()`, `analyze_structure` does not, so a bare `ValueError` escapes as an unhandled exception instead of the typed `AtlasError` every other refusal uses), B22-M1 (`read_slice` line-range unpacking silently drops malformed entries down to `[]`, which `ViewService` then treats as "no intervals" and renders the whole file — the exact "substitute content" failure the tool description promises never happens). The progress.md cross-block log independently names this "the MCP-validates-less pattern" at least four times (B17, B18, B19, B22 cross-block notes) — four different reviewers rediscovering the same architectural gap from four different services.
source: Clean Architecture (Martin) — a use case / interaction boundary must enforce its own preconditions; an entity or service that trusts its caller to have validated input has an unstated, unenforced contract. Also the Engineering Invariants rule in this repo's own CLAUDE.md ("Guards key on the invariant, not a proxy") applied at the architecture level: the proxy here is "which adapter this request arrived through."
recommendation: Move bound validation for every numeric/range/enum parameter into the application-service entry point it already exists to serve (the pattern `core/mermaid._validate` already gets right for `max_nodes`). Once services own their own preconditions, delete the now-redundant CLI-side argparse guards rather than maintaining two copies. Add one MCP-adapter test class that, for every tool with a numeric parameter, asserts a boundary-invalid value produces a typed `AtlasError`-shaped tool error, not a transport-level crash or a silently wrong answer.
confidence: HIGH

finding_id: 2
persona: ARCHITECT
severity: HIGH
scope: module
files: [src/agentless_mcp/core/extractor.py]
category: SRP
issue: extractor.py sits in the software-architecture "zone of pain": high afferent coupling (Ca=14 — the second-most-depended-on module in the repo after util.errors and core.symbols), low instability (I=0.18, meaning it is hard to change without breaking many callers), and near-zero internal abstraction — 2090 LOC, 77 top-level names, one flat namespace mixing four unrelated concerns behind no internal seam. The module's own comment concedes the arrangement is by loose association rather than by responsibility.
evidence: B07-M6 documents the four concerns concretely: (a) generic tree-sitter node-walking, (b) three shared node-type vocabulary tables (COMMENT_NODE_TYPES, INDENT_BLOCK_NODE_TYPES, BODY_BLOCK_NODE_TYPES) that extractor.py itself barely reads but that core/normalize.py, core/skeleton.py and core/patchlint.py import directly, and (c) ~79 lines of Python-only binding-scope analysis (_PYTHON_SCOPE_FIELDS, _python_binding_scopes, _locally_bound) reachable only through one `if language == "python"` special case — the single place in the file that branches on a language name outside its own registry, contradicting the module's stated "language support is registry-driven, single dispatch" design. B07-C1 separately shows four hand-recursive walkers inside this file blow the stack at ~250 chained calls and abort a whole-repository index — exactly the kind of defect a 2090-line module with no internal boundary makes easy to introduce and hard to catch, since the walker discipline (iterative vs recursive) is inconsistent within the file itself.
source: Fundamentals of Software Architecture (Ford & Richards) — the stability/abstractness metrics and "zone of pain" quadrant (low I, low A, high Ca): a concrete, widely-depended-on module accrues the highest cost to change of anything in the system. Also Clean Code (Martin) — SRP as "a class should have one reason to change"; this module has at least four.
recommendation: Move the three shared node-type tables into a neutral `core/nodetypes.py` that extractor, normalize, skeleton and patchlint all import (mechanical, no behavior change — this is also what removes normalize.py's and skeleton.py's current dependency on the extractor internals). Move the Python-only binding-scope analysis into `core/pybinding.py`, invoked through a per-language hook from `collect_refs` rather than a special case inside the generic walker. This is explicitly flagged in the audit as the single highest-value mechanical refactor in the dependency graph and the two moves are independently safe to land before any other extractor change.
confidence: HIGH

finding_id: 3
persona: ARCHITECT
severity: HIGH
scope: cross-module
files: [src/agentless_mcp/application/repo_context.py, src/agentless_mcp/adapters/mcp/server.py]
category: abstraction
issue: The security/trust-boundary contract for repository authorization is stated three times and enforced consistently in none of them. repo_context.py's module docstring claims exact-match confinement ("serves those two directories and nothing under, beside or symlinked from them"). server.py's module docstring claims the same thing in its own words ("checked, exactly, against the roots the server was started with") and then, two sentences later, states the opposite ("Configured roots come from --root flags and, additively, from the client's own MCP roots capability"). The code implements the second, permissive reading: `server.py:187` unions client-advertised roots into the authorization allowlist before the exact-match check ever runs.
evidence: B16-H1 and B22-H1 independently measure the same behavior: a server started with zero `--root` flags still serves whatever directory the connected client advertises, and a server started with one `--root` accepts any additional directory the client names — verified end to end with `contained_path` passing for a file inside the newly-authorized, unconfigured directory. B22-H2 compounds it structurally: the one piece of foreign input this boundary parses (the client's advertised `file://` URI) has no single parse-or-raise step — an empty path silently resolves to the server's own cwd, and a non-empty/non-local URI authority is silently dropped rather than refused, so a malformed value becomes a plausible-looking authorized path instead of a typed refusal. B22-M4 shows a third contradiction: the fallback-selection branch defaults to an advertised root that matches *zero* configured roots, the opposite of what docs/agent-guide.md documents as the selection rule.
source: Clean Architecture (Martin) — a boundary's contract must be stated once and enforced at the boundary; a security invariant documented in a module docstring that the module's own code contradicts within the same file is the architectural equivalent of an interface with no enforced postcondition. This is also a direct instance of this repo's own CLAUDE.md rule: "Guards key on the invariant, not a proxy" — the invariant is "is this directory one the operator configured," and the code instead keys on "did the client mention it."
recommendation: Resolve the ambiguity as a design decision, not a bug fix scattered across three files. If `--root` is meant to be a confinement boundary (the reading every doc surface other than server.py's second sentence supports), client-advertised roots may only narrow the effective root among the configured set — never add to it — and a server started with no `--root` and no static configuration must refuse to serve rather than defer to the client. Encode that decision once, in repo_context.py's `_authorise`, and delete the union at server.py:187. Rewrite both docstrings to describe the one model that results, and give the URI parse (B22-H2) a single typed parse-or-raise step so a malformed advertised root is a refusal, not a coerced value.
confidence: HIGH

finding_id: 4

Treat "two adapters need the same non-adapter-specific behavior" as a standing signal to add it to `application/` rather than reimplementing, and add one test per resolved instance that asserts both call sites now produce identical output for identical input.

finding_id: 5
persona: ARCHITECT
severity: HIGH
scope: cross-module
files: [src/agentless_mcp/core/refs.py, src/agentless_mcp/core/cache.py, src/agentless_mcp/core/graph.py, src/agentless_mcp/core/resolve.py, src/agentless_mcp/core/patchlint.py, src/agentless_mcp/core/communities.py]
category: layers
issue: The import-linter layers contract treats `core` as one opaque member, so no direction is enforced inside the repo's largest layer. One concrete violation of the dependency-inversion principle already exists there: `core/refs.py` — a domain scan module — imports `core/cache.py`'s concrete `effective_source` factory function at runtime (not merely for typing), pulling `sqlite3`, `hashlib`, `util.filelock` and `util.platforms` transitively into every module that imports `refs`, including `graph`, `resolve`, `patchlint`, `communities`, `mermaid`, and all four application services that build on them.
evidence: B09-M1 verifies the split precisely: the *type* coupling is correctly inverted (`refs` depends on the `FileSource` Protocol, not the concrete `SqliteSource`, and `test_cache.py` substitutes a structural double), but the *module* coupling is not, because the Protocol is defined inside `core/cache.py` — the 1102-line SQLite persistence module — rather than in a neutral seam both modules could depend on, and `refs.py:111` calls `effective_source`, a concrete factory in that same infrastructure module, on every scan. The Phase-1 coupling metrics corroborate the asymmetry this produces: `core.refs` carries I=0.50 (Ca=7, Ce=7) — a domain module pulled to the middle of the instability scale by depending on a persistence module — while `core.cache` itself sits at I=0.56 (Ca=8, Ce=10, 1102 LOC), i.e. neither module is stably positioned relative to the other, and no contract prevents the direction from getting worse.
source: Clean Architecture (Martin) — the Dependency Inversion Principle applied to package structure: "depend in the direction of abstraction," and the abstraction a client needs belongs with the client (or a neutral module both share), never inside the implementation it is meant to decouple from. This repo's own CLAUDE.md states the same rule directly: "infrastructure imports the domain; the domain imports nothing" and "core is treated as one opaque member" in the dependency contract — which this finding shows is currently a blind spot, not a guarantee.
recommendation: Move the `FileSource` Protocol and the `effective_source`/`OnDemandSource` default into a small neutral module below both (`core/facts_source.py`, already recommended in B09), and have `cache.py` import it rather than defining it. That is a mechanical, behavior-preserving move — `FileSource` is purely structural. Once the module boundary is fixed, add an explicit intra-core layering rule to the import-linter configuration (e.g. `refs`/`graph`/`resolve`/`patchlint` may not import `cache`) so the contract that already holds informally everywhere else in `core` becomes machine-enforced rather than accidental.
confidence: HIGH

None of these three splits require a behavior change and each directly shrinks the coverage-gap surface named in its block's review.
